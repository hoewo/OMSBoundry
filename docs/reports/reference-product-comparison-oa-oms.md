# 参考 OA 与 OMS 六层边界对照

日期：2026-09-25  
状态：第二参考产品证据已就绪；不是第二真实客户验证

## 结论

OMS 可以作为第二个参考产品帮助缩小下一阶段方向，但目前不能作为架构已通过的证据。参考 OA 已有六个独立应用和 J1～J4 运行证据；OMS 当前是已接受业务规格和可运行的浏览器内存原型，生产服务、数据所有权、权限和外部集成仍未确定。

两份参考材料共同加强了“稳定 Base + 加法扩展”的候选方向：合同、主体／人员、义务与实际资金分离、文件版本和历史纠错应保持稳定；设计生产和施工履约应分别作为有自己生命周期的类型化业务能力装入；开票、审批、管理费、税务和经营汇总不能塞回 Contract、Money 或通用 Project。

该结论只决定下一步如何降低风险，不证明跨客户通用性。跨客户产品边界仍必须等待至少两个独立真实客户场景。

## 稳定共性

| 共性 | 参考 OA | OMS | 当前方向 |
| --- | --- | --- | --- |
| 合同事实 | Contract Ledger 已有 revision、补充、结算和关闭 | 甲方合同与施工队合同形成上下游链 | 保留 Contract 独立所有权，后续补双段链路而不复制合同表 |
| 主体、人员与角色 | People 已实现，Party 独立边界已接受 | 甲方、我方、施工队、工头和人员是主关系 | Party Directory 仍是下一项；People 保存人员／成员关系，消费应用保存角色和当时快照 |
| 义务与资金 | Money 已分离义务、实际收付、核销和余额 | 应收确认、应付确认、付款授权、到账和付款明确不是同一事实 | Money 内核保持不变，审批只决定业务时点，不冒充资金事实 |
| 文件证据 | Evidence 已拥有文件版本和受控访问 | 合同、票据、审批和资金记录均要求保留附件版本 | 业务应用只保存 File ID／Version 和业务含义 |
| 历史与纠错 | revision、调整、冲销、反向和替代已实际验收 | 关键金额、日期、对象变化后需重新确认，历史版本保留 | 所有新增域先定义纠错，不用静默覆盖换取开发速度 |
| 最低部署 | D1 单节点组合已验证 | OMS 接受一台 ECS 最低生产部署 | 继续用同一镜像／契约支持单节点，逻辑独立不等于每应用一台机器 |

## 六层差异账

| 层 | OMS 证据 | 归属判断 | 当前处置 |
| --- | --- | --- | --- |
| 稳定 Base | 合同链、义务／资金、文件版本；独立发票生命周期 | 前三项已有稳定内核；Billing 是跨两个参考产品出现的独立责任域候选 | 保持现有内核；Billing 在票据更正／撤销证据完整后做独立纵向闭环 |
| 配置 | 甲方、施工队、工头、人员等术语和角色显示 | 稳定 key 可以配置显示，但配置不能改变事实所有权 | 先完成 Party／People 边界，再提供术语和角色映射 |
| 版本化策略 | 三类审批、管理费、税务和人员支付条件 | 业务时点可确认，审批矩阵、费率、舍入、税务和例外仍未知 | 保持 `needs_business_evidence`，不建万能审批或页面公式 |
| 类型化扩展 | 施工范围、年度预算、人员履约；经营汇总 | 施工履约类似 `design-v1`，应拥有自己的状态与完成条件；经营汇总不得污染 Money | 待建立 Construction Operations 与 Operating Ledger 候选边界，不先写通用平台 |
| 客户装配 | 以甲方合同串联主体、施工、票据、资金、汇总和资料 | 最终由 Suite Manifest、公开契约、菜单和旅程装入 | OMS 原型可作体验参考，不能直接成为生产组合 |
| 客户专项 | 当前没有真实客户证据 | 无法确认哪些差异只属于某个客户 | 不创建客户 fork、客户字段或客户 migration |

## 对 OA 完整体计划的影响

1. **Party Directory 继续是当前首项。** 两个参考产品都依赖主体稳定 ID、当前档案和历史快照；继续在合同和台账内各存一套可变主体目录会放大后续耦合。
2. **Party 之后优先调查 C3 Billing／Invoice 纵向闭环。** 开票在参考 OA 和 OMS 都出现，并且与合同、应收和实际回款有清楚的事实分离；它比管理费、奖金或通用审批拥有更多稳定证据。这里的“优先调查”不是直接编码，进入实现前仍需补齐红冲、作废、退票、跨期和附件版本规则。
3. **施工履约是第二生产类型候选，不进入通用 Project。** 它需要施工范围、年度预算、人员名册和完成条件，边界应像 `design-v1` 一样由独立类型化应用验证。
4. **经营总账只作为独立候选责任域。** 它记录公司收支汇总，不是 Money Flow 的义务账，也不是专业财务总账；科目、期间关闭和调整规则未确定前不实现。
5. **审批暂不建设成通用平台。** 当前只稳定了三个业务时点；流程编排、权限、门槛和例外仍需业务证据。

## 保留的未知项

- 甲方合同与施工队合同的正式状态机、分配和结算规则；
- Party 当前档案、施工队 Group、人员 Membership 和支付时快照的准确分工；
- 发票红冲、作废、退票、跨期更正和税务口径；
- 应收确认、应付确认、付款授权的审批矩阵和例外层级；
- 管理费基数、费率、舍入、税务和调整；
- 人员款项直接支付或经施工队分发的责任与合规；
- 施工范围、年度预算和完成条件的正式生命周期；
- 经营汇总的科目、期间关闭、调整及外部财务系统边界；
- OMS 的生产身份、数据所有权、契约、故障恢复和真实部署证据。

## 下一道门槛

本对照完成后，当前不依赖外部环境的顺序保持为：

1. 实现并验收 Party Directory 的独立闭环与 Contract／Money／Project 消费迁移；
2. 对 Billing／Invoice 做 C3 进入证据审计，只有生命周期和纠错充分时才实现；
3. 每次增量继续回归六个 Level A、J1～J4、可裁剪子集和六层变化账；
4. 公司 Ubuntu 或个人 ICP 任一路径可用后，用同一发布物补完整入口链；
5. 取得第二真实客户后，才运行正式跨场景比较并判断 Base 是否真的可复用。

如果 Party 或 Billing 迫使共享业务表、复制可写事实、建立客户核心分支或现场补丁，应把它记录为架构反证并调整边界，而不是为了按计划完成而掩盖问题。
