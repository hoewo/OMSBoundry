# M5 Contract → Money Flow 启动就绪门禁

里程碑：M5 启动前控制  
日期：2026-09-20  
状态：生效；尚无案例通过

## 1. 目的

本门禁决定一条参考材料是否足以启动首个 Contract → Money Flow 实现切片。它防止把页面设想、单句需求、OA 定制算法或技术人员猜测直接固化为两个稳定系统之间的业务契约。

业务输入使用[真实业务案例采集表](../../templates/contract-money-flow-case-intake.md)。门禁只判断证据是否完整，不要求客户先设计 API、事件或数据库。

## 2. 状态

每份案例只允许以下状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 尚在采集，不能进入契约设计 |
| `needs_business_confirmation` | 已有材料，但存在必须由业务责任人回答的歧义 |
| `ready_for_contract_design` | 九项业务证据齐全，可以设计公开契约与联调测试；仍不能直接宣称实现完成 |
| `rejected_as_reference_only` | 只能说明某个系统如何定制，不能证明目标业务流 |

只有 `ready_for_contract_design` 可以为首个 M5 实现分配功能编号。

## 3. 九项必过证据

| 编号 | 必须证明的事实 | 通过标准 | 不通过示例 |
| --- | --- | --- | --- |
| R1 | 权威来源与触发时点 | 明确到合同激活、某个 revision、阶段／最终结算或另一项可识别事实 | “合同有变化就同步” |
| R2 | 来源版本与历史身份 | 能区分原事实、后续版本、重复送达和撤回后重提 | 只传当前合同金额 |
| R3 | 目标账簿与交易双方 | 明确 Money Flow owner、债权方、债务方及 Contract 主体映射 | “甲方付给我方”，但存在资质单位或代收方 |
| R4 | 义务内容 | 应收／应付、精确金额、币种、到期日和多期拆分均可重现 | “按合同金额生成应收” |
| R5 | 决策责任 | 明确谁确认、是否只建议、能否拒绝以及拒绝后如何处理 | “系统自动判断” |
| R6 | 业务重复身份 | 业务人员能说明哪些事实相同代表重复、哪些代表新义务 | 只依赖按钮点击或传输次数 |
| R7 | 来源变化处置 | 至少覆盖一条真实金额变化，并说明已确认／已核销状态下的预期 | “覆盖成最新金额” |
| R8 | 故障与人工责任 | 明确外部不可用时本系统是否继续、谁发现遗漏、谁重试和对账 | “失败自动重试”但无人负责 |
| R9 | 可验收结果 | 至少有首次形成义务和后续变化两个 Given／When／Then 样例 | 只有字段清单，没有结果 |

任意一项不通过，案例都不得进入 `ready_for_contract_design`。技术人员不能用默认值、配置开关或“第一版先这样”替业务补答。

## 4. 立即退回条件

出现以下任一情况，直接标记 `needs_business_confirmation` 或 `rejected_as_reference_only`：

- 只有界面截图、字段列表、原型或一句“合同自动生成应收”；
- 只说“照 OA 做”，但没有确认 OA 的固定 Project、经营链和算法在目标客户仍成立；
- 没有明确 Money Flow 账簿所有者，或把客户名称等同稳定 Party 身份；
- 把合同金额、结算金额、开票金额、实际收款和义务余额混成一个金额；
- 要求一个系统直接写另一个系统的表；
- 要求变更时覆盖已确认义务、实际资金或 Allocation 历史；
- 没有重复投递、目标系统离线和人工对账结果；
- 案例含未脱敏个人信息、账号、银行卡、证件或原始敏感文件。

## 5. 通过后的工程输出

案例通过只授权“契约设计”，不直接授权实现。工程人员必须按顺序形成并评审：

1. 业务事实映射：来源事实、目标 Obligation Suggestion 和最终 Obligation 的责任边界；
2. 版本化 Contract Snapshot 或公开查询契约，包含来源 ID、revision、发生时间和金额依据；
3. 从 R6 推导的稳定幂等键与重复载荷冲突规则；
4. 连接器过程状态：待处理、待确认、已接受、已拒绝、失败、可重试和人工对账；
5. 来源变化到 Obligation Adjustment Suggestion 的追加规则，禁止覆盖既有事实；
6. 双系统分别离线、重复投递、超时、部分成功和恢复后的联调矩阵；
7. 契约兼容性测试、连接器集成测试和两个 actual release 的端到端联调方案；
8. 关闭连接器后两个系统仍可独立完成各自核心闭环的回归方案。

上述设计通过后，才允许进入代码实现。每个切片仍须遵循“一项功能、实现、自动化验证、真实 PostgreSQL 验证、必要联调、再进入下一项”。

## 6. 当前判定

OA 参考证据审计状态为 `rejected_as_reference_only`：它证明“合同有效／结算金额影响应收统计”是现实信号，却没有提供 R1 至 R9 所要求的通用跨系统责任链。当前尚无案例达到 `ready_for_contract_design`，因此 M5 保持未开始。

OMS 雏形参考证据审计同样为 `rejected_as_reference_only`：它明确由独立审批通过形成应收／应付，合同、发票和结算材料本身都只是依据。若未来选定 OMS 为实际装配客户，可以 `needs_business_confirmation` 为起点补齐缺失事实，但当前不能提升为通用产品契约。

两个参考源对“合同金额是否直接形成应收”的答案相反，进一步证明不能提前实现自动确认。判定依据见[OA 参考证据审计](./contract-money-oa-reference-audit.md)和 [OMS 雏形参考证据审计](./contract-money-oms-prototype-reference-audit.md)。
