## 1. 目的与边界

本审计只回答两个问题：既有 OA 中实际存在怎样的合同、应收、开票和收款关系；这些关系是否足以启动 OMSBizFoundry 的 Contract → Money Flow 连接器。

参考源是 `/Users/crispydog/Workspace/Hoewo/WebProjects/RoadSystemOA/road-design-oa-system` 在干净提交 `826e0fc65aa09947fc4f64f62a2644fa5d11a302` 的代码与规格。它是一个完成度较高、定制化明显的项目，不是 OMSBizFoundry 的产品规格。没有读取或复制客户数据库、账号、文件和生产数据。

本审计没有修改两个应用、数据库 schema、公开 API 或 `connectors/`；也没有把参考项目的页面、字段、岗位和算法写入稳定内核。

## 2. 参考实现中的实际业务流

```text
项目下录入合同
  → 按签订时间依次应用补充／修订文书
  → 得到当前有效合同金额
  → 按“结算是否跟随合同金额”选择有效金额或人工结算金额
  → 直接作为该项目的预期应收基础

经营人员另行人工登记开票
经营人员另行人工登记甲方付款
  → 已收 = 甲方付款合计
  → 未收 = max(预期应收 - 已收, 0)
```

这不是“合同系统发布事实、连接器幂等消费、收支系统确认义务”的跨系统流程。它是同一个 OA、同一个 Project 上的内部统计：合同和补充协议提供应收基数，开票与付款由用户分别录入，查询时再聚合。

## 3. 可确认的参考事实

| 参考事实 | 直接证据 | 对 BizFoundry 的意义 |
| --- | --- | --- |

## 4. 明显定制、不得直接复用的内容

| OA 规则或结构 | 为什么不能进入通用内核 |
| --- | --- |
| 所有合同与财务记录强制挂在 Project 下 | 两个 BizFoundry 小系统已明确不依赖 Project，Money Flow 来源也可以是订单、结算单、人工依据或外部系统 |
| 固定 `client_to_qualification`、`qualification_to_our_company` 两层经营链 | 这是特定公司的资质合作链，不代表任意客户的债权方、债务方与账簿所有者关系 |
| 合同金额直接等于预期应收 | 合同金额、当前有效金额、结算金额、分期和实际形成的义务可能不同，需要真实确认时点与责任人 |
| `float64` 保存金额 | 不满足 BizFoundry 的精确十进制金额不变量 |
| 奖金、管理费、设计／勘察／咨询费和 `1.065` 公式 | 属于行业与客户算法，不是合同或收支台账的稳定事实 |
| 用最新合同及金额占比推断财务记录费种 | `financial_service.go:2592-2658` 自身也标为 heuristic；推断结果不能成为可审计的来源事实 |
| 一个 `FinancialRecord` 承载奖金、成本、支付、开票、专家费、委托等多种语义 | 会混淆义务、票据、实际资金和分配；BizFoundry 已把这些事实分开 |
| 财务记录允许直接编辑和删除 | 与 Money Flow 已建立的不可变事实、调整、冲销和反向纠错模型冲突 |

## 5. 与当前两个小系统的对应

当前 Contract Ledger 已能提供合同 revision、补充／更正、独立结算、终止、关闭、主体快照和 Evidence。当前 Money Flow Ledger 已能人工建立并确认义务，登记实际收付，执行多对多 Allocation，并以调整、减免、反向和关闭保留历史。

因此，OA 参考没有发现需要修改两个系统核心事实模型的新证据。真正缺失的是两个稳定内核之外的业务决策与公开连接契约：

```text
哪个 Contract 事实
  → 在什么业务时点
  → 由谁确认
  → 相对于哪个 Money Flow 账簿所有者
  → 对哪个债权方／债务方
  → 形成何种金额、币种和到期日的义务建议
```

## 6. M5 启动就绪度

| 必需证据 | OA 是否提供 | 当前结论 |
| --- | --- | --- |
| 一个真实、脱敏的合同到义务案例 | 否 | 只有同一 OA 内部统计规则，没有跨系统责任链 |
| 权威触发事实：激活、阶段结算、最终结算或其他 | 否 | 实现同时存在有效合同金额与结算金额，无法替客户选择 |
| 账簿所有者、债权方、债务方映射 | 否 | 固定两层 chain 是客户定制，不能泛化 |
| 金额、币种、到期日形成规则 | 部分 | 只有金额聚合，没有通用币种、到期日和分期规则 |
| 自动创建还是人工确认建议 | 否 | OA 是人工录入付款／开票，不存在义务建议流程 |
| 合同后续变更如何影响已确认义务 | 否 | 没有调整建议、拒绝、已核销或已关闭义务处理规则 |
| 来源 snapshot、版本与幂等业务键 | 否 | 同库查询没有定义公开、版本化的交换契约 |
| 失败、重试、拒绝和人工对账责任 | 否 | 没有跨系统失败场景 |
| 端到端验收样例 | 否 | 没有可用于连接器联调的期望输入与输出 |

结论：OA 提供了一个有价值的业务信号，但不足以启动 M5 实现。M5 保持“未开始”，不创建空连接器、outbox、事件表、共享 Party 或跨库读取。

## 7. 启动 M5 所需的最小样例

不需要客户先写完整需求文档。业务人员可直接填写[真实业务案例采集表](../../templates/contract-money-flow-case-intake.md)，工程人员再按 [M5 启动就绪门禁](./m5-start-readiness-gate.md)复核。只需提供一条真实流程的脱敏样例，并由业务责任人确认以下事实：

1. 来源合同当前处于哪个 revision，是否已有阶段或最终结算；
2. 哪一个事实触发处理，触发发生时间是什么；
3. Money Flow 中的本方账簿所有者、债权方和债务方分别是谁；
4. 应收还是应付，金额、币种、到期日如何得到；
5. 系统应只产生待确认建议，还是允许满足某些条件后自动确认；
6. 同一来源重复送达时应认作同一件事的稳定业务键；
7. 合同金额后来增加、减少或重述时，已确认、已部分核销、已归零或已关闭的义务分别怎样处理；
8. 建议被拒绝、连接失败或目标系统不可用时，由谁重试、撤销或人工对账；
9. 给出至少一个“首次形成义务”和一个“后续合同变化”的期望结果。

## 8. 有证据后的候选首切片

以下只是待确认方案，不是当前产品事实：

```text
Contract 发布不可变的、版本化来源快照
  → 独立连接器按来源 ID + revision 幂等接收
  → 形成待确认 Obligation Suggestion
  → Money Flow 管理员明确接受或拒绝
  → 接受后调用 Money Flow 公开命令形成自己的 Obligation
```

第一切片优先只做“一条已确认来源形成一条待确认应收或应付建议”。暂不自动确认，不处理批量导入、票据、现金、核销，也不让连接器修改已存在义务。只有真实样例确认触发事实和映射规则后，才为它分配 M5 功能编号并编写契约与联调测试。
