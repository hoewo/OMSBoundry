## 2. OMS 雏形实际表达的业务关系

```text
甲方合同／施工队合同／结算材料／发票／回款计划
  → 作为应收或应付申请的依据
  → 独立审批通过
  → 形成已确认应收或已确认应付
  → 独立登记实际到账或付款
  → 通过核销减少义务余额

已确认应付
  → 独立付款申请与付款授权审批
  → 获得执行授权
  → 独立记录实际付款
```

这条流程明确否定“合同存在或合同金额变化就自动形成义务”：开票、回款、结算材料、施工合同和人员名册都只能作为依据；应收、应付和付款授权分别在独立审批通过时形成。

## 4. 原型只能证明展示意图

`platform/app/oms-workbench.tsx` 把合同、应收、回款、应付和审批分别建成独立的虚构数组。样例体现：

- 应收记录持有自己的编号、确认金额、已收、未收、预计日期和审批编号；
- 应付记录持有自己的编号、确认金额、已付、未付、资金条件与付款授权；
- 审批记录分为应收确认、应付确认和付款授权；
- 审批抽屉明确提示“通过后形成义务或授权，不代表实际到账／付款”；
- 金额用 JavaScript `number`，页面统一展示人民币符号，未定义生产币种和精确金额契约；
- 审批通过／退回、付款批次、导入和附件都只改变当前会话或显示模拟结果。

因此原型数据可以帮助阅读产品意图，但不能提供 R2 的稳定来源身份、R6 的幂等业务键或 R8 的跨系统失败恢复证据。

## 5. 与 OA 参考的关键差异

| 问题 | OA 参考 | OMS 雏形 | 跨场景可保留结论 |
| --- | --- | --- | --- |
| 什么形成预期应收 | 合同有效／结算金额直接成为统计基础 | 独立应收审批通过；合同等只作依据 | 不能从合同金额自动确认义务 |
| 应收是否独立事实 | 没有独立 Obligation，查询时从合同聚合 | 有独立已确认应收与预计日期 | Money Flow 必须拥有自己的义务事实 |
| 后续变化 | 合同金额变化直接重算统计 | 关键变化重新审批并保留原版本 | 变化应追加决定／调整，不覆盖历史 |
| 实际资金 | 人工登记付款记录 | 独立登记到账／付款并核销 | Cash 与 Obligation 长期分离 |
| 决策责任 | 未提供 | 审批通过，但审批矩阵仍开放 | 自动确认不是跨场景稳定规则 |

两个参考源在最关键的触发规则上不一致。这不是需要“二选一”的实现细节，而是足以禁止提前固化自动连接器的反证。当前唯一稳定的共同信号是：合同事实可以提供业务依据，义务和实际资金必须在 Money Flow 中保持独立、可追溯并可受控确认。

## 7. 对 M5 候选设计的约束

本审计不把审批系统变成两个小系统的强制前提。它要求未来 M5 契约区分两种来源：

1. Contract Snapshot／Settlement Fact：说明义务依据是什么；
2. Confirmation Decision：说明由谁、在什么规则下决定形成义务。

在不安装外部工作流时，Money Flow 管理员对 Obligation Suggestion 的明确接受可以承担 Confirmation Decision；若客户已有审批系统，则连接器可以引用其版本化批准决定。无论哪种方式，Contract Ledger 都不能仅凭合同激活或金额变化越权创建正式 Obligation。

这一约束只收紧责任边界，不代表现在已经确定事件格式、审批集成或建议状态机。它们仍须由通过门禁的真实案例驱动。
