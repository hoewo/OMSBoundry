# Money Flow Ledger：Obligation 坏账处置边界审计

里程碑：M4  
候选编号：MF-M4-005  
日期：2026-09-19  
状态：边界审计完成，功能延期；未进入实现

## 审计目的

判断当前材料是否足以把“坏账”实现为一个小而完整、不会污染现有 Obligation 余额语义的业务事实。

本审计不是坏账功能规格，不承诺数据库、接口或页面。当前代码、迁移和运行时不存在 Bad Debt 事实，不能使用 Amount Adjustment、Remission、负 Allocation 或手工余额覆盖代替。

## 已有可靠事实

- 坏账只可能属于 `receivable`；应付义务被债权人免除属于 Remission，不是本方“坏账”；
- Amount Adjustment 表示义务依据金额发生变化，不能表达可收回性判断；
- Remission 表示债权人已经有效免除义务，可能消灭对应应履行金额；
- 坏账描述应收的可收回性处置，未必消灭债权或债务人的原义务；
- 实际资金仍只能通过 Cash Transaction 与 Allocation 表达，坏账不能伪装成收款；
- 余额、处置、关闭和会计凭证必须保持可解释，不能通过更新根表汇总字段形成第二真相源。

这些事实足以否决错误复用，但不足以确定一个可执行写入模型。

## 当前无法回答的关键问题

| 问题 | 选择会改变什么 |
| --- | --- |
| 坏账是“预计难以收回”、会计减值，还是最终核销？ | 决定它是可变估计、不可变处置，还是会计系统事实 |
| 处置后原债权是否继续存在并允许追收？ | 决定是否还能对原 Obligation 形成 Allocation |
| 后续追回款核销原 Obligation，还是记录独立 Recovery？ | 决定资金兼容规则、余额公式和报表口径 |
| 坏账是否允许部分转回或全部撤销？ | 决定是否必须同时交付 Reversal／Recovery，而不能只做单向事实 |
| Amount Adjustment 发生在坏账之后时如何重算？ | 决定调减下限是否包含坏账，以及历史估计如何保持可解释 |
| “业务剩余”“法律应履行”“预计可收回”和“账面净额”需要展示哪几个？ | 决定是否需要多套明确命名的余额投影 |
| 什么来源、审批或证据足以记录坏账？ | 决定最小权限与审计边界；单一 administrator 原因文本未必足够 |
| 坏账是否允许触发受控关闭？ | 决定生命周期前置条件和关闭依据引用 |

现有 OMS 雏形、仓库讨论和 Money Flow 实现均没有给出这些问题的可验证答案。

## 方案审计

### 方案 A：像 Remission 一样直接扣减 outstanding

否决。若坏账不消灭原权利，直接扣减现有 outstanding 会使后续 Allocation 被上限约束拒绝；它在运行时等价于另一种 Remission，只是换了名称。

### 方案 B：只记录 Bad Debt，不影响任何余额

否决。它无法回答系统最基本的“还预计收回多少”，用户也无法判断该事实对业务的实际作用。一个没有投影语义的写入表不是完整功能。

### 方案 C：新增独立可收回余额投影

这是当前唯一可能保持语义一致的方向，但还不能实现。至少需要同时定义：

```text
settlement outstanding
  = effective amount - net allocated - remitted

expected collectible
  = settlement outstanding - net bad-debt disposition
```

其中 `settlement outstanding` 是否允许继续 Allocation、坏账如何转回、追回款如何入账、调额如何影响处置，必须一起锁定。只实现一张单向坏账表会留下不可恢复的业务断点。

### 方案 D：实现会计减值、备抵与分录

否决进入当前小系统内核。Money Flow Ledger 不是总账，当前也没有科目、期间、凭证、计量方法或税务规则。若未来需要，只能通过明确会计适配器或另一个窄域系统衔接。

## 当前决定

1. `MF-M4-005` 在边界审计后延期，不创建 migration、领域类型、HTTP 入口、页面字段或可写汇总；
2. 当前 `outstanding` 继续只表示 `effective - net allocated - remitted`，不暗含坏账、减值或预计损失；
3. 不使用 Amount Adjustment、Remission、Cash Reversal、负 Allocation 或关闭事实冒充坏账；
4. 不把坏账加入 Allocation 上限或 Amount Adjustment 下限，避免在语义未定时固化错误不变量；
5. 下一切片可以独立审计受控关闭，但只能基于已经实现且可重建的余额与处置事实，不能假设坏账已经存在；
6. 当真实客户场景能够回答上述关键问题时，重新打开本候选并先形成正式规格和 ADR，再决定是否编码。

## 重新进入实现的最小证据

至少需要一条真实业务样例，明确给出：

- 一条具体 receivable 在处置前后的法律权利、业务余额和账面口径；
- 部分坏账、全部坏账与后续追回款各自如何处理；
- 记录人、批准人、依据文件和生效时间；
- 是否允许转回，以及转回后能否继续 Allocation；
- 处置与 Obligation 关闭、统计和导出的关系。

在这些信息出现前，继续编码不会让系统更接近稳定可用，只会制造一个名称正确但行为错误的模块。
