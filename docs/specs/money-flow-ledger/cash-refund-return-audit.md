# Money Flow Ledger：真实退款／退回款边界审计

里程碑：M4  
候选编号：MF-M4-010  
日期：2026-09-20  
状态：边界审计完成，功能延期；未进入实现

## 审计目的

判断 OMS 雏形、已完成度较高的 OA 项目、BizFoundry 讨论材料和现有 Money Flow 事实模型，是否足以定义一个小而完整的真实退款／退回款闭环。

本审计不是退款功能规格，不承诺 migration、领域类型、接口或页面。当前运行时不存在 Refund 事实，也不能使用负金额、修改原 Cash Transaction、错误录入 Reversal 或 Allocation Reversal 冒充真实退款。

## 已经成立的稳定边界

- 原收款或付款确实发生、之后资金又反向移动时，必须保留两次真实资金移动；不能让原 Cash Transaction 失效；
- 收款后的退款从本方账簿视角是新的资金流出，付款后的退回款是新的资金流入；新事实必须有自己的发生日、账户标签、外部流水号、来源依据、Actor 和审计；
- 退款金额仍必须为正的精确十进制，方向由事实类型表达，不能用负数绕过现有金额不变量；
- 新资金应引用原 Cash Transaction，并冻结或校验原方向、双方主体、币种和账簿所有者，不能只靠描述文本建立关系；
- 部分退款和多次退款是必须预留的现实场景，累计金额与并发上限不能由页面单独保护；
- 错误录入的 Cash Reversal 与真实退款语义不同：前者说明原资金不应生效，后者说明原资金和后续反向资金都真实发生；
- 错误 Allocation 的 Reversal 也不能自动代表退款对义务结清关系的影响，因为原 Allocation 在退款发生前可能完全正确；
- 退款、拒付扣回、银行手续费、付款失败退票和合同金额调整可能引起相似现金方向，但不能在没有证据时合并为同一种事实。

这些边界足以确定哪些做法错误，但不足以形成可验收的写入模型。

## 参考材料能够证明什么

### OMS 雏形

OMS 目前只有合同、应收／应付、收付款和审批展示信号。仓库中出现的“退回”均指审批退回，不是资金退款；没有原资金引用、部分退款、多次退款或义务重新打开的真实业务样例。

因此 OMS 不能为退款的不变量提供产品事实。

### OA 已实现项目

OA 能证明甲方支付等资金记录在真实项目中有使用价值，但它把支付、开票、奖金和成本合并为可编辑、可删除的 `FinancialRecord`，金额使用浮点数，并用 `income`／`expense` 方向参与统计。现有枚举和服务没有退款／退回款类型，也没有原资金引用、累计退款上限、退款纠错或 Allocation／Obligation 语义。

OA 的统计还会把未收金额的负值截为零，无法作为超收、退款或余额恢复规则的证据。它只能作为“现有客户实现没有回答退款问题”的反例，不能复制为 BizFoundry 内核。

### BizFoundry 现有模型

现有 Cash Transaction 已经提供独立正金额的 `receipt`／`payment`、双方 Party 快照、账户标签、外部流水唯一范围和不可变审计；ADR-0018 也明确真实退款必须是第二次资金移动。

但现有 Allocation 只表达一笔正向资金对一条义务的核销，Allocation Reversal 只表达原核销错误。当前没有“原核销在当时有效、后来因退款而部分或全部失去结清效果”的事实类型，因此不能只增加一条反向 Cash Transaction 就宣称义务余额仍然正确。

## 当前无法回答的关键问题

| 问题 | 选择会改变什么 |
| --- | --- |
| 收款退款是否重新增加原 receivable 的 outstanding？付款退回是否重新增加原 payable？ | 决定退款是否只影响现金统计，还是同时改变义务结清投影 |
| 原资金已分配给多个 Obligation 时，退款按原 Allocation 比例、用户选择还是另一业务依据回退？ | 决定是否需要独立 Refund Allocation、金额拆分与上限 |
| 原 Allocation 在退款前是正确事实，是否允许使用现有 Allocation Reversal？ | 决定历史是否会被错误解释为“原核销录入错误” |
| 退款后基础义务已经取消、减免或调额时，是重开旧义务还是建立新的退款义务？ | 决定生命周期、关闭与 revision 兼容规则 |
| 已经 `closed` 的 Obligation 遇到退款是否允许重开？ | 决定是否必须同时交付 Closure Reopen，而不是绕过终态保护 |
| 部分／多次退款累计是否必须小于等于原资金金额；手续费、利息或赔偿如何处理？ | 决定金额上限和哪些金额必须成为独立资金或义务 |
| 第三方代退、原付款方／收款方变更或不同账户退回是否允许？ | 决定主体兼容和账户约束 |
| 退款是否必须与原币种一致；跨币种退回如何处理？ | 决定金额可比性与汇兑边界 |
| 退款本身录错时能否使用现有 Cash Reversal；退款的退款是否允许链式引用？ | 决定纠错闭环和关系图约束 |
| 银行拒付、付款原路退回、主动退款和争议扣款是否共享生命周期？ | 决定一个 Refund 类型是否足够，还是需要不同事实 |
| 新外部流水如何去重，原流水引用是否参与唯一范围？ | 决定导入幂等与数据库索引 |

现有材料没有一条完整案例能够同时回答资金、Allocation、Obligation 和纠错结果。

## 方案审计

### 方案 A：把原 Cash Transaction 更新为负数或减少金额

否决。它会覆盖已经发生的真实资金、破坏外部流水唯一占用和历史 Allocation，并让历史时点无法重建。

### 方案 B：使用 Cash Transaction Reversal

否决。Cash Reversal 表示原资金事实不应继续生效，并要求先把净 Allocation 反向为零。真实退款需要同时保留原资金与第二次资金移动，二者不能共用语义。

### 方案 C：新增一条普通反方向 Cash Transaction，只关联原资金

当前不进入实现。它可以使实际流入／流出历史完整，却没有回答原义务是否重新形成 outstanding。若原资金已核销义务，系统会出现“钱已经退回，但义务仍显示结清”的潜在矛盾。

### 方案 D：退款前强制使用现有 Allocation Reversal

否决。原 Allocation 在资金首次发生时可能完全正确；后来退款是新的业务事实。把它标记为错误核销会扭曲审计原因，并且完整 Reversal 无法表达退款只涉及原 Allocation 的一部分。

### 方案 E：自动按原 Allocation 比例回退义务余额

否决。比例分摊、指定义务、建立新义务或不影响义务都是不同业务选择。没有真实案例时自动分摊会制造不可见的业务决定，跨多条 Allocation 时也无法证明符合用户意图。

## 当前决定

1. `MF-M4-010` 在边界审计后延期，不创建 migration、领域类型、接口、页面或退款汇总；
2. Cash Transaction 继续只接受正金额 `receipt`／`payment`；原事实不得因真实退款被修改或失效；
3. Cash Reversal 继续只处理原资金登记错误或最终确认未发生，不扩展为退款；
4. Allocation Reversal 继续只处理错误核销，不用于表达原核销正确但后来资金退回；
5. 当前 Obligation outstanding、Closure 和历史余额公式不暗含退款效果；系统也不声称已经支持净退款口径；
6. 在退款对义务结清效果明确前，不先实现“只有现金、不处理义务”的半闭环；
7. 获得真实退款时间线后，先形成正式规格和 ADR，再决定是新增 Refund、Refund Allocation、义务重开／新义务中的哪一种组合。

## 重新进入实现的最小证据

至少需要两组真实、可验收的业务时间线：

- 一笔已核销 receivable 的收款发生部分退款，明确退款前后原资金、每条 Allocation、Obligation outstanding 和关闭状态；
- 一笔已核销 payable 的付款被部分或全部退回，明确是重开原义务、创建新义务还是只保留未分配反向资金；
- 至少一例多次退款或一笔资金分配多个义务，给出累计上限和分摊决定人；
- 说明主动退款、银行拒付和付款失败退回是否同类，以及手续费如何记录；
- 给出原流水与退款流水、账户、币种、双方主体、业务日期、记录时间、操作者和证据；
- 给出退款录错、重复导入、并发退款和已关闭义务的处理结果。

这些证据出现前，延期比制造一个只能记录反向现金、却可能让义务继续错误结清的功能更符合“小而精、稳定可用”的目标。
