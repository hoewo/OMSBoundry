# Contract Ledger：合同草稿签约主体与角色

里程碑：M1  
功能编号：CL-M1-003  
状态：已接受

## 目标

用户能够在合同草稿中引用主体目录中的主体，为其填写该主体在本合同中的业务角色，并在激活前移除错误关联。每次变更都具备幂等保护和草稿版本并发检查。

本功能建立的是可修改的草稿关联，不是签约时历史快照。主体名称、登记标识和主体 revision 只在后续激活功能中冻结为不可变快照。

## 角色边界

- 角色是合同关系中的业务角色，不是系统权限角色或客户岗位；
- 角色采用合同内自由文本，去除首尾空白后长度为 1 至 100 个字符；
- 不预置或强制“甲方、乙方、设计方、施工方”等行业枚举；
- 同一主体可以在同一合同中承担多个不同角色；
- 多个主体可以承担同一角色；
- 同一合同内“主体 + 不区分大小写的角色”只能存在一个有效关联。

## 草稿引用与激活快照

草稿关联保存 Party ID，并在页面中读取主体当前的：

- 主体类型；
- 法定名称或姓名；
- 登记标识；
- Party revision。

草稿存在期间，主体当前资料若发生受控变化，草稿页面应读取最新资料。激活合同的后续功能必须把 Party ID、Party revision、法定名称、登记标识和合同角色一起冻结，之后主体目录变化不得改写已激活合同历史。

## 写入命令

### 添加签约主体

输入：

- Command ID；
- Contract ID；
- Party ID；
- 角色；
- Expected Draft Version。

成功后创建有效关联，并把合同 `draft_version` 加一。

### 移除签约主体

输入：

- Command ID；
- Contract ID；
- Draft Party Link ID；
- Expected Draft Version。

成功后给关联记录写入移除时间，并把合同 `draft_version` 加一。关联不物理删除；移除后可以通过新的添加命令重新关联。

## 幂等与并发规则

- Command ID 在本功能的添加和移除命令之间全局唯一；
- 相同 Command ID 和相同标准化负载重放时，返回第一次执行结果，不再次变更草稿版本；
- 相同 Command ID 携带不同负载时返回幂等冲突；
- Expected Draft Version 必须等于数据库当前版本，否则返回并发冲突；
- 幂等重放优先于版本检查，因此已成功命令在合同继续变化后仍可安全重放；
- 只有 `draft` 状态可以添加或移除签约主体；
- 不存在的合同、主体或有效关联必须明确拒绝。

## 用户流程

```text
打开合同草稿详情
  → 从本系统主体目录选择主体
  → 填写合同内业务角色
  → 提交 Command ID + Expected Draft Version
  → 服务端在事务内锁定合同并检查幂等、状态和版本
  → 新增关联或标记移除
  → draft_version + 1
  → 返回刷新后的合同草稿详情
```

## 验收标准

- 能从主体目录向合同草稿添加签约主体及自由文本角色；
- 同一主体可以承担多个不同角色；
- 多个主体可以承担同一角色；
- 重复的有效“合同 + 主体 + 角色”被拒绝；
- 能在激活前移除错误关联，数据库保留移除事实；
- 添加和移除均支持安全幂等重放；
- 复用 Command ID 但改变负载时明确拒绝；
- 过期 Expected Draft Version 被拒绝，且不改变关联和合同版本；
- 非草稿合同不能变更签约主体；
- 页面具备 CSRF 防护和请求大小限制；
- 真实 PostgreSQL 集成测试验证事务、约束、版本和清理；
- 不依赖 Money Flow、Project、Approval 或外部主体中心。

## 本功能不包含

- 新建或编辑主体；
- 签署代表；
- 合同草稿其他字段的编辑或取消；
- 激活、Party Snapshot 或正式 revision；
- 权限、Actor 和完整审计事件；
- 文件、证据和电子签章；
- 应收应付或其他跨系统业务流动。
