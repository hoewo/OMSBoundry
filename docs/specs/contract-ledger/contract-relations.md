# Contract Ledger：合同关系图

里程碑：M2  
功能编号：CL-M2-004  
日期：2026-09-19  
状态：已完成并验证

## 目标

用户能够在两份已经形成正式 revision 的合同之间登记一条有方向、有类型、可追溯且不可变的关系，并从任一端查看关系。关系只描述合同之间已经确认的业务联系，不把合同塞进固定父子树，也不允许上游合同自动改写下游合同。

本功能只属于 Contract Ledger。它不创建应收应付、资金、核销或结算事实，不要求 Money Flow Ledger 在线。

## 独立关系事实

一条 Contract Relation 保存：

- 独立 Relation ID；
- 来源 Contract ID 与登记时的 source revision；
- 目标 Contract ID 与登记时的 target revision；
- 关系类型；
- 可选生效日期；
- 可选说明，最多 500 个字符；
- 可信 Actor 和记录时间；
- 形成它的幂等 Command ID。

关系是独立有向边，不形成新的合同 revision，不推进任何合同状态，也不复制或修改任一合同的金额、主体、Instrument 或条款。列表展示登记时两个 revision 的编号与标题快照；合同后来形成新 revision 时，旧关系仍明确指向登记时看到的版本。

## 第一版内置类型与方向

第一版采用小而明确的内置集合，不建设客户可编程关系类型注册器。方向必须按下面语义解释：

| 类型代码 | `来源 → 目标` 的含义 | 防环 |
| --- | --- | --- |
| `funding_source_for` | 来源合同是目标合同的资金来源或上游依据 | 是 |
| `entrustment_basis_for` | 来源合同是目标合同的委托或上游依据 | 是 |
| `subcontract_of` | 来源合同是目标合同的分包合同 | 是 |
| `specific_under_framework` | 来源合同是目标框架合同下的具体合同 | 是 |
| `supersedes` | 来源合同替代目标合同 | 是 |
| `references` | 来源合同引用目标合同 | 否 |

同一来源、目标和类型只能存在一条关系；两份合同间允许存在不同类型的边。反向边不是同一事实，但对标记为“防环”的类型，新增边不能使该类型形成有向环。防环不把图限制为树：同一合同仍可有多个上游或多个下游。`references` 允许双向引用，但自关联始终禁止。

## 状态和 revision 边界

- 来源和目标都必须已经形成正式 revision，即状态只能是 `active`、`terminated` 或 `closed`；
- `draft` 和 `cancelled` 不是正式合同事实，不能建立关系；
- 命令携带来源和目标的 Expected Revision；
- repository 在同一事务中按固定顺序锁定两份合同，核对状态与 current revision；
- 任一端 revision 已变化时整条命令拒绝，不静默改成新 revision；
- 成功关系保存两端当时的 revision 外键，保证引用的快照真实存在；
- 建立关系不要求两份合同币种、主体、状态或生效日期相同。

## 幂等、并发和不可变性

- 每次建立关系使用 UUID Command ID；
- 同一 Command ID 与相同负载重放返回原 Relation，不新增关系或审计；
- 同一 Command ID 改变来源、目标、类型、revision、生效日期、说明或 Actor 时返回幂等冲突；
- 不同命令并发建立同一条边时恰好一条成功，另一条得到重复关系冲突；
- 防环类型按关系类型串行完成“检查路径 + 插入”，两个反向命令并发时不能同时成功；
- Relation、relation command 和通用审计都是追加事实，数据库禁止更新或删除；
- 当前功能不提供删除、停用、改向或改类型。发现错误需等待独立的受控纠错规格，不能直接修改历史。

## 页面与权限

- 正式合同详情同时显示“作为来源”的出向关系和“作为目标”的入向关系；
- 每条关系显示类型、另一端登记时的编号／标题、两端 snapshot revision、生效日期、说明、Actor 和记录时间；
- administrator/editor 可以从正式合同详情进入“建立合同关系”页面；viewer 只读；
- 目标选择页面复用现有合同检索和稳定分页，只允许选择 `active`、`terminated` 或 `closed` 合同；
- 选定目标后页面明确展示完整的“来源 → 目标”语义、两端当前 revision，并要求用户确认；
- POST 使用 CSRF、Command ID 和两端 Expected Revision；成功后重定向来源合同详情；
- 校验错误返回 `422`，状态／revision／重复／防环冲突返回 `409`，不存在返回 `404`；
- 页面绝不接受请求提供 Actor，Actor 只来自登录会话。

## 审计

成功写入一条 `contract_relation_linked` 通用审计，归属来源合同，包含 Relation ID、目标 Contract ID、类型、两端 revision、生效日期和说明。目标合同详情仍通过入向关系本身显示 Actor 和记录时间。幂等重放不重复审计。

## 明确不做

- 草稿关系、待确认关系或审批流程；
- 自定义类型注册、客户行业层级和固定 Project 父对象；
- 百分比分配、金额分摊或关系金额；
- 自动继承主体、金额、状态、条款或生命周期；
- 删除、停用、改向、改类型或受控纠错；
- 图形化拓扑、跨全部类型统一防环或路径业务推断；
- 外部上下文引用、Evidence Reference；
- Contract → Money Flow 事件、义务建议或任何跨系统写入。

## 验收标准

1. 六种内置类型的合法输入都能形成一条独立关系，并明确显示方向。
2. 自关联、未知类型、非法日期、超长说明、草稿或取消合同明确拒绝且不写事实。
3. 两端 Expected Revision 在事务锁内校验；任一端变化都返回冲突。
4. 相同 Command ID 重放只返回原关系；改变负载返回幂等冲突。
5. 同一来源、目标、类型的不同命令并发时恰好一个成功。
6. 五种防环类型不能形成直接、间接或并发环；`references` 可以形成双向边。
7. Relation、command 和审计在同一事务提交；故意制造末端审计失败时不留下部分事实。
8. 直接更新或删除 Relation 与 command 时 PostgreSQL 返回不可变事实错误。
9. 详情从来源和目标两端都能读取关系，并显示登记时 revision 的编号和标题快照。
10. administrator/editor 可以建立，viewer 不显示表单且直接 POST 返回 `403`；匿名访问仍受登录保护。
11. 目标选择检索、分页、选定和确认流程通过 HTTP 测试。
12. Money Flow 数据库和应用停止时仍能完成全部验收，不产生任何跨系统事实。
