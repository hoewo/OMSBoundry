# Contract Ledger：合同草稿创建与列表

里程碑：M1  
功能编号：CL-M1-002  
状态：已接受

## 目标

用户能够创建一个具有稳定身份的合同草稿，并在合同列表中看到持久化结果。草稿还不是正式合同事实，可以在后续功能中补充签约方、修改或取消；只有单独的激活功能才会冻结主体快照并产生 revision 1。

## 本功能的数据

- Contract ID：系统生成的稳定 UUID；
- Command ID：每次创建表单生成的 UUID，用于防止重复提交；
- 编号命名空间：必填，1 至 64 个字符；
- 合同编号：必填，1 至 100 个字符；
- 标题：必填，1 至 200 个字符；
- 通用分类：可选，最长 100 个字符；
- 币种：三个英文字母，保存前转为大写；
- 合同总额：可选的非负十进制数，整数最多 18 位、小数最多 6 位；
- 签署日期：可选的 `YYYY-MM-DD`；
- 生效日期：可选的 `YYYY-MM-DD`；
- 状态：固定为 `draft`；
- Draft Version：固定从 1 开始；
- Current Revision：草稿阶段为空，激活后才产生。

合同金额使用十进制文本校验并保存到 PostgreSQL `numeric(24,6)`，应用代码不经过 `float32` 或 `float64`。

## 编号范围

当前第一版采用单账簿部署，一个 Contract Ledger 实例代表一个账簿。因此编号唯一范围是：

```text
当前账簿 + 编号命名空间 + 合同编号
```

数据库对命名空间和合同编号执行不区分大小写的唯一约束。未来增加多账簿能力时，必须显式引入 `ledger_id`，不能把唯一性退化为全局合同编号。

## 幂等规则

- 相同 Command ID 和相同业务负载重复提交时，返回第一次创建的合同，不产生第二条数据；
- 相同 Command ID 携带不同业务负载时拒绝，返回幂等冲突；
- 不同 Command ID 使用已经存在的“命名空间 + 合同编号”时拒绝为编号冲突。

## 日期规则

签署日期和生效日期是两个独立事实，本功能不强制生效日期晚于签署日期，因为现实合同可能约定追溯生效。履约开始和结束日期在后续合同条款功能中增加。

## 用户流程

```text
打开合同列表
  → 填写编号命名空间、编号、标题、分类、币种、金额和日期
  → 提交
  → 服务端校验与幂等检查
  → 持久化 draft
  → 返回列表并显示创建结果
```

## 验收标准

- 能创建金额已确定的合同草稿；
- 能创建金额暂未确定的合同草稿；
- 金额全程使用精确十进制表示；
- 非法编号、标题、币种、金额和日期被拒绝；
- 编号唯一约束不区分大小写；
- 重复 Command ID 不重复创建数据；
- 重复 Command ID 但负载变化时明确拒绝；
- 列表从 PostgreSQL 读取草稿；
- 表单具备 CSRF 和请求大小限制；
- 单元测试、真实 PostgreSQL 集成测试和 HTTP 验收通过；
- 功能不读取 Party 内部表以外的数据，也不依赖 Money Flow、Project 或 Approval。

## 本功能不包含

- 添加签约方和合同角色；
- 编辑或取消草稿；
- 激活合同和生成 revision；
- 金额分类明细；
- 履约期间；
- 项目或其他 Context Reference；
- 文件和 Evidence Reference；
- 审批、用印和法务流程；
- 自动生成应收应付。
