# 阶段一：参考 OA 小系统重组验证

日期：2026-09-23  
状态：Level A、Level B、首次实际组合变化的定制化六层验收与当前高保真可移植开发包已完成；完整入口、真实公司 Ubuntu、真实客户与跨场景产品边界仍待验证

## 1. 阶段目标

OMSBizFoundry 的阶段一产品目标是：**以现有完成度较高、定制化明显的 OA 为参考产品，使用可独立运行的小系统和正式装配组件，重组出一套能够完成所选核心业务旅程的参考 OA。**

这个目标解决的不是“已经掌握整个行业”问题，而是先回答一个更可验证的问题：

> 当前小系统边界是否足以解释并承载一套真实存在、已经长期演进的定制 OA，而不退回单体复制，也不把客户差异塞进万能平台？

参考 OA 提供现成的业务对象、操作、状态变化和定制痕迹。它是阶段一的主要业务证据源，但不是行业标准、目标客户需求或可以逐表复制的产品规格。

## 2. 成功不等于逐功能重写

阶段一不追求页面、表结构和历史实现逐项一比一复制。以下结果不构成完成：

- 只把当前完整组合部署成功；
- 只做出与旧 OA 相似的菜单和页面；
- 把旧 OA 的表、角色、固定公式或客户术语原样拆进多个服务；
- 为了覆盖全部旧功能而增加万能字段、自由 JSON、统一流程或客户核心分支；
- 只证明某个接口可调用，没有证明用户能完成端到端工作。

阶段一验证的是业务结果等价、责任边界可解释和组合交付成立，不是代码结构或界面实现相同。

## 3. 分两步确定范围

### 3.1 先做参考能力与旅程盘点

从参考 OA 的当前规格、代码和可运行行为中，按可追溯证据记录：

1. 用户在什么场景下发起操作；
2. 输入了哪些业务事实；
3. 谁确认、谁拥有以及状态如何变化；
4. 最终得到什么可观察结果；
5. 发生撤回、变更、重复、失败或纠错时如何处理；
6. 该能力属于稳定业务信号、客户配置、客户策略、类型化扩展、装配还是客户专项。

盘点结果必须区分“参考 OA 已有行为”“BizFoundry 已覆盖能力”“明确缺口”和“仍需业务确认”，不能因为代码中存在某个页面或字段就自动进入阶段一核心范围。

### 3.2 再确认阶段一核心旅程

阶段一只实现能共同检验小系统边界的一组核心旅程。候选范围至少从以下方面取证，但是否进入实现由盘点结果决定：

- 企业登录、人员与小组协作；
- 项目或工作对象作为业务上下文；
- 合同建立、变更、结算、关闭和证据；
- 应收应付、实际收付款、核销、调整与追溯；
- 文件证据和权限；
- 参考 OA 中审批、奖金、外委、资质合作等明显定制能力的正确放置位置。

候选清单不是预先承诺全部实现。只有能够说明“问题 A → 可验证结果 B”、责任所有者和验收证据的旅程才能进入阶段一核心范围。

## 4. 目标装配

参考 OA 的公网运行仍使用统一基础设施：

```text
Browser
  → Nginx
  → Gateway
  → IAM
  → 按核心旅程选装的业务小系统
```

- Nginx、Gateway、IAM 和部署运维包是基础设施与装配组件，不拥有 OA 业务事实；
- Contract Ledger、Money Flow Ledger、People & Groups、Evidence Service 继续拥有各自已经确认的事实；
- Project Workspace、连接器、策略或新的类型化扩展只有在参考旅程提供证据时才进入；
- 未选装业务系统不得成为隐藏启动依赖；
- 系统之间只通过版本化 API、快照、事件或能力凭证协作，不跨库读取和写入。

## 5. 阶段一验收门槛

只有同时满足以下条件，才能称为“成功用小系统搭建参考 OA”：

1. **范围可追溯**：核心旅程均能回溯到参考 OA 的规格、代码、可运行行为或经确认的脱敏案例；未知内容保持开放。
2. **结果可完成**：用户能够从统一入口完成每条核心旅程，并得到与参考 OA 业务目的相符的可观察结果。
3. **责任可解释**：每项事实、状态转换、权限和纠错都有唯一所有者，不依赖共享数据库或口头约定。
4. **小系统仍独立**：Contract、Money Flow、People & Groups 等仍可单独安装、启动、升级、备份和恢复；移除非必需应用不会破坏其自身闭环。
5. **差异有归属**：参考 OA 的定制差异均落在稳定内核、配置、策略、类型化扩展、客户装配或客户专项中的唯一一层。
6. **没有客户核心分支**：参考 OA 组合不复制仓库、不现场修改核心镜像，也不要求长期维护 OA 专用核心分支。
7. **装配可交付**：同一版本化发布物可按 Suite Manifest 在 D1 环境安装、登录、备份、恢复和升级；外部依赖及故障影响明确。
8. **差距透明**：未覆盖、被拒绝或仍需业务确认的能力有明确清单，不用空壳、假数据或技术演示冒充完成。

阶段一通过只证明当前架构成功承载了一个高价值参考产品。它不证明已经找到整个商业圈子的最终通用边界；后续仍需用第二个独立真实场景检验哪些能力可以继续保持稳定、哪些只是 OA 专项。

## 6. 已确认的首个 Demo 范围

首个 Demo 固定包含：

- J1：项目立项与责任建立；
- J2：经营承接、合同、人工确认应收义务、实际收款与核销；
- J3：设计生产组织、成果交付与项目完成；
- J4：项目资料和状态追溯。

第一生产类型为设计项目。咨询、勘察或测绘中的第二类型不作为首个 Demo 的通过条件，而在首个 Demo 暴露出稳定扩展边界后另行选择。合同或结算事实只作为 Money Flow 义务的来源依据，责任人明确确认后才形成正式义务。

首个 Demo 先使用本地业务验证模式：各应用使用同形本地模板 IAM Provider 并通过独立本地地址访问，不要求 Nginx、Gateway、中心 IAM 或公网域名参与。业务闭环通过后，同一业务发布物再进入完整组合入口验收。详细行为规格见 [`arckit/spec/assembly/reference-oa-demo.md`](../../../arckit/spec/assembly/reference-oa-demo.md)。

## 7. 第一项实现工作

下一项工作不是立即补写新应用，而是完成一次**参考 OA 全景能力与核心旅程审计**：

1. 建立可追溯的能力和旅程清单；
2. 将每项能力映射到现有小系统、基础设施、候选扩展或明确缺口；
3. 选择最小但能代表 OA 业务闭环的阶段一旅程集合；
4. 为每条旅程定义用户结果、责任边界、失败恢复和验收方式；
5. 依据结果决定 Project Workspace、连接器、审批适配或其他类型化扩展的实现顺序。

不依据旧 OA 菜单顺序、数据库表数量或现有路线图编号直接开始新的业务实现。

全景审计已经完成，见[参考 OA 全景能力与核心旅程审计](./oa-reference-capability-journey-audit.md)。六个应用的 Level A 独立 Demo 与 Level B 高保真组合均已通过。Level B 在同一组非真实数据上完成 J1～J4、People／Contract／Money／Design 的 revision 与纠错历史、幂等重放和 Contract／Money／People／Evidence／Design 五来源逐项停机隔离；设计阶段仍由独立 Design Operations 拥有，没有进入通用 Project 内核。

后续业务验证按 [Demo Validation 2](../../../arckit/spec/assembly/demo-validation-2.md) 执行：Level A／Level B 是持续回归基线；从最小 J1～J4 到高保真 J1～J4 的实际变化已检验配置、策略放置门槛、类型化扩展、连接器拒绝、客户装配和客户专项反证，未产生客户核心分支。当前高保真 `v0.1.0-demo.11` 开发包已从同一无源码归档依次通过六个独立产品、设计交付／商业台账两类可裁剪子集和全量组合的 clean-room 复演，并包含只读 Ubuntu 目标机预检；公司 Ubuntu 完整入口、正式 clean-HEAD 发布和个人试验田公网复验继续作为独立部署轴；第二个独立客户场景继续验证跨场景产品边界。
