## 3. 参考 OA 的真实主脊柱

参考 OA 当前四个主要入口是项目立项、项目管理、项目资料管理和项目统计信息。合同、收付、招投标、生产文件、批复审计、外委和奖金都从 Project 上下文进入；后端绝大多数业务 API 也以 `/projects/:id/...` 为资源边界。

因此参考 OA 的主脊柱是：

```text
账号与业务权限
  → 项目立项与项目角色
  → 同一项目下并行推进经营链和生产链
  → 文件、金额、人员和完成状态形成可追溯结果
  → 项目资料与统计提供跨项目查询
```

这并不说明 Contract、Money Flow 或 Evidence 应当成为 Project 的内部模块。它只说明组合体验需要一个 Project 上下文来关联并呈现这些独立事实。

## 6. 代表性端到端旅程

### J1：项目立项与责任建立

**问题 A**：项目资料和后续工作开始前，没有统一项目身份、责任人和可访问范围。

**结果 B**：有权限的人派发项目时填写名称与经营负责人；被指派人员在完成普通项目立项前补正式编号及类型，生产负责人和其他成员按后续需要配置。完成后进入同一 OA 项目基本详情；系统保留责任历史，并只向有相应范围与能力的人显示项目和本人待办。此为参考操作时机，不将全部责任齐备统一设为立项门槛。

- 所有者：Project Workspace 拥有项目身份、基础资料、Assignment 和待办派生；People 提供 Person／Group 引用；IAM 签发有界凭证。
- 关键状态：草拟／待补全／已立项／取消，以及 Assignment 生效／结束；具体命名仍需规格确认。
- 失败与纠错：重复编号、已离职人员、并发修改、负责人更换和取消立项必须保留可解释历史。
- 验收：从统一入口创建项目、指派人员、相关人员看到待办；移除 Project 后 Contract、Money 和 People 仍可独立运行。

### J2：经营承接、合同与回款闭环

**问题 A**：项目从承接资料到合同、应收和实际回款分散，无法可靠判断经营进度。

**结果 B**：用户明确记录承接方式或不适用，提交所需证据，建立并结算合同，由责任人确认应收义务，登记实际收款并核销，项目能够从正式事实派生经营状态。

- 所有者：设计运营扩展拥有承接方式和阶段；Contract 拥有合同；Money 拥有义务、资金和核销；Evidence 拥有文件。
- 首切片边界：合同到义务先由用户明确确认并保存来源快照；不预建自动 Contract → Money 连接器。开票与管理费不作为经营闭环成立条件。
- 失败与纠错：文件上传失败、合同 revision 冲突、义务建议未确认、错误收款或错误核销分别由事实所有者处理，不由 Project 改写目标数据。
- 验收：同一项目页面可经正式 API 完成链路并回显来源；停掉 Money 后合同仍可操作，Project 明确显示资金能力不可用而不伪造成功。

### J3：生产组织、成果交付与项目完成

**问题 A**：项目类型不同导致人员、阶段和必交成果不同，留空又无法区分未完成与不适用。

**结果 B**：用户选择一个或多个项目类型，为项目安排人员；每种类型按自己的阶段推进，明确记录不适用，上传并引用成果，所有经营和生产条件满足后得到可解释的项目完成结果。

- 所有者：Project 拥有项目类型关联与项目 Assignment；设计运营扩展拥有阶段、适用性、成果要求和完成投影；Evidence 拥有文件版本。
- 首切片范围：至少覆盖一种完整生产类型，再证明第二种类型可以通过类型化定义加入而不修改 Contract、Money、People 或 Evidence 核心。
- 失败与纠错：恢复“不适用”、替换文件版本、阶段条件回退、人员更换和扩展停机后都必须保持历史可解释。
- 验收：项目完成状态可下钻到具体经营／生产条件和正式证据；删除菜单或隐藏按钮不能绕过服务端权限。

### J4：项目资料与状态追溯

**问题 A**：参与人需要按项目找到有权访问的合同和生产证据，并理解项目为什么处于当前状态。

**结果 B**：用户从项目资料入口查询和下载被授权文件，从项目状态下钻到来源事实；系统记录技术访问审计，业务下载统计若启用则使用明确投影。

- 所有者：Project 聚合 Resource Link；各来源应用拥有业务引用含义；Evidence 拥有文件和技术访问。
- 失败与纠错：来源应用不可用、引用版本缺失、签名 URL 过期或权限变化时明确失败，不返回陈旧的伪成功结果。
- 验收：跨项目越权被服务端拒绝；Evidence 停机不破坏 Project、Contract 或生产状态事实，只让字节访问明确不可用。

## 7. 阶段一首个核心集合提案

阶段一不是先复制全部旧 OA，而是先共同完成 **J1 + J2 + J3 + J4**。四条旅程缺一不可：

- 只有 J1 是项目通讯录，不是 OA；
- 只有 J2 会退回合同和收支台账组合，无法验证设计生产业务；
- 只有 J3 会把生产扩展做成孤岛，无法验证稳定台账复用；
- 没有 J4，文件和状态只是散落功能，不能形成可追溯工作产品。

首个集合明确延期以下能力：项目包／子项目转换、完整开票生命周期、通用审批平台、生产成本／外委完整来源流程、奖金与薪酬、考勤、全部公司统计、回款提醒、客户专用管理费和 `1.065` 公式。延期不表示永不实现；它表示这些能力不用于证明第一条结构假设，后续必须逐项取得真实生命周期和纠错证据。

## 8. 对下一实现顺序的影响

审计支持 **M9 仍是下一业务应用方向**，但需要收窄并拆分：

1. 薄 Project Workspace 正式规格已经固定，只拥有 Project、基础资料、Assignment、Resource Link 和项目自身历史；
2. 同时定义“设计项目运营”类型化扩展的边界，避免把项目类型、阶段、承接方式和批复审计做成万能 Project 字段；
3. 先完成 J1 的最小纵向闭环，再以一种生产类型接入 J3；
4. 通过正式 API 把现有 Contract、Money、Evidence 接入 J2／J4，目标应用仍作最终授权和写入；
5. Contract → Money 自动连接器、Billing、奖金和通用审批继续等待真实规则，不因 OA 首屏需要而提前实现。

上述顺序已在 2026-09-25 实现为六应用／六数据库的 Level B 高保真 J1～J4 组合，并通过空库执行、立即幂等重放和 Contract／Money／People／Evidence／Design 五来源逐项停机隔离。从最小组合扩展到该高保真基线的实际变化也已完成六层账目：配置、`design-v1` 类型化扩展和客户装配成立，规则冲突下的自动连接器与无证据客户能力被明确拒绝，未产生客户核心分支。`v0.1.0-demo.11` 开发包已从同一无源码归档先复现六个独立产品，再复现设计交付／商业台账两个子集及同一全量业务基线，并包含只读 Ubuntu 目标机预检；获授权后仍须在公司 Ubuntu 验证正式发布与完整入口，第二个真实客户场景继续检验跨客户适配。设计项目运营扩展保持独立责任域。

## 9. 已接受的产品取舍

阶段一首个可验收集合采用 J1～J4，奖金、外委、成本、开票和项目包不进入首个 Demo。第一生产闭环使用设计类型；第二类型在首个 Demo 通过后根据实际扩展证据选择，不预先承诺咨询、勘察或测绘。合同或结算到 Money Flow 义务由责任人明确确认，不立即自动生成。

业务架构验证先在本地运行，各应用使用同一 IAM 契约的本地模板 Provider 和独立入口。Nginx、Gateway、中心 IAM 与统一 Workbench 的完整入口验证使用同一业务发布物在后续环境执行，不成为 J1 第一纵向闭环的启动前提。

## 10. OA 完全体（全业务范围）可行性结论

### 10.1 可以实现的含义

对参考 OA 当前代码、确认需求、领域模型和路由的复核没有发现必须共享业务表或合并数据所有权才能成立的业务关系。Project 可以继续作为工作上下文，IAM、People、Party、Contract、Money、Evidence 和各生产类型分别拥有事实；经营承接、Billing、成本外委和奖金也可以作为新增责任域，通过版本化来源快照、命令或事件协作。因此当前架构能够承载 OA 完全体。

这个结论只表示架构不存在已知阻断，不表示当前代码已经完整，也不表示仅靠配置即可完成。

### 10.2 当前实现与完整目标之间的差距

| 层次 | 当前事实 |
| --- | --- |
| 已有运行骨架 | IAM／入口基础、People、单项目 J1、Contract、Money、Evidence、`design-v1` 与 J1～J4 组合 |
| 已接受但未完成 | Contract／Money 的 Party 目录迁移、项目级完整权限、完整双租户矩阵与完整 OA 总装；Party 管理页和 Project 客户选择已完成本地 D1 人类工作流验证，真实浏览器可视点击仍待补证 |
| 需要扩展 | 项目包与子项目、双段业务链、咨询／勘察／测绘、批复审计、项目完成投影 |
| 需要新增责任域 | 经营承接／投标、Billing／Invoice、成本／报销来源、外委／采购、Bonus／Compensation、跨域只读报表与工作队列 |
| 尚未确认 | 项目包合同分配、票据反向生命周期、退款语义、批复审计影响、真实审批、考勤工资所有权和回款提醒 |

OA 完全体因而是显著业务增量，不是页面补齐。每个缺口需要自己的问题 A、可验证结果 B、事实所有者、状态、纠错、权限和故障验收。

### 10.3 通过条件

完整目标按 C1～C8 业务旅程验收，并持续回归当前六个独立产品和 J1～J4 组合。统一页面可以聚合操作，但不得复制目标应用事实；跨域性能使用快照、事件和可重建读模型解决，不以跨库联表换取短期便利。

稳定 Base 加 Customer Overlay 是当前最合适的产品线候选方向：客户差异优先增加装配、策略、类型化扩展、连接器、投影和隔离专项。若完整 OA 实现必须修改每个客户的核心状态机、共享数据库或长期维护客户分支，则这次验证失败，必须重新调整边界。

完整业务规格见 [`arckit/spec/assembly/full-reference-oa-validation.md`](../../../arckit/spec/assembly/full-reference-oa-validation.md)，产品线技术假设见 [`arckit/tech/assembly/customer-overlay-research.md`](../../../arckit/tech/assembly/customer-overlay-research.md)。
