# OMS 一期 MVP 产品设计 v1

日期：2026-10-11  
状态：第一版产品基线；实现中的技术缺口与验证结果另行登记  
用途：约束 OMS 一期产品、页面、数据语义、装配入口和验收范围

实施状态（2026-10-20，BF-165）：项目详情已按第 4.3 节完整发布并完成板块化重排；合同、双向票据、回款与支付凭证按第 9 节统一接入 Evidence 安全预览；普通工作区、列表和详情已按第 7 节建立可读性与空间密度基线，简单业务详情、新增、编辑、筛选和导出统一使用居中业务弹窗，全部选择器继续使用同一锚定弹层。长期开页后的短期应用凭证和 CSRF 在变更前按正式链路刷新。OMS 已成为根域名登录后的默认服务端首屏，旧 OA 与参考页面收进独立旧版工作台。该实现仍是既有 Owner 的请求时组合投影，不改变事实所有权。

## 1. 产品目标与边界

第一版面向需要管理项目合同、票据与收付的企业，用尽量少的入口管理对外项目经营：建立项目，关联一个甲方和一个或多个施工方，维护合同应收与各施工方应付，登记实际开票、收票、回款和支付，并通过总览与台账看清当前余额。现实客户是否属于“资质单位”不是产品前提；系统中的当前公司统一称为“本方经营主体”。

第一版追求“使用简单、入口少、核心链完整”，不是会计总账、审批平台或工程进度系统。

当前明确不做：

- 公司内部人员薪酬、耗材、奖金、报销等内部成本；
- 工程是否开工、进行中或完工等项目进度；
- 应收／应付期限、逾期判断、催收任务和自动提醒；
- 项目进度、项目状态和项目归档；
- 付款申请、审批、授权和待执行流程；
- 发票与某一笔回款／支付之间的核销关联；
- 期初余额或期初累计开票、回款、收票、支付等专门记录；
- 退还甲方款项、施工方退款或其他反向资金记录；
- 脱离项目存在的收支或发票；
- 多币种、税费计算、银行接口、OCR、自动分类和复杂文件版本管理。

## 2. 信息架构

第一版固定四个一级入口：

| 一级入口 | 二级入口 | 主要目的 |
| --- | --- | --- |
| 经营总览 | 无 | 通过图表查看当前余额、期间收支和项目资金情况 |
| 项目经营 | 项目列表、甲方管理、施工方管理 | 建立项目及其甲方、施工方和约定金额 |
| 应收回款 | 应收管理、开票管理、回款记录 | 查看项目应收，登记我方向甲方开票和实际回款 |
| 应付支付 | 应付管理、支付记录、发票管理 | 查看施工方应付，登记实际支付和施工方提供的发票 |

登录后默认进入经营总览。电脑端使用左侧分层导航：一级工作区保持四项；当前一级工作区自动展开对应二级菜单，但不会自动收起用户此前展开的其他工作区，三个业务组可以同时展开并分别收起；内容区不再重复放置 Tab。手机端继续使用四项底部一级导航，并在顶栏下方显示当前工作区的紧凑二级导航。二级入口只切换同一工作区的业务视角，不改变事实所有权。

## 3. 经营总览

经营总览是纯查看页面，不提供新增、编辑等业务按钮。“新建项目”只位于项目列表。

第一版使用少量、可直接下钻的图表：

1. 回款圆环图：当前全部项目的已回款与未回款；
2. 支付圆环图：当前全部项目的已支付与未支付；
3. 月度收支柱状图：按所选年份／月份展示实际回款与支付；
4. 项目资金横向条形图：按项目展示应收、已回款、应付和已支付。

应收／应付余额图展示当前实时余额，不受月份筛选影响；期间柱状图按业务发生日期统计。点击图形进入已经带好时间、项目或状态筛选的对应列表。页面不放分析长文、重复副标题或操作按钮。

## 4. 项目模型

### 4.1 建立与关系

- 项目是第一版的业务主线；
- 一个项目关联一个甲方；
- 一个项目可关联一个或多个施工方；
- 一个项目只有一份甲方主合同，补充协议作为该合同附件；
- 同一项目中的同一施工方只保留一条关系和一条应付汇总，多份补充协议通过附件和金额更新处理；
- 不支持一个项目下存在多份独立甲方合同。

项目最低创建条件：项目名称、甲方、应收总额。项目开启日期默认当前日期，用户可以选择并在后续更新；它用于记录业务上的项目开始时间，与系统自动生成且不可由用户替代的创建时间不是同一含义。施工方、施工方应付总额、甲方合同文件和施工方协议文件都可以后续补充。

新建项目中的甲方选择器只显示当前启用的甲方档案，并在字段旁提供“创建甲方”入口。点击后关闭新建项目表单并进入“项目经营 → 甲方管理”，由用户显式完成主体建档；系统不得在项目表单中隐式创建主体、按名称自动匹配或保留半套项目。甲方创建完成后，用户再返回项目列表重新新建项目。

第一版不增加“期初汇总”记录。旧项目的历史背景可通过备注说明；所有累计开票、回款、收票和支付金额仍只来源于实际录入且未作废的对应记录。

项目名称允许重复，系统以不展示给用户的稳定 ID 区分。创建项目时如发现已有同名项目，明确提示用户并建议使用更易区分的名称，但经确认后仍允许创建；项目选择器使用“项目名称＋甲方＋开启日期”辅助区分同名项目。

项目尚未产生相关开票、回款、收票或支付记录时，可以更换甲方或移除施工方，但操作时必须使用阻断式确认窗口，清楚展示修改前后的主体和影响，不得只给轻量提示。一旦已经存在对应业务记录，直接禁止更换甲方或移除施工方，并说明须先作废相关记录；修正后再重新登记。主体档案中的联系人、电话和地址等资料不受该关系锁定影响。

### 4.2 应收与应付来源

- 项目应收总额是甲方合同总金额，例如 800 万元；它是最终应收／项目总收入，不是利润；
- 应收管理每个项目一条汇总，只读展示项目中的同一份数据；
- 每个施工方分别维护约定应付总额；金额可先留空，后续补录或调整；
- 应付管理每个“项目＋施工方”一条汇总；新增施工方后产生新条目；
- 项目应付总额是各施工方当前应付总额之和；
- 应收、应付汇总不能在汇总模块独立新增或编辑，只能随项目更新。

修改应收总额或施工方应付总额时必须填写修改原因并保留变更记录。若新总额小于已发生回款、支付、开票或收票，系统二次确认后允许保存，并以红色显示异常。

### 4.3 项目页面

项目详情使用独立完整页面，项目创建和编辑使用统一居中业务弹窗。项目详情只负责项目自身资料和汇总，不重复承担财务专用模块的操作。

项目详情按业务归属固定分为四个板块：项目资料／基本信息、甲方业务／合同与回款、施工方业务／合同与支付、金额变更与项目记录。页面顶部只提供返回项目列表；编辑项目位于基本信息板块，合同详情位于甲方业务板块，关联施工方和设置应付位于施工方业务板块。项目说明、创建时间和 revision 并入基本信息，不再作为脱离上下文的尾部区块。操作入口的位置用于说明业务归属，不改变底层 Owner、权限或命令。

项目详情默认展示：

- 项目名称、甲方、主合同及附件；
- 施工方、各自应付总额及协议附件；
- 甲方侧摘要：应收总额 → 累计开票 → 累计回款 → 未回款；
- 施工方侧摘要：应付总额 → 累计收票 → 累计支付 → 未支付；
- 施工方侧允许折叠查看每个施工方的汇总；
- 金额变更记录，以及弱化展示的创建／更新时间和操作信息。

项目资料更新时间必须明确命名为“项目资料更新”，不得让用户误以为它代表最近开票、收票、回款或支付。甲方／施工方金额链中的累计开票、累计收票、实际回款和实际支付同时展示有效记录笔数与最近业务日期；项目标题区显示四类票款中的最近业务日期。新增实际记录后的成功反馈给出该项目更新后的累计金额和笔数，便于用户立即核对；项目页仍不展开具体流水。

合同入口统一命名为“合同详情”，不再把入口局限为附件管理。居中详情弹窗按“合同身份与状态 → 合同金额 → 往来主体与日期 → 附件”的顺序渐进展示；合同内部编号不展示。草稿合同可以进入统一编辑弹窗修改名称、金额、签订日期和生效日期，保存时追加 Contract 草稿版本；已生效、终止、关闭或取消合同在第一版 OMS 中只读，不绕过 Contract 生命周期。附件上传仍是独立动作，失败不得回滚或重复合同编辑。

当一份上游合同能够唯一对应项目回款，或一份下游合同能够唯一对应“项目＋施工方”支付时，新合同金额低于已发生金额必须立即以红色提示，并在保存时二次确认后才允许形成异常状态。若同一方向存在多份合同而收付款未绑定到具体合同，第一版不得按聚合资金猜测某一份合同异常。

项目开启日期既在项目详情中展示，也作为项目列表中的独立日期列；它与数据库创建时间不同，列表不展示创建／更新时间。

项目详情不展示具体开票、收票、回款或支付流水，也不提供这些记录的新增按钮或专用模块跳转，避免页面信息过多。

### 4.4 项目列表

项目列表只突出：项目名称、弱化的甲方名称、项目开启日期、应收状态和应付状态。应收／应付状态正常只显示“已完成／未完成”，超额收付或负余额显示“金额异常”；列表不展示应收、未收、应付、未付的具体金额，精确金额进入项目详情或专业模块查看。创建时间和更新时间不占列表列位，只在详情中弱化显示；列表默认按项目开启日期倒序，状态列按异常、未完成、已完成排序。

项目筛选支持项目名称、甲方、施工方、回款状态和支付状态。筛选使用紧凑按钮与浮层，不长期占用一整行高度。

## 5. 甲方与施工方管理

甲方和施工方档案只有名称必填。联系人、联系电话、银行账户、税号、地址和备注等资料选填；第一版列表只显示少量必要字段，完整资料进入统一居中详情弹窗。

甲方管理和施工方管理按真实项目关系展示 Party Directory 主体：甲方来自 OMS 项目的 `client_party`，施工方来自项目中尚未解除的 `contractor-party` 关系，并显示对应关联项目数。新增但尚未建立项目关系的主体不进入任一角色列表，只保留在新建项目／关联施工方的可选主体中；保存反馈必须明确提示用户下一步建立关系。页面不向 Party 主档写永久甲方／施工方类型，同一主体可在不同项目承担不同角色，只有事实关系支持时才会同时出现在两个列表。

第一版不在甲方或施工方详情中增加关联项目区域。

被项目或业务记录引用的甲方和施工方不能物理删除，只能修改或停用；未被引用的误建资料可以删除。停用资料不再出现在新增选择器中，历史记录继续正常显示。

第一版不设置项目进度、项目状态或项目归档。未产生任何业务引用的误建项目可以删除；已经产生合同、施工方或财务记录的项目不得物理删除，只能修正项目资料并继续保留历史。

## 6. 财务汇总与实际记录

### 6.1 汇总入口

- 应收管理：一个项目一条记录，突出项目、应收总额、已回款、未回款和资金状态；备注只作为弱化的辅助信息；
- 应付管理：一个项目＋施工方一条记录，突出项目、施工方、应付总额、已支付、未支付和资金状态；备注只作为弱化的辅助信息；
- 应收和应付都是项目数据的只读投影，不提供新增和编辑；
- 应付列表不按项目分组，按条目产生时间倒序自然排列。

应收／应付备注的优先级低于开票、收票、回款和支付记录的备注，不占用主要视觉空间，也不在项目详情中重复展示。

资金状态由金额自动判断：未回款／部分回款／已回款，以及未支付／部分支付／已支付。第一版没有工程进度状态。

### 6.2 实际记录

第一版只登记已经实际发生的四类业务事实：

| 模块 | 业务含义 | 必填内容 | 自动带出／限制 |
| --- | --- | --- | --- |
| 开票管理 | 我方向甲方开出的发票 | 项目、金额 | 甲方由项目自动带出 |
| 回款记录 | 甲方实际支付给我方的款项 | 项目、金额 | 甲方由项目自动带出 |
| 发票管理 | 施工方向我方提供的发票 | 项目、施工方、金额 | 施工方只能从项目已关联施工方中选择 |
| 支付记录 | 我方向施工方实际支付的款项 | 项目、施工方、金额 | 施工方只能从项目已关联施工方中选择 |

四类记录都有业务发生日期，新增时默认当前日期，用户可以选择并在后续更新。四类记录还提供选填备注和附件。第一版不强制发票与回款／支付一一对应，也不提供可选关联；发票、资金分别累计。所有系统内部编号自动生成但不在页面展示，业务编号、银行流水号和发票号码暂不要求。

项目和四类实际记录都同时保存两类时间：系统自动生成、不可由用户输入替代的记录时间，以及默认当前日期、允许用户调整的业务日期。图表、日期筛选和业务排序使用业务日期；创建记录、审计和操作追踪使用系统记录时间。不得用其中一种覆盖或冒充另一种。

业务日期在界面和业务契约中精确到“日”，不要求用户填写时分秒；系统记录时间精确到秒。同一业务日期存在多笔记录时，使用系统记录时间作为第二排序条件，保证顺序稳定。

累计回款可以由多笔组成，累计开票和累计回款分别统计；未回款＝项目应收总额－有效实际回款。累计支付可以由多笔组成；未支付＝施工方应付总额－该施工方有效实际支付。

### 6.3 纠错与异常

- 四类实际记录保存后锁定所属项目、甲方和施工方，不允许通过编辑把记录转移到另一个项目或主体；选错时必须作废原记录后重新登记；
- 金额、业务日期、备注和附件允许后续编辑，修改后重新计算所有相关汇总与异常状态，并保留修改前内容、操作人和系统记录时间；
- 删除实际执行为作废并保留原记录、操作人和时间；
- 修改金额或作废记录时必须填写修改／作废原因；修改业务日期、备注或附件时暂不强制填写原因，但仍自动记录修改前后内容、操作人和系统时间。原因与变更记录只进入详情中的历史，不占用普通列表空间；
- 作废记录不参与任何汇总，列表默认隐藏，可通过“包含已作废”筛选查看；
- 新增回款超过应收、新增支付超过应付、累计开票超过应收或累计收票超过应付时，系统警告并二次确认，但允许保存；
- 保存超额记录后，相关金额以红色明确提示异常；
- 第一版不做申请、审批、授权和待执行状态，提前或错误登记由人工纠正。

## 7. 页面与列表统一规则

除项目详情和文件预览外，各入口统一使用“列表＋居中业务弹窗”。项目、甲方、施工方及四类实际记录可以新增／编辑；应收、应付等纯关联汇总只查看，不出现新增或编辑页面。简单记录的新增、编辑、筛选和导出使用同一弹窗容器；文件预览保持独立上层。

简单业务详情统一按“当前状态 → 核心金额 → 主体／日期／来源 → 备注／附件”渐进展示。应收／应付优先呈现总额、已发生金额和未发生金额；回款／支付优先呈现本次金额和业务日期；票据编辑先显示记录状态，再进入可更正字段；合同详情继续使用第 4.3 节的专用摘要，但视觉层级与普通详情一致。纯查看弹窗只提供关闭，不放置禁用的“仅查看”或无意义提交按钮。桌面弹窗居中并保留四周上下文，手机端占满视口；遮罩点击和 Esc 可关闭当前业务弹窗，文件预览关闭后返回原弹窗。

页面内所有选择器使用同一可见组合框：白色触发器、统一箭头、选中态和下拉层。原生 `select` 只保留为表单值、必填校验和既有事件源，并从视觉与指针交互中隐藏；统一下拉层挂载到页面顶层，根据触发器实时定位，靠近边缘时向内避让、下方空间不足时向上展开，同时支持方向键、首尾项、回车／空格选择、Esc 关闭、禁用状态和异步动态选项。筛选、分页、创建／编辑表单和合同切换不得各自实现另一套下拉样式。

列表规则：

- 发生记录默认展示全部时间并按业务发生日期倒序；
- 所有列表分页，默认每页 20 条，可切换 20／50／100 条；
- 筛选和排序先作用于全部结果，再执行分页；
- 搜索框和“筛选”按钮保持在一条紧凑工具栏内，浮层承载详细条件；
- 项目和施工方是主要业务识别信息；甲方可弱化或移至详情；
- 开票、收票、回款和支付列表必须展示发生日期、项目、金额和备注；涉及施工方的列表同时展示施工方；
- 内部记录 ID、创建编号等不展示；创建和更新时间只在详情中弱化显示；
- 备注列给相对更宽空间，最多显示一至两行；电脑端悬停、手机端点击、详情弹窗均可查看全文；
- 其他长文本同样省略展示，避免撑高列表。

空间与字号规则：

- 桌面侧栏应收窄到只容纳一级与当前二级导航，不用宽侧栏承载解释文案；1100px 以下进一步收窄，手机隐藏；
- 普通工作区使用侧栏之外的全部可用宽度，不再固定缩在 1440px 中央；项目详情保留阅读边界，但允许在大屏展开到 1720px；
- 列表正文以 13px 为可读基线，表头和辅助说明保持次级但不得依赖 8px 小字；详情字段、金额链、文件行和弹窗表单使用同一层级体系；
- 放大字号不能同步放大顶栏、标题区和筛选区；首屏空间优先给图表、列表和项目事实，不用空白或重复标题填充。

## 8. 筛选与导出

应收、应付、开票、收票、回款和支付列表支持导出 Excel。点击导出后先打开紧凑导出窗口，带入当前列表筛选条件，并允许在窗口中确认或补充项目、主体、日期、状态等适用条件。导出默认覆盖筛选后的全部记录，不受列表分页限制；预计数据量较大时明确提示生成可能较慢，再由用户确认执行。第一版不做 Excel 导入。

每次导出一个模块的一个工作表，包含该模块适用的项目、甲方／施工方、业务日期、精确金额、状态、完整备注和附件文件名，不包含附件文件本身或系统内部 ID。金额以数值单元格和“元”为单位保留两位小数。

核心筛选包括项目、施工方、甲方、回款／支付状态、发生日期范围和是否包含已作废。不同列表只显示与自身业务有关的条件，筛选能力不能通过大面积表单占据首屏。

## 9. 文件能力

甲方合同、补充协议、施工方协议、发票凭证和收付款凭证均支持选填多个附件。普通列表不展示文件名，只显示附件图标和数量；具体文件在详情页或详情抽屉中查看、预览、下载和作废。

所有详情中的附件统一使用同一文件行与预览层：PDF 和常见图片通过 Evidence 短期授权直接预览，图片支持缩放；关闭后回到原详情并释放临时地址。格式不受浏览器安全原生预览支持，或超过既有预览大小阈值时，页面明确说明并只提供下载，不把下载伪装成预览。第一版不提供 Office 转换、OCR、自动分类、在线编辑或复杂版本管理。文件数量、大小和允许类型服从现有 Evidence Service 的能力与安全限制，不为 OMS 单独建立文件存储或修改底层文件边界。

## 10. 金额规则

- 第一版只支持人民币；
- 应收、应付、开票、收票、回款和支付金额必须大于零，不接受零数或负数；
- 所有金额显示小数点后两位；
- 表单、业务列表、详情和 Excel 导出统一以“元”为单位并显示两位小数；
- 经营总览图表为便于阅读可以使用“万元”等缩写单位，但图表必须明确标注单位，悬停、点击或下钻后显示精确到元的完整金额；
- 输入最多保留两位小数；
- 汇总、差额、排序和导出使用精确金额表示，禁止二进制浮点计算；
- 后端优先复用现有整数最小货币单位或高精度十进制契约，不因 OMS 页面随意修改小系统数据库设计。

第一版不使用负数普通记录模拟退款。录入错误通过编辑或作废纠正；真实退款须在后续版本以独立、方向明确的业务类型设计。

## 11. 权限、身份与部署

Workbench 页面内“已经进入过某应用”不能当成长期授权。所有变更操作在发送 Owner 命令前重新通过 Gateway 换取该应用短期 Capability；读取只在 Gateway 明确说明入口凭证失效时允许一次重新换票和重读。普通权限拒绝、字段校验、revision 冲突、Owner 故障和其他业务错误不得自动重试。

第一版产品只要求两档业务能力：

- 查看：查看总览、列表和详情；
- 维护：在查看基础上新增、编辑和作废允许维护的记录。

授权优先复用现有 IAM 能力，不在 OMS 内另建角色系统。新增、修改和作废自动记录操作人、操作时间；普通列表不展示这些审计字段。

第一版确认保留登录并复用现有 IAM。账号由后台／既有 IAM 开通；部署阶段可以预置验收账号，但不得在 OMS 内增加自注册、匿名管理员或免登录旁路。

公网固定入口链为 `Browser → Nginx → Gateway → IAM → Unified Workbench OMS`。`https://oatest.antuinfo.cn/` 是一期默认产品入口，登录后直接进入 OMS；`/oms-v1/` 保留为同一工作面的显式别名。旧项目立项、项目管理、资料、统计和参考 Demo 统一由 `/legacy/` 进入“旧版工作台”，旧 `/oms/` 只保留为参考 Demo 兼容别名。业务浏览器不得直接访问 Workbench 或各事实应用的内部端口。

部署必须通过 Customer Overlay 配置 `OMS_OPERATING_PARTY_ID`，其值是 Party Directory 中本方经营主体当前档案的规范小写 UUID。该配置只声明“本次组合中我方是谁”，不授予任何能力，也不复制主体档案；为空、格式错误、主体停用或不可读取时，所有依赖本方方向的开票／收票新增动作失败关闭。旧 `OMS_QUALIFICATION_PARTY_ID` 只作为已有部署的兼容别名，不能继续用于新配置。只读 Demo／`preview=oa` 不得注入真实本方经营主体 ID。

甲方与施工方页面只从 Party Directory API 实际返回的持久化主体中，投影已有对应项目关系的主体；未关联的持久化主体只用于允许其参与后续建项／关联的选择器。Workbench 不得为了填满页面而注入演示、默认、推荐或兜底主体；没有对应角色关系时直接显示空状态并提供人工新增入口。主体在页面中的业务角色由项目关系确定，不能把 UI 所在页面写回为 Party Directory 的全局类型。

## 12. 后端兼容原则

本文件首先描述 OMS 页面、字段和使用流程，不等于要求按页面结构新建后端表。实现应优先复用 Project Workspace、Party Directory、Contract Ledger、Billing、Money Flow、Evidence 和 IAM 的现有事实与版本化能力。

OMS／Workbench 只负责编排和投影，不得取得上述应用的事实所有权；不能跨库读写、共享 ORM、复制金额事实或为了页面方便破坏现有数据边界。页面需求与现有能力不一致时，先做缺口矩阵，再决定只读投影、连接器、Overlay 或版本化兼容增强。

Money Flow 当前已有固定 `due_on` 下的逾期／账龄投影，但没有催收流程或自动通知，人工义务也尚不能表达无固定期限。当前 OMS 不接入这些能力，也不能填写假到期日。无固定期限、期限依据、追加式跟进和可选提醒已经列入后续兼容待办。

## 13. 已确认但仍需实现验证的体验要求

- 经营总览默认页能在数秒内看懂回款、支付和项目资金情况；
- 笔记本首屏尽量展示真实列表内容，压缩标题、页头和筛选区高度；
- 桌面、笔记本和手机均可用，手机不产生整页横向滚动；
- 复杂信息采用摘要、折叠和详情抽屉渐进展示，不用长文填充页面；
- 图表、汇总、列表和 Excel 必须来自同一批有效业务事实。

## 14. 当前开放项

以下问题已明确保存，尚未被默认为产品事实：

1. OMS 页面到现有小系统 API、只读投影、连接器与 Capability 的精确映射和缺口；
2. 经营总览各图的最终视觉形式、项目图展示数量和排序；
3. Excel 各模块最终列集合，以及触发“大数据量、导出可能较慢”提示的性能阈值；
4. 附件允许的类型、大小、数量以及预览降级方式；
5. 备注和其他长文本的最大长度；
6. 两档业务能力如何映射到既有 IAM 账号、Grant 与原生 Capability；
7. 桌面、笔记本和手机的最终交互验收结果。

上述开放项不改变已确认产品范围。实现前必须形成小系统能力映射与缺口矩阵；任何需要改变应用事实所有权、跨库写入、共享业务表或大规模重解释既有 Contract／Money 语义的方案，都必须标记为“大边界改动”并停止隐式实施。

## 15. 页面验收清单

1. 未登录访问 `/oms-v1/` 必须进入现有 IAM 登录，不出现预览身份或匿名管理员；
2. 登录后默认进入经营总览，页面没有新增、编辑等业务按钮；
3. 桌面侧栏仅出现四个一级入口，手机使用四项底部导航；
4. 项目列表提供新建项目，项目详情使用完整页面，其他简单详情及新增／编辑使用统一居中业务弹窗；
5. 应收与应付列表只读，实际开票、收票、回款、支付分别可以新增和查看；
6. 所有金额以精确值计算，业务页面显示两位小数，图表缩写可下钻到精确值；
7. 超额事实允许强确认后保存并以红色提示，作废事实不再参与汇总；
8. 列表具备紧凑筛选、分页、长文本省略和按筛选结果导出；
9. 笔记本首屏可看到主要图表或列表，手机不产生整页横向滚动；
10. 新入口、静态资源、受保护读取和写入都经过 Nginx、Gateway 与 IAM 契约。

## 16. 实施顺序与停止条件

1. 先完成小系统能力映射与缺口分级；
2. 再实现 `/oms-v1/` 路由、一期工作面和既有应用适配器；
3. 优先打通项目、主体、发票和实际资金的纵向闭环，再补图表、导出和附件；
4. 运行单元、集成、浏览器、响应式和公网入口验证；
5. 从开始执行本轮任务起最多连续工作八小时，到时无论完成度如何都停止变更，保存可复验状态并等待用户检查；
6. 若能力映射判定必须大幅修改小系统边界，立即写入边界变更记录，不以页面便利为由直接实施。
