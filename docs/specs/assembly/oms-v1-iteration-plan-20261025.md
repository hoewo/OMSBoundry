# OMS1 版本迭代计划（2026-10-25）

状态：需求已确认，实施已启动；BF-184～BF-237 是本轮当前产品基线，本文件是产品与开发入口。

工程分期、依赖和验收门见 [`oms-v1-iteration-implementation-plan-20261025.md`](./oms-v1-iteration-implementation-plan-20261025.md)。BF-237 已关闭最后产品待确认项，后续状态以各阶段实际代码、测试和运行证据为准，不能因文档完成就宣称功能完成。

问题 A → 可验证结果 B：会议结论只有五条短标题，容易在实现时被误解或遗漏 → 把每一项逐条澄清为可验证范围、边界、依赖、延期项和验收证据，再按确认后的顺序实施。

## 1. 迭代主线

1. 账号＋租户系统；
2. 公司内部管理接入正式小系统；
3. SDK／API 开放平台＋AI；
4. 走通闭环；
5. 反馈 V2 接入。

上述顺序来自 2026-10-25 会议摘要。每一项在需求澄清完成前只代表工作主线，不代表功能范围、系统 Owner 或验收已经全部确定。

## 2. 已确认：账号＋租户系统

### 2.1 产品定义

- 一个租户对应一个组织／公司。
- 多个组织／公司共同使用同一域名、同一套 OMS1 服务和同一服务器部署。
- 隔离方式是逻辑数据隔离，不要求每个租户拥有独立服务器或独立数据库。
- 第一版登录用户只需登录使用，不需要理解、选择或切换“当前组织”。租户上下文由账号、会话和可信身份确定，不能由浏览器请求参数或自报 Header 决定。

### 2.2 第一版必须具备

- 运维／平台后台创建租户并建立该租户的首个管理员账号；
- 企业管理员邀请或建立成员账号、停用成员账号并分配角色／能力；
- 登录、会话、Capability Credential、审计以及所有业务 Owner 的读写都必须携带可信 Tenant ID；
- 同一套 OMS1 服务中的不同租户数据必须互不可见、不可写、不可导出，也不能通过稳定 ID、搜索、分页、附件或错误信息侧漏；
- 租户隔离必须覆盖 Party、Project、Contract、Billing、Money、Evidence，以及本轮后续接入的 People、Payroll、内部财务申请和反馈数据，不能只在 Workbench 或 IAM 页面层过滤；
- 现有单租户数据需要以显式迁移或绑定方式进入一个明确租户，不通过名称猜测，也不静默改变既有 ID、revision、审计和业务引用。

### 2.3 延后项

- 同一个自然人账号加入多个租户；
- 登录后切换组织／租户；
- 多租户成员身份合并、跨租户邀请接受和切换后的会话／授权刷新。

这些能力延后不代表可以把 Tenant ID 写死在页面或业务服务中。第一版契约和数据模型仍须允许后续兼容扩展，不能以跨租户共享账号或客户端切换参数破坏隔离。

### 2.4 当前基础与缺口

- 现有 IAM 已拥有 Tenant、Subject、邀请／激活、会话、Grant 和短期 Capability Credential 等基础能力；业务 Owner 也普遍保存并校验 Tenant ID。
- 当前运行与配置仍需专项审计，确认它是否只是“表结构带 Tenant ID，但一个进程固定一个 Tenant”，不能仅凭字段存在宣称已经支持同域名多租户。
- 本项需要形成同一域名、同一服务进程下至少两个租户的真实正反例矩阵，并覆盖登录、邀请、角色、Owner 读写、搜索分页、导出、附件访问、停用、撤权和恢复。

### 2.5 第一版验收方向

1. 平台后台创建租户 A、租户 B 及各自管理员；
2. 两个管理员分别邀请成员并分配不同角色；
3. 两个租户在同一域名登录并完成各自 OMS1 最小读写；
4. 使用租户 A 的会话、Capability、资源 ID、导出和附件访问尝试读取或修改租户 B，结果全部拒绝且 B 数据无变化；
5. 停用账号或撤销角色后不能获得新会话／新能力，既有短期凭证遵守已接受的有界失效规则；
6. 备份与恢复后 Tenant ID、账号、Grant、Owner ID、revision、引用和审计保持一致。

## 3. 已确认：公司内部管理、开放 API、闭环与 Feedback

### 3.1 已确认：公司内部管理的财务申请边界

报销和付款申请需要独立的 `Internal Finance Requests` 业务小系统，不能写入 Workbench、People & Groups 或 Money Flow。它拥有：

- 报销／付款申请类型、草稿、申请人、操作人、申请金额、用途、收款信息快照和业务日期；
- Evidence File ID／Version 及其在申请中的业务含义，但不拥有文件字节；
- revision、提交、撤回、审批占位、拒绝／通过结果、历史和幂等命令；
- 向 Money 提交应付建议的投递状态，以及 Money 返回的稳定建议／义务／实际付款引用；
- 申请当前是否等待审批、无需审批、待支付或已支付的来源状态。

它不拥有实际资金、核销、账户余额、人员主档、主体当前档案、项目或合同。People & Groups、Party Directory、Project、Contract 和 Evidence 只在确有业务需要时通过版本化引用提供精确快照；Money Flow 仍独占已确认义务和实际付款。

#### 审批占位

- 审批环节必须进入第一版状态机、API、页面和历史结构，不能以后再靠改写旧记录补入；
- 报销和付款申请分别拥有审批策略，同一租户可以分别设置，不能用一个总开关强迫两类申请采用相同流程；
- 本版本两类申请均默认“不需要审批”，当前交付也按无需审批运行；
- “不需要审批”必须保存为明确的配置／策略快照和历史结果，不能伪造审批人、审批意见或“自动批准”；
- 无需审批的申请提交后进入待支付；未来启用审批时才经过待审批 → 已批准／已拒绝，再由已批准进入待支付；
- 审批策略变更只影响变更后提交的申请；每笔申请冻结提交时的策略快照，旧申请不能因租户配置变化被重新解释；
- 正式版本预计以需要审批作为常规流程，但具体审批层级、审批人规则、转交和加签仍需后续确认，第一版不得提前猜测；
- 当前不建立通用审批平台。真实审批启用前先由 `Internal Finance Requests` 拥有本域审批状态；出现两个以上稳定复用流程后，再评估独立审批协同系统。

#### 申请金额修订

- 草稿保存后仍可编辑申请金额，每次正式保存追加申请 revision，不原地覆盖已保存版本；
- 申请提交后、尚未发生任何实际付款时，用户可以显式撤回，追加新 revision 后重新提交；页面必须保留撤回原因、修改前后金额、操作人和时间；
- 当前 `not_required` 策略下重新提交直接回到待支付；未来启用审批后，金额或其他受审批字段的变化使旧审批结果失效，新 revision 必须重新进入审批，不能沿用旧批准；
- 一旦任一 Payment Delivery 成功并在 Money 形成实际资金／分配引用，原申请金额永久冻结，不能再撤回或改写；
- 付款后出现新增或减少差额时，使用引用原申请 ID／revision 的新申请或类型化调整申请处理，保留原因和关系，不改变原申请、付款或 Money 事实。

#### 报销收款人边界

- 报销申请的收款人默认是申请人本人，申请人和收款人是两个明确字段，不能因默认相同而只保存一个；
- 允许改选本租户内其他内部成员代收，但必须通过稳定 Person ID 选择并填写代收原因，提交时冻结申请人、收款人及其来源 revision；
- 外部单位或外部个人不能作为报销收款人，相关支出统一使用“付款申请”，避免报销和对外付款两种单据边界混乱；
- 操作人、申请人和收款人可以是不同主体，页面、权限、历史和导出必须分别展示，不能用当前登录人覆盖业务事实；
- 成员后续更名、停用或离职不能改写已提交报销的收款人快照，也不能单独决定已经成立申请是否允许付款。

#### 付款申请收款方与账户快照

- 付款申请优先从 Party Directory 选择已有外部单位或个人，并保存稳定 Party ID／revision；
- 允许为偶发付款手工录入一次性收款方，但该快照只属于本次付款申请，不能自动创建、合并或修改 Party Directory 主体；
- 无论来自主体库还是手工录入，提交时都必须冻结收款名称、开户行和账号快照，并明确记录来源类型；不能在付款时临时读取当前资料替换已提交内容；
- Party Directory 后续更名、账户变更或停用不回写旧申请；申请未付款时如需更换账户，按 BF-192 撤回、追加 revision 并重新提交，不能直接覆盖；
- 一次性收款方与主体库可能重复时页面可以提醒用户优先复用已有主体，但不得静默匹配或自动归并；
- 付款申请只拥有业务发生时的收款快照和引用，不因此取得 Party Directory 当前档案的所有权。

#### 收款账户敏感信息

- 银行账号属于租户内敏感业务信息；列表、搜索结果、批量选择、普通详情和普通导出默认只显示后四位，不能返回完整账号后再依赖前端遮挡；
- 只有获得版本化“付款敏感信息查看”能力的财务人员，才能在申请详情中通过显式动作查看完整账号；普通申请人即使是本人，也只查看脱敏账号；
- 完整账号导出使用独立的敏感导出能力，不能因为拥有普通列表导出权限而自动获得；
- 每次完整查看和敏感导出都记录 Tenant、Actor、申请、用途、时间和结果审计，导出文件本身必须显式标记敏感内容；
- 完整账号不得进入列表缓存、搜索索引、URL、普通日志、错误信息、分析埋点或前端持久化状态；
- Workbench 不能通过隐藏按钮替代授权，Internal Finance Requests 必须校验目标应用原生 Capability Credential 和租户边界后才返回完整值。

#### 申请附件要求

- 报销和付款申请在草稿阶段都可以暂不上传附件，草稿保存不能因缺少附件失败；
- 报销正式提交时至少需要一份已经由 Evidence Service 完成保存并返回稳定 File ID／Version 的票据或费用凭证；上传中、失败或只有本地文件名不算有效凭证；
- 付款申请第一版允许无附件提交，但页面必须强提示“尚未提供付款依据”，由用户显式确认后继续，并在提交快照中记录缺少附件的事实；
- 两类申请都支持添加多份附件并声明业务含义；Internal Finance Requests 只保存 File ID／Version 和含义，不保存文件字节、对象地址或长期访问链接；
- 提交时冻结当时适用的附件要求和附件引用，不能因租户后续配置变化重解释旧申请；
- 后续可以按申请类型配置附件是否必填，但第一版不得用一个全局开关改变已经确认的默认规则。

#### 报销费用明细与总额

- 一张报销申请允许录入一条或多条费用明细，正式提交时至少存在一条有效明细；
- 每条明细分别记录稳定明细 ID、费用日期、费用类别、精确金额、说明和零到多个 Evidence File ID／Version 引用；
- 报销申请总额只能由当前 revision 中全部有效明细金额精确求和得出，页面不得提供可独立修改的总额输入框；
- 金额使用整数最小货币单位，新增、修改、删除明细后必须由 Owner 重新计算总额，不能信任浏览器自报汇总值；
- 提交后需要改动明细时遵守 BF-192 的撤回和 revision 规则；已发生付款后不能改写原明细或总额，只能通过引用原申请的新申请／调整申请处理；
- 附件可以关联具体费用明细，也可以作为整张申请的补充材料，二者的业务含义必须明确保存。

#### 费用类别字典

- 第一版由平台提供一组可直接使用的基础费用类别，租户管理员可以在本租户新增类别或停用不再使用的类别；
- 费用类别字典属于 Internal Finance Requests 的本域配置，不为尚未出现的复用场景建立通用字典小系统；
- 平台预置类别保留稳定 key 和平台来源，租户可以在本租户停用，但不能反向修改平台定义；租户新增类别具有租户内稳定 ID；
- 类别改名必须追加新 revision，只影响之后选择和提交的明细；已提交费用明细冻结类别 ID／key、名称和 revision，不随当前字典变化；
- 已被草稿或历史申请引用的类别不能物理删除或覆盖；停用只阻止新选择，历史查询、详情和导出仍须显示原快照；
- 类别配置和停用需要租户管理员能力并记录 Actor、时间、原因和 revision，不能由任意申请人临时创建全租户类别。

#### 付款申请用途明细与收款方

- 一张付款申请允许录入一条或多条付款用途明细，正式提交时至少存在一条有效明细；
- 每条用途明细分别保存稳定明细 ID、精确金额、用途说明和零到多个 Evidence File ID／Version 引用；
- 付款申请总额只能由当前 revision 中全部有效用途明细金额精确求和，页面不得另设可独立编辑的总额；
- 整张付款申请只能冻结一个收款方及一套收款账户快照，全部用途明细共同使用该收款方；
- 需要向不同收款方付款时必须拆分为不同付款申请，不能在同一申请中按明细保存多个收款方或由付款时临时改选；
- 提交后修改明细、总额或收款方继续遵守 BF-192；首笔付款后均不可改写，只能新增引用原申请的补充／调整申请。

#### 整单付款与核销粒度

- 第一版报销和付款申请的实际付款、累计已支付和剩余应付都按整张申请计算，不要求用户把每次付款分配到费用／用途明细；
- 费用明细和用途明细只表达申请金额的业务构成，不单独拥有待支付、部分支付或已支付状态；
- 每条 Payment Delivery 只分配到稳定 Application ID／revision，其成功 Allocation 累计值与申请总额比较后投影整单状态；
- 页面显示整单实付、已分配、未付和超额异常，不得根据录入顺序猜测某一明细已经支付；
- 如果未来出现按明细核销的真实需求，必须新增明确的版本化分配模型和迁移方案，不能用前端顺序分摊或静默重解释既有付款。

#### 费用归属引用

- 报销和付款申请都可以在整单层面保存可选的费用承担部门、项目和合同引用；第一版不要求每条费用／用途明细分别归属；
- 新建申请时默认带出申请人在 People & Groups 中的当前部门，用户可以改选本租户其他部门或清空；默认值只是录入便利，不能作为不可修改的业务规则；
- 项目和合同均为可选关联，必须从当前租户的版本化 Owner 投影选择，不能仅保存自由文本或跨租户资源 ID；
- 提交时冻结 Group／Project／Contract 的稳定 ID、revision 和显示快照，来源 Owner 后续变化不回写旧申请；
- 第一版费用归属只用于详情展示、列表筛选和导出，不据此生成统计、预算占用、会计分录、付款资格或审批路由；
- 未关联部门、项目或合同不阻止第一版提交；未来如需按租户或申请类型改为必填，必须增加版本化策略并只影响后续提交。

#### 申请查看与操作权限

- 普通成员只能创建、查看和在状态允许时修改／撤回自己的申请，不能读取同租户其他成员的草稿、申请、附件、收款信息或付款记录；
- 财务人员只有取得 Internal Finance Requests 的本租户全量读取能力后，才能查看本租户全部申请；确认付款、批量确认、敏感账号查看和敏感导出继续使用彼此独立的能力，不能由一个“财务角色”名称自动全部放开；
- 部门负责人第一版不因 People & Groups 中的岗位、Group 角色或费用承担部门关系自动看到部门成员申请；未来审批启用后按明确的审批与资源能力另行授权；
- 租户管理员负责租户成员和能力配置，但管理员身份本身不自动获得财务申请全量读取、付款确认或完整银行账号权限；
- Workbench 可以按能力隐藏入口，但 Internal Finance Requests Owner 必须对单条读取、列表、搜索、导出、附件引用和命令分别校验 Tenant、Actor、资源范围与当前状态；
- 被停用账号不能获得新能力；历史申请继续保存当时申请人、操作人及授权审计，不能因人员状态变化转为其他人的申请。

#### 实际付款确认

- 待支付不等于已支付，审批通过或无需审批都不能自动产生实际资金；
- 报销和付款申请都允许分多次实际付款；用户每次在外部真实完成付款后，必须在 OMS1 显式执行“确认付款”；
- 每次确认独立记录本次金额、实际付款日期、操作人、备注和 Evidence 付款凭证引用（如有），不能用申请上的一个布尔值代替付款明细；
- 每次正式确认通过版本化、幂等连接器向 Money Flow 登记独立 payment，并保存 Money 返回的稳定 ID／revision；只有稳定事实返回后，该次金额才能计入累计已支付；
- 累计已支付为 0 时申请显示“待支付”，大于 0 且小于申请应付金额时显示“部分支付”，与申请应付金额相等时显示“已支付”；剩余金额使用整数最小货币单位精确计算；
- Money 写入失败或结果未知时申请保持可续办状态，使用同一命令重试，不得重复登记资金；
- 单次付款可以单独失败或续办，不能回滚已经成功的其他付款；
- 当前不接银行代付，不以按钮点击、审批通过或应付建议被接受冒充实际付款。
- 当本次实际付款大于申请剩余应付额时，页面必须强提醒，要求用户二次确认并填写超额原因；不能静默截断金额，也不能把已经发生的真实付款拒绝在系统外；
- 确认超额后，Money 记录完整实际 payment，只将申请剩余应付额分配／核销到零，超出部分保留为该笔资金的未分配金额；
- Internal Finance Requests 分别保存实际付款金额、分配到本申请的金额和超额金额；申请显示“已支付＋超额异常”，剩余应付为 0，不允许出现负余额；
- 超额异常必须可筛选、可进入付款明细并显示原因及 Money 引用；它不能自动提高申请金额、生成新申请或获得会计分类。

#### 批量确认付款

- 批量确认只允许勾选“待支付”或“部分支付”的申请；已支付、已撤回、已拒绝以及尚未满足当前审批策略的申请不能进入本次批量；
- 打开批量确认时，每笔默认带出当前剩余应付额，用户可以逐笔修改本次实际付款金额和实际付款日期；默认值只是录入便利，不能替代用户确认；
- 提交前必须显示逐笔明细、本次付款总额以及超额、缺少必要信息、状态或 revision 已变化等异常；超额项仍逐笔遵守 BF-191 的强提醒、二次确认和原因要求；
- 一次批量提交是多个独立 Payment Delivery 命令的编排，不生成一个不可拆分的总付款事实；每笔使用自己的幂等键、expected revision 和 Money 引用；
- 部分成功时保留所有已成功付款及其稳定引用，失败或结果未知项单独显示原因并保持可续办；重试只能重放失败／未知项的原幂等命令，不能回滚成功项或重复登记资金；
- 批量结果必须明确展示成功、失败、结果未知和未执行数量及逐笔状态，申请列表只按已取得的稳定 Money 事实刷新。

成员管理接入 People & Groups、薪酬正式 Owner 的后续边界已经在 3.2～3.6 及 BF-204～BF-215 中逐项确认；本段不再保留独立待确认项。

### 3.2 已确认：工资审批与发放基线

- 正式工资事实由独立 Payroll 小系统拥有，不能继续保存在 Workbench 浏览器状态，也不能写入 People & Groups 或 Money 数据库；
- 工资表／工资批次必须保留审批环节及其状态、API、页面位置和历史，第一版默认且当前实际采用“无需审批”；
- “无需审批”是明确的版本化策略结果，不能伪造审批人、审批意见或自动批准记录；未来正式版本可以把审批设为常规路径，但不得重解释已经生成的工资表；
- 计划发薪日只表示计划日期，到期不能自动把工资改成“已发放”；
- 只有外部实际完成发薪后，用户才能在 OMS1 中人工确认“已发放”；确认人、确认时间和对应工资 revision 必须留痕；
- 审批通过或无需审批均不等于实际发薪，Payroll 在 Money 返回稳定的实际资金事实之前不得投影为已发放；写入结果未知时沿同一幂等命令续办，不能重复登记资金；
- 发放确认同时支持按成员逐条确认和勾选多个成员批量确认；批量确认只是对多条成员工资行的编排，不生成一个无法拆分的总付款事实；
- 只有部分成员确认成功时，工资表显示“部分发放”；全部应发成员均确认成功后才显示“已发放”；
- 批量处理中部分 Money 写入失败或结果未知时，保留已经成功的成员付款及稳定引用，只使用各成员原幂等命令续办失败／未知项，不能回滚成功项或重复登记。

#### 工资数据查看与操作权限

- 普通成员只能查看与本人稳定 Person ID 对应、且该成员工资行已经完成实际发放确认的工资单；不能查看草稿、待确认、付款失败／未知或其他成员工资；
- 成员本人可见时点按自己的工资行判断，不要求整张工资表全部发放；批量部分成功时，已成功成员可以查看本人单据，未成功成员仍不可见；
- 工资经办人的全量读取、编辑未发放工资、逐条确认发放、批量确认发放和导出分别使用 Payroll 原生版本化能力，不能用一个页面角色名全部放开；
- 部门负责人不因 People & Groups 岗位或 Group 角色自动查看下属工资，租户管理员也不因管理员身份自动拥有工资读取、编辑、发放或导出能力；
- Payroll Owner 必须根据可信 Actor 映射的 Person ID、Tenant、工资行资源和当前状态执行授权，不能接受浏览器自报“本人”或只依赖 Workbench 隐藏入口；
- 工资相关读取、导出、修改和发放确认必须保留 Actor、时间、目标工资 revision 和结果审计，停用账号不能获得新能力。

#### 成员工资单金额构成

- 成员本人可见的已发放工资单必须清楚列出固定工资、当月绩效、全部正／负调整、应发合计、个人承担的五险一金逐项及合计、个税、实发金额和实际发放日期；
- 应发合计由 Payroll 使用当前工资 revision 中的固定工资、绩效和调整精确计算，实发金额按“应发合计－个人五险一金－个税”计算，不能信任前端自报合计；
- 单位承担的五险一金逐项及合计单独显示为“企业承担”，用于说明企业用工成本，但不从成员工资扣除，也不参与实发金额；
- 工资单中的缴费方案来源／revision、基数、适用比例和舍入结果必须可追溯，页面不能只显示一个无法解释的扣款合计；
- 正负调整逐条显示类型、金额和原因，不能合并成无法追踪的“其他”；
- 成员看到的是实际发放所依据的不可变工资 revision；后续补发或扣回在新的工资行／调整记录中单独展示，不改写旧工资单。

#### 工资表生成、录入与核对

- 新建工资表时，Payroll 按用户确认的成员范围冻结适用的 Compensation Profile revision，自动带出固定工资、社保基数、公积金基数，并按适用 Contribution Scheme revision 计算个人／单位缴费；
- 新生成工资行的绩效和调整初始金额均为 0，但工资行状态必须是“待核对”，不能因为数值为 0 就视为已经确认；
- 工资经办人可以在统一表格中逐行录入绩效和类型化正／负调整，每条调整必须有类型与原因；
- 第一版同时支持按稳定 Person ID 或租户唯一成员编号进行模板批量导入；导入前必须展示成员匹配、原值、新值、金额差异、错误行和未匹配行，用户确认后才提交；
- 导入与逐行保存都使用 expected revision 和幂等命令，预览过期必须重新生成，失败或未匹配行不能静默套用到其他成员；
- 只有经办人显式完成工资行／工资表核对后，当前默认无需审批的工资才能进入待发放；核对后再次编辑会追加新 revision 并回到待核对，不能沿用旧确认。

#### 工资月份唯一性与调整批次

- 同一 Tenant、同一工资月份只能存在一张有效的“常规工资表”；草稿、待核对、待发放、部分发放和已发放都占用该唯一性；
- 重复新建常规工资表时，Payroll 不创建第二份数据，而是返回已有工资表的稳定 ID 和当前 revision，Workbench 提示并进入已有记录；
- 常规工资表内的成员增减、薪酬同步和发放前修订都在同一工资表上追加 revision，不能通过新建同月工资表绕过历史；
- 补发和扣回使用独立的类型化调整批次，同一月份允许存在多批，但每条调整必须引用原工资行 ID／revision、记录原因并明确正负方向；
- 调整批次不占用常规工资表唯一性，也不能伪装成第二张常规工资表；它拥有独立的核对、审批策略快照、发放确认和 Money 引用；
- 创建常规表和调整批次均使用幂等命令，重试不得产生重复 Period、Line、补发或扣回事实。

#### 工资表作废与替代

- 常规工资表在尚无任何成员实际发放成功、且没有结果未知的发放命令时允许作废；作废必须填写原因，并保存 Actor、时间、原工资表 ID／revision 和完整历史；
- 作废是追加状态而不是删除数据，作废工资表不再允许编辑、核对、审批或发放，但详情、历史和审计仍可读取；
- 作废后可以新建同一月份的替代常规工资表，新表必须引用被替代表 ID／revision 和作废原因，并重新生成、核对及冻结审批策略；
- 同一月份仍只能有一张有效常规工资表；替代表建立后，被作废表不能恢复为有效或与替代表同时发放；
- 一旦任一成员已有成功 Money payment，整张工资表永久禁止作废或替代；后续差额只能通过 BF-207 的补发／扣回调整批次处理；
- 发放结果未知时必须先沿原幂等命令查询或续办到确定状态，不能通过作废或新建替代表绕过未知资金事实。

#### 零实发与负实发

- 工资行实发金额等于 0 时，经办人必须显式执行“确认无需发放”；确认保存 Actor、时间和工资 revision，但不向 Money 创建零金额义务、付款或核销记录；
- 已确认无需发放的零实发工资行视为该成员当月工资处理完成，成员可以按 BF-204 查看对应工资单，页面明确标记“无需发放”而不是“已转账”；
- 工资行实发金额小于 0 时禁止进入实际发放，不得向 Money 创建负数付款，也不能把负值静默截断为 0；
- 负实发工资行转为“待处理扣回”，冻结负值构成、来源工资 revision 和原因，后续只能通过引用原工资行的扣回调整处理；
- 存在待处理扣回时，工资表必须单独显示该数量和金额，不能把相关成员计入已发放或无需发放；
- 零实发确认和负实发转待扣回都使用 expected revision 与幂等命令，重试不得重复完成或生成重复调整。

#### 单成员工资分次发放

- 同一成员的一条正数工资行允许对应一笔或多笔实际发放，每次独立保存本次金额、实际日期、操作人、备注和 Money 稳定 payment／allocation 引用；
- 只有 Money 成功返回的分配金额才进入累计已发放；累计为 0 时是待发放，大于 0 且小于工资行实发金额时是部分发放，相等时才是已发放；
- 工资行剩余应发由实发金额减去成功累计分配额，使用整数最小货币单位计算，不能用前端显示值或按钮状态代替；
- 批量发放默认逐成员带出当前剩余金额和默认实际日期，但允许逐笔修改；提交后仍拆成独立、幂等的成员 Payment Delivery；
- 某次发放失败或结果未知时保留此前成功资金和引用，只沿该次原幂等命令查询／续办，不能回滚或重复其他成功付款；
- 工资表状态根据各成员工资行投影；存在任一部分发放或部分成员已发放时显示部分发放，全部正数行已付清且零实发行已确认无需发放后才可显示已发放，待处理扣回另行提示。

#### 工资超额发放

- 本次实际发放金额大于成员工资行剩余应发时，页面必须强提醒，要求经办人逐笔二次确认并填写超额原因；批量发放中的超额项不能用一次总确认替代；
- 经确认后，Money 记录完整实际 payment，只将工资行剩余应发额分配到该 Line，超出部分保留为同一资金事实的未分配金额；系统不能截断已经发生的实付；
- Payroll 分别保存本次实付、分配到工资行和超额金额及 Money 引用，工资行显示“已发放＋超额异常”，剩余应发固定为 0，不允许出现负值；
- 超额不能自动提高实发工资、修改原工资 revision、生成绩效／奖金或视为已经完成扣回；
- 后续处理超额只能创建引用原工资行、超额 Payment Delivery 和 Money 引用的扣回调整，并独立记录实际追回事实；
- 超额异常必须可筛选、进入明细、导出并显示原因和处理状态，在扣回完成前不能从异常列表静默消失。

#### 成员工资收款账户

- 成员工资收款账户属于 Payroll 的版本化“薪酬支付档案”，通过同租户稳定 Person ID 关联／挂载，不进入 People & Groups 基础成员档案；
- 薪酬支付档案明确保存账户名、开户行、账号、启用状态、生效时间和 revision；这里的挂载不是共享表、跨库外键或由 People 代写 Payroll；
- 账号在普通成员视图、列表和普通导出中仅显示后四位；完整查看与完整导出使用两个独立 Payroll 能力，并逐次记录 Tenant、Actor、成员、用途、时间和结果审计；
- 新建工资表时冻结该成员当时适用的支付档案 ID／revision、账户名、开户行和账号快照；实际发放必须引用工资行冻结的快照，不能临时读取当前账户替换；
- 支付档案后续变更只形成新 revision，不回写已生成工资表、已确认工资行或既有 Money 事实；
- 完整账号不得进入搜索索引、URL、普通日志、错误信息、分析埋点、列表缓存或前端持久化状态，Payroll Owner 必须在返回完整值前校验原生 Capability。

#### 工资账户维护权限

- 第一版只有获得 Payroll“薪酬支付档案维护”能力的工资经办人可以新增、变更、停用成员工资收款账户；成员本人只能查看自己的脱敏信息，不能直接修改；
- 每次账户变更必须选择生效月份、填写原因并二次确认，Payroll 追加新 Payment Profile revision，不能覆盖旧值；
- 生效月份表示该 revision 可供之后生成的对应月份工资表选择，不能使已生成工资表自动换卡或重写既有快照；
- 账户维护能力不自动包含完整账号批量导出或全部工资读取能力；编辑页面需要的完整值由 Owner 通过精确资源能力返回；
- 账户变更审计记录 Tenant、Actor、成员 Person ID、前后 revision、脱敏差异、生效月份、原因、时间和结果，普通审计日志不复制完整账号；
- 后续如增加成员自助改卡，必须另建提交、验证和经办确认流程，不能直接放开当前 Owner 更新命令。

#### 已生成工资行同步账户

- 已生成工资表不会自动使用新的 Payment Profile revision；经办人只能对目标成员工资行显式执行“同步收款账户”；
- 只有该成员工资行不存在成功或结果未知的 Payment Delivery 时才允许同步；确认失败且已查明未产生资金的记录不阻止同步，但必须保留失败历史；
- 同步前必须预览旧／新账户的脱敏差异、Payment Profile revision、生效月份和受影响工资行，用户二次确认后以 expected revision 和幂等命令提交；
- 同步只追加目标工资行及工资表 revision，并把该行退回“待核对”；其他成员已经发放不阻止该成员同步，也不回滚或改写其他工资行；
- 目标成员一旦已有部分或全部成功发放，或存在结果未知命令，就禁止同步账户快照；剩余款不得通过静默换卡继续发放；
- 同步、拒绝和重试均记录 Actor、时间、前后 Payment Profile revision、目标 Line revision 和结果，普通历史只显示脱敏账户差异。

#### 缺少工资账户

- 成员在适用工资月份没有有效 Payment Profile 时，仍允许生成和核对工资行；Payroll 在工资行冻结明确的“缺少收款账户”状态，不能伪造空账号或借用其他成员账户；
- 正数实发工资行缺少有效账户快照时，必须禁止逐条和批量确认发放，直到经办人建立有效支付档案并按 BF-214 手动同步该工资行；
- 手动同步成功后工资行回到待核对，必须重新确认后才能发放，不能因补齐账户自动沿用旧核对结果；
- 批量发放预览必须列出缺少账户的成员并标记不可执行；这些行不应阻断其他满足条件成员的独立付款，但不能被静默跳过而不显示结果；
- 零实发工资行仍可显式确认无需发放，负实发工资行仍进入待处理扣回，两者都不因缺少收款账户改变 BF-209 状态规则；
- 缺少账户数量和成员必须可筛选、查看和导出，补齐前持续显示，不能因工资表整体进入部分发放而消失。

### 3.3 已确认：成员与薪酬字段归属

- 姓名、部门、岗位、在职状态、入职日期等成员基础信息由 People & Groups 拥有；
- 成员档案与薪酬档案在小系统和数据所有权层面分开；固定工资、社保缴费基数和公积金缴费基数属于 Payroll 的成员薪酬档案，使用稳定 Person ID 关联／“挂载”到 People 成员，不进入 People & Groups 核心；
- 这里的“挂载”只表示 Payroll 保存对稳定 Person ID 的版本化关联，不表示跨库外键、共享表或由 People 代写 Payroll 数据；
- 固定工资和两个缴费基数当前作为同一份版本化 Compensation Profile 的明确字段，不拆成三个小系统，也不实现无类型的通用属性包／EAV；这些字段需要独立权限、精确金额、生效范围、revision 和审计，不能降级为任意键值；
- Workbench 的“成员档案”页面可以组合展示和编辑上述两类信息，但必须分别调用对应 Owner，不能把组合页面变成事实所有者或跨库写入；
- 绩效是月度工资事实，只在对应工资期间／成员工资行中录入，不保存为成员固定档案；
- 生成工资表时冻结当期使用的固定工资、两个缴费基数、比例方案 revision 和计算结果；薪酬档案后续变化不能静默重算历史工资；
- 每次修改固定工资、社保缴费基数或公积金缴费基数都必须明确选择生效月份，并在 Payroll 追加新的 Compensation Profile revision，不原地覆盖旧档案；
- 新 revision 只用于其生效月份及以后尚未生成的工资表；所有已经生成的工资表继续使用各自冻结的旧档案快照，不自动同步或重算；
- 对已经生成但尚未发生任何实际发放的工资表，用户可以显式执行“同步薪酬档案”；系统必须先展示固定工资、缴费基数、个人扣款、单位缴费和应发／实发金额的变更前后差额，再由用户确认；
- 同步成功后追加新的工资表／工资行 revision，保留原快照、同步操作人、时间、来源 Compensation Profile revision 和差额历史，不原地覆盖旧行；绩效等月度人工录入值不得被薪酬档案同步清空；
- 同步命令必须消费工资表 expected revision 并支持幂等重放；预览后工资表或薪酬档案发生变化时必须拒绝旧预览确认，要求重新预览；
- 工资表一旦有任一成员发生实际发放，整张工资表进入不可同步状态；部分发放和全部发放都不能再采用新薪酬档案重算或修改既有工资行；
- 发放后发现的差额只能在后续工资表中追加“补发”或“扣回”调整项，并冻结被调整的原工资期间、成员工资行 ID／revision、原因、精确金额和操作人；
- 调整项不能改写、冲销或删除原 Payroll 发放确认和 Money payment，只在后续期间形成新的计算及资金事实；
- 固定工资、基数、绩效和计算结果均使用整数最小货币单位；比例使用整数基点或更明确的整数精度，禁止二进制浮点数；

### 3.4 已确认：五险一金比例方案

- 五险一金计算方案属于 Payroll 的版本化计算策略，不新增独立小系统，也不能把比例硬编码在 Workbench；
- 平台标准方案按适用地区和生效月份维护不可变 revision，明确养老、医疗、失业、工伤、生育和公积金的个人／单位比例、缴费基数上下限及各项舍入规则；不能假设全国始终使用一套比例；
- 租户选择适用的标准方案，成员只需维护自己的社保缴费基数和公积金缴费基数，Payroll 根据工资期间适用的方案 revision 自动计算；
- 平台标准方案对租户只读。企业存在特殊规则时，租户管理员可以从某个标准 revision 复制为租户自定义方案，保存来源 revision、修改项、原因、生效月份和操作历史，不能直接修改标准方案；
- 工资表生成时冻结所用方案 ID／revision、来源类型、各项比例、上下限、舍入规则和计算明细；标准方案或租户方案后续更新不得重算历史工资；
- 工资行同时计算并展示每一项个人承担额、个人承担合计、每一项单位承担额和单位承担合计，不能只保存一个合并后的“五险一金”数字；
- 个人承担合计从成员当期应发金额中扣除；单位承担合计不减少成员工资，只计入企业用工成本；
- `固定工资＋绩效＋补发－扣回－个人五险一金` 标为“税前应付”；按 3.5 扣除外部录入／导入个税后才得到第一版最终实发金额。企业用工成本当前投影为当期应发金额加单位承担合计；
- 标准方案必须保留权威规则来源和核对时间；未经实际核对的演示默认值不得标为“国家规定”或用于正式工资；
- 所有比例和计算使用整数精度与显式舍入，金额结果保存为整数最小货币单位，禁止二进制浮点数。

### 3.5 已确认：个人所得税第一版边界

- 第一版 Payroll 保留每个成员工资行的“个人所得税”字段，支持人工逐条录入和批量导入；
- 个税在第一版是外部计算结果的输入快照，Payroll 保存精确金额、来源方式、来源说明／文件引用、操作人、录入时间和工资 revision，不负责推导该金额；
- 批量导入必须按稳定 Person ID 或租户内唯一成员编号匹配，不能仅按姓名猜测；提交前预览匹配、重复、缺失和金额变化，确认后使用幂等命令追加工资 revision；
- 工资表发生任何实际发放前可以更正个税输入并保留历史；部分或全部发放后不能改写原工资行，只能走后续补发／扣回调整；
- 第一版最终实发金额按 `固定工资＋绩效＋补发－扣回－个人五险一金－人工／导入个税` 精确计算；单位五险一金不参与成员实发扣减；
- 累计预扣法、起征点、税率表、专项附加扣除、其他税前／税后扣除、年度汇算、申报与缴税均不在第一版自动计算范围；页面必须明确“个税由外部计算后录入／导入”，不能宣称系统已经完成税务合规；
- 后续自动计税必须作为版本化 Payroll 税务策略另行设计、核对和验收，不能用前端公式替换本轮外部输入。

### 3.6 已确认：成员离职／停用生命周期

- 成员离职或停用由 People & Groups 追加状态 revision 和明确生效日期，不物理删除 Person、Membership、历史快照或引用；
- 离职／停用只是 People 成员状态，不与 Payroll 工资资格、工资表包含关系或实际发放建立自动因果；系统不得仅因当前状态为离职而阻止生成工资、补发、扣回或确认实际付款；
- Payroll 和 Workbench 可以在工资行展示当前“离职／停用”状态并用于筛选或提醒，但状态变化不自动新增、移除、归零、隐藏或重算工资行；
- 工资表是否包含该成员、当期应发多少，由该工资期间的显式录入／同步和工资 revision 决定，不能由 People 状态代替工资判断；
- 离职／停用成员的历史工资、审批、发放确认、Money 引用、补发／扣回和审计仍可按权限查询；
- People 成员状态与 IAM 账号状态是两个事实：离职不能直接删除账号或历史身份。是否由策略提出停用账号任务、由谁确认停用，后续在账号／租户管理流程中继续确认；
- 第一版不根据月中入职／离职日期自动按天折算工资，也不引入考勤、计薪日或请假规则；
- 工资经办人在当月成员工资行中录入明确的正／负“月中入离职调整”，保存精确金额、原因、操作人、时间和工资 revision；该调整参与应发金额计算；
- 发生任何实际发放前，调整的新增／更正只能追加工资 revision 并保留原值；发放后差额统一在后续工资表中走补发／扣回，不能修改原工资行或 Money payment；
- 页面必须说明调整由人工确认，不能把它描述为系统已按考勤或法规自动算出；自动折算待考勤和计薪规则形成独立、可验证边界后再设计；
- 成员重新入职时沿用原稳定 Person ID；People & Groups 追加新的任职／成员关系周期和 active revision，不新建同一自然人的重复成员；
- Payroll 为重新入职追加新的 Compensation Profile revision 和生效月份，不自动沿用或覆盖离职前薪酬；页面可以提供复制旧档案作为录入便利，但必须由用户确认后形成新 revision；
- 重新入职后的工资使用新的 People 与 Compensation Profile revision；离职前工资、调整、发放、Money 引用和审计继续保留在同一 Person 历史链中；
- 重新入职不自动恢复 IAM 账号，账号重新启用／邀请必须由有权限的企业管理员在 IAM 中单独确认；
- 新建工资表时默认勾选当前在职成员；离职／停用成员仍可搜索、筛选和手动加入，并在候选与工资行中显示清晰状态提醒；
- 默认勾选只属于 Workbench 操作便利，不是 Payroll 资格规则。用户确认名单后，Payroll 冻结所选 Person ID、People revision 与显示快照；未被默认勾选不表示该成员不能获得工资。

### 3.7 已确认：发票报销 SDK／API 开放入口

- 本轮不建设 AI 模型、对话、Agent、Skill、CLI 或自动识别产品；AI、CLI、Agent Skill 和其他工具只是外部 API 调用方，是否使用 AI 由调用工具自行决定；
- OMS1 负责提供稳定、版本化的 API 契约、认证入口、错误语义和调用文档，使不同工具可以提交发票文件及报销表单并在系统中形成正式数据；
- Workbench 需要提供员工可使用的 API Key 申请／管理页面；申请人必须先拥有 OMS1 登录账号，并能通过可信账号关系解析到唯一 Tenant、Subject 和对应成员 Person；
- API Key 必须绑定申请员工账号和单一 Tenant，调用方不能在请求参数、Header 或表单中自报／切换 Tenant，也不能使用 Key 访问其他员工或其他租户数据；
- API Key 的可用操作不能超过该账号当前获得的 Owner 原生能力；是否可以建立、修改或提交报销，必须由 IAM／Policy Provider 签发的可信上下文和 Internal Finance Requests Owner 最终校验，不能只检查 Key 是否存在；
- 当前闭环只开放“发票报销”一个业务范围：取得上传能力、经 Evidence Service 提交并完成发票文件、建立本人报销草稿、填写费用明细与附件引用、正式提交，以及查询本人此次提交结果；
- 本轮不通过开放 API 提供付款申请、工资、人事、项目、合同、收付款确认、审批操作或任意 Owner 通用读写；后续每增加一种业务都单独确认范围、能力、契约和验收；
- 接口文档必须覆盖认证、租户／账号绑定、请求模型、文件上传、幂等键、revision、提交状态、错误恢复、限流和示例；外部 Skill／CLI 的开发、运行和提示词不属于 OMS1 交付；
- 发票文件仍归 Evidence Service 所有，Internal Finance Requests 只保存稳定 File ID／Version 与业务含义；开放入口不能绕过 Evidence 完成校验或把文件字节写进报销数据库。

#### API Key 创建与当前账号能力

- API Key 创建不再建立一套重复的业务审批流程；员工登录后只有持有版本化“发票报销 API 访问”能力时，才能在管理页面直接创建 Key；
- 没有该能力时页面明确显示无权创建，并由租户管理员通过 IAM／Policy 配置先授予能力；不能通过提交 Key 申请绕过现有授权；
- 创建 Key 只证明该非交互凭证归属于当前账号，不冻结永久权限；每次调用仍须检查账号启用状态、Tenant／Person 映射、Key 状态和账号当前的发票报销能力；
- 租户管理员停用账号、撤销发票报销 API 能力或撤销 Key 后，该 Key 不得继续获取新的调用授权；不能把创建时权限长期复制进 Key 后绕过撤权；
- Key 的权限上限是员工本人发票报销 API 范围，不因申请人、管理员或页面角色名扩大到他人数据、付款、审批或其他业务；
- Key 创建、使用拒绝、撤权和撤销都记录 Tenant、Subject、Person、Key 稳定标识、Actor、时间和结果，审计中不得记录完整密钥。

#### API Key 数量、展示与撤销

- 每名员工在单一租户内最多同时持有 5 个有效 API Key；每个 Key 必须填写便于识别的名称，用于区分 CLI、Agent Skill 或其他调用工具；
- 完整密钥只在创建成功时显示一次，页面离开后不能再次查看或恢复；服务端只保存安全校验所需的哈希／verifier，不保存可还原明文；
- Key 管理页仅展示稳定 Key ID／前缀、名称、创建时间、最后使用时间和状态，不把完整秘密返回浏览器；
- 每个 Key 可以独立撤销；撤销是不可逆终态，不能重新启用，需要替换时创建新 Key 并由用户主动撤销旧 Key；
- 创建第 6 个有效 Key 时明确拒绝并引导用户撤销不再使用的 Key，不能静默删除最旧 Key；
- 创建、复制确认、使用、最后使用时间更新和撤销的审计使用 Key ID／前缀，任何日志、错误、埋点或支持信息都不能记录完整密钥。

#### API Key 有效期与轮换

- API Key 创建时必须选择固定有效期，可选 30／90／180／365 天，默认 180 天；第一版不提供永久 Key；
- Key 到达创建时确定的过期时间后自动失效，不得继续换取调用授权；过期 Key 不再占用 5 个有效 Key 名额，但仍保留非秘密元数据和审计记录；
- 管理页必须展示到期时间，并在临近到期时提醒用户轮换；具体提醒阈值属于实现配置，不能改变凭证的实际过期时间；
- “续期”不是延长原 Key，也不能重新显示原 secret；用户必须创建新 Key、替换外部工具配置，再主动撤销旧 Key；
- 新旧 Key 可以在轮换窗口内短期并存，但仍共同受每员工每租户最多 5 个有效 Key 的限制，系统不能自动替换、撤销或删除旧 Key。

#### 开放 API 限流与认证异常

- 第一版普通开放 API 默认按单个有效 Key 每分钟 60 次、单个租户每分钟 600 次执行双层限流；请求必须同时满足两层额度，不能通过创建多个 Key 绕过租户上限；
- Evidence 发票上传会话、上传完成校验等重资源操作使用独立的并发限制，不与普通表单请求共用简单计数；具体并发值属于部署配置，并须通过压测后确定；
- 超过任一额度时返回稳定的 `429` 错误、明确的限流错误码和可重试时间，不创建或推进报销业务事实；调用方须按 `Retry-After` 等契约退避；
- 连续认证失败不能自动封禁员工账号或永久撤销 Key，避免外部攻击者用错误请求锁死合法员工；系统只可按来源 IP 等网络维度实施短期、可恢复的失败限速；
- 认证失败的阈值和限制时长由安全配置管理，错误响应不得泄露 Key 是否存在、所属员工、租户或具体失败原因；成功与拒绝都只用 Key ID／前缀记录审计，不记录 secret；
- 租户管理员仍可按 BF-217／BF-218 显式撤销 Key 或停用账号，但限流组件不能替代 IAM 授权、Key 状态和 Owner 最终授权。

#### 开放 API 幂等与重复提交

- 所有会创建、修改、完成或提交事实的开放 API 请求都必须携带调用方生成的 `Idempotency-Key`；只读请求不要求该 Header；
- 幂等作用域绑定 Tenant、员工 Subject 和版本化接口动作，不绑定某一个 API Key，因此同一员工在 Key 轮换后仍可使用原幂等键安全恢复同一请求；
- 相同作用域内，同一幂等键与相同规范化请求内容重复到达时返回首次已确定结果，不重复建立上传会话、附件引用、报销草稿／明细或正式提交；
- 同一幂等键携带不同请求内容时返回稳定 `409` 冲突，不得覆盖首次请求，也不得猜测调用方想修改原事实；
- 草稿类命令的幂等记录至少保留 7 天；正式提交命令的幂等标识随报销业务记录长期保留，不能因 Gateway 缓存清理失去防重能力；
- Gateway 可以执行快速重放，但最终防重必须由对应 Owner／Evidence 的版本化命令契约保证；超时或结果未知时调用方使用原幂等键查询／重试，不生成新键规避未知状态。

#### 发票重复识别与重提

- 发票重复识别在同一 Tenant 内执行，不跨租户暴露或比较业务数据；网页版和开放 API 必须使用同一套 Owner 规则，不能只在某个客户端提示；
- 相同 Evidence 文件内容哈希，或表单提供的规范化“发票代码＋发票号码”与既有有效报销记录相同，均视为强重复；正式提交必须拒绝并返回可供当前员工按权限查看的既有报销单稳定引用；
- 强重复响应不能越权泄露其他员工报销内容；无权查看既有单据时只返回稳定重复错误和可交由财务核对的引用，不返回金额、附件或申请人信息；
- 仅“开票方＋开票日期＋含税金额”等组合相同而没有强标识命中时视为疑似重复，允许保存和提交，但必须显示警告、记录命中依据并进入人工核对；
- 已驳回或撤回的报销需要再次提交时，应在原单上追加 revision，或建立带原报销单引用和重提原因的新 revision 链；不能创建无关联的新记录绕过强重复校验；
- 文件哈希由 Evidence Service 提供稳定引用，Internal Finance Requests 保存用于业务判断的哈希／发票标识快照和匹配结果，不复制文件字节，也不把重复判断交给 AI／OCR 作为唯一事实来源。

#### 发票报销 API 提交后的状态与付款边界

- 首版报销主状态按“草稿 → 已提交 → 无需审批 → 待支付 → 部分支付／已支付”推进；“无需审批”是提交时冻结的审批策略结果，不表示已经发生付款；
- 员工通过网页或开放 API 正式提交后，申请金额、费用明细、发票／附件引用、收款信息和来源快照冻结，不能直接覆盖；
- 在没有任何成功付款或结果未知付款时，员工可以撤回原申请、追加 revision 后重新提交；撤回与重提必须保留历史和 BF-222 的关联，不能修改已经确认的 revision；
- 一旦存在成功付款或结果未知付款，申请人不能修改、撤回或重提该申请；后续差异只能通过追加付款、退款／冲销或独立调整业务表达；
- 实际付款只能由持有财务支付确认能力的人员在 OMS1 内确认，并通过 Money Flow Ledger 的版本化契约记录实际资金与核销；Internal Finance Requests 只保存 Money 稳定引用和自身投影状态，不自建资金事实；
- 发票报销开放 API 仅允许申请人查询本人申请的当前状态和受限结果，不开放审批、支付确认、资金写入或他人申请读取；
- 将来某类申请启用审批时，在“已提交”与“待支付”之间进入“待审批 → 已通过／已驳回”；当前按租户和申请类型配置的“无需审批”路径不需要改写既有历史记录。

#### 员工本人提交记录 API

- 发票报销开放 API 必须提供“我的提交记录”列表能力，员工可以通过自己的 API Key 查询当前 Tenant 内由本人账号／Person 提交的报销记录，而不是只能保存提交响应中的单个 ID；
- 列表的员工身份和 Tenant 只能从已验证 API Key 与当前账号映射派生，接口不得接受可切换的 `tenant_id`、`subject_id`、`person_id` 或“代他人查询”参数；
- 列表至少返回报销单稳定 ID、当前 revision、事项摘要、申请总额、提交时间、当前状态、审批状态、支付状态、重复核对标记和最后更新时间，并支持进入本人单笔详情；
- 草稿、已提交、撤回／驳回、待支付、部分支付和已支付记录都属于本人的提交历史，不能因终态、Key 撤销／轮换或页面清理而从列表中消失；
- 列表必须使用稳定分页和排序契约，不能一次无上限返回全部记录；
- 列表与详情都由 Internal Finance Requests 做 self-resource 最终授权；Gateway 或 Workbench 不能仅凭前端隐藏来隔离其他员工记录。

#### 本人提交查询契约与状态获取

- 正式提交成功响应必须立即返回报销单稳定 ID、当前 revision 和当前状态，调用方可以随后按 ID 读取本人单笔详情；
- 首版列表支持按状态和提交日期范围筛选，并支持 `updated_since` 增量取得在指定时间后发生变化的本人记录；
- 列表默认按最后更新时间倒序，相同更新时间再按稳定 ID 排序，以保证翻页期间顺序可复现；
- 列表使用不透明游标分页，默认每页 20 条、调用方最大可请求 100 条；不得使用任意大 offset 或无上限返回；
- 第一版不提供任意字段排序和模糊全文搜索；按稳定报销单 ID 的单笔查询与按规范化条件过滤分别使用明确参数；
- 列表和单笔详情返回审批状态、支付状态、重复核对标记、最后更新时间和当前允许操作，并支持 `ETag`／`If-None-Match` 条件读取，供 CLI／Skill 低成本轮询；
- 首版不建设 Webhook、消息推送或通用回调平台；开放平台设置页只预留“Webhook 通知（暂未开放）”入口，不允许录入／保存回调地址，也不建立订阅、投递或重试事实；后续需要主动通知时，必须另行确认订阅权限、签名、事件版本、重试、去重、停用和审计契约后再启用。

#### 开放 API 版本、文档与兼容性

- 首版员工发票报销 API 使用 `/open-api/v1/` 版本前缀，不能以无版本路径或页面内部接口作为对外稳定契约；
- 交付可下载的 OpenAPI 规范、中文使用说明和可直接修改运行的 `curl` 示例，覆盖认证、Evidence 上传、草稿／明细、提交、本人列表／详情、幂等、分页、限流和错误恢复；
- V1 内只允许不改变既有语义的兼容新增，例如新增可选字段或新端点；客户端必须忽略不认识的可选响应字段；
- 删除或重命名字段、改变字段／状态含义、收紧既有合法输入、改变幂等／分页／错误语义等破坏性变化必须发布新的主版本路径，不能静默覆盖 V1；
- 旧主版本停止支持前至少提前 180 天在开放平台页面和文档中公告弃用时间、迁移说明和替代版本；公告不等于可以提前中断既有版本；
- 文档示例不得包含真实租户、员工、发票、账号或有效 API Key，自动化契约测试必须验证规范与实际响应一致。

#### API 使用记录与审计可见性

- 开放平台必须提供 API 使用记录列表；员工可以查看自己名下各 Key 的调用记录，不能查看同租户其他员工记录；
- 持有独立“开放 API 使用审计”能力的租户管理员可以查看本 Tenant 的调用记录；租户管理员身份本身不隐式获得该能力，也不能跨租户读取；
- 单条记录只保存／展示 Tenant、Key 稳定 ID／前缀、员工 Subject／Person 引用、接口动作类别、调用时间、结果／错误码、请求 ID 和脱敏来源 IP；
- 使用记录不得保存或展示完整 secret、Authorization Header、请求／响应正文、发票字段、报销明细或 Evidence 文件内容；通用日志、trace 和导出同样执行凭证与业务内容清洗；
- 使用记录保留 180 天，到期按可审计清理策略删除；业务报销、Evidence 和 Money 的法定／业务保留期不随使用记录删除；
- 员工本人查看和租户审计查看使用不同能力并记录审计；首版提供筛选分页列表，不把该记录扩张成通用统计、计费或行为分析平台。

#### API Key 网络来源与生命周期入口

- 首版 API Key 调用不强制绑定固定 IP 或 IP 白名单，员工代理、移动网络或办公出口变化不能因此导致凭证失效；
- 所有开放 API、文档试调和 Evidence 上传授权都只允许经过正式 HTTPS 入口；明文 HTTP 请求不得携带或转发 Key，并应在读取认证信息前拒绝；
- 首版依靠 Key 状态、账号当前能力、Tenant／Person 绑定、请求限流、业务 Owner 授权和 BF-228 使用审计共同保护，不把网络地址当作员工身份；
- IP／CIDR allowlist 仅作为未来可选增强设置，默认关闭；启用前须单独确认配置权限、IPv4／IPv6、代理可信链、锁定恢复和审计规则，当前不得展示为可用功能；
- API Key 的创建与撤销只能在员工已登录的 Workbench 开放平台页面执行，并要求明确二次确认；开放 API 本身不提供 create-key、revoke-key 或批量生成 Key 的端点；
- 二次确认记录 Actor、Tenant、Key ID／前缀、操作和时间，但不得要求页面重新展示既有 secret，也不得把确认状态长期当作新的身份凭证。

#### 发票文件格式、容量与安全校验

- 发票报销首版允许上传 PDF、OFD、XML、JPG／JPEG 和 PNG；文件类型按 Evidence Service 的版本化 allowlist 管理，开放 API 与网页使用同一规则；
- 单个文件最大 20 MB，每张报销单最多关联 20 个文件，全部文件总计不得超过 100 MB；限制必须在创建上传会话、完成上传和正式提交时分别复验；
- Evidence 必须校验实际文件签名／结构、大小、内容哈希和安全扫描结果，不能只相信文件名扩展名或客户端声明的 MIME；
- 文件完成校验与安全扫描未结束、失败或结果未知时，不得形成可提交的稳定 Evidence Version，也不能正式提交报销；调用方沿原上传／幂等标识查询或恢复；
- 首版拒绝 ZIP／压缩包、Office 文档、脚本和可执行文件；XML 必须禁用外部实体和外部资源解析，图片／PDF／OFD 的预览或元数据提取不得执行嵌入内容；
- Internal Finance Requests 只保存通过校验的 File ID／Version、用途和提交时快照，不复制文件字节、安全扫描结果全文或 OSS 凭证。

#### 上传会话与未引用文件清理

- 浏览器／API 获得的单次上传授权有效 15 分钟，Evidence 上传会话最长保留 24 小时；授权过期不等于已完成文件或业务引用过期；
- 未完成、上传失败或安全校验不通过的临时对象，在会话过期后 24 小时内由 Evidence 有界清理；清理失败进入重试和运维可见状态，不能伪装成已删除；
- 已完成且从未被任何业务草稿／revision 引用的稳定 File Version 保留 7 天，超过期限后才允许清理；期限内调用方仍可使用原 File ID／Version 建立合法引用；
- File Version 一旦被报销草稿或任一业务 revision 引用，就不得由未引用文件清理任务自动物理删除；即使从当前表单移除，历史 revision 的引用仍然有效并服从业务保留策略；
- 清理命令必须幂等、记录 Tenant、File ID／Version、原因、尝试时间和结果，并在删除前由 Evidence 重新校验引用保护状态；发现引用存在或引用状态未知时必须失败关闭；
- Internal Finance Requests 只能通过 Evidence 版本化引用／保留契约表达挂载或解除当前引用，不直接调用 OSS 删除，也不因删除草稿而同步物理删除文件。

#### 报销草稿归档与删除

- 报销草稿属于 Internal Finance Requests 业务数据，不因退出登录、API Key 到期／撤销或更换调用工具而丢失；员工以新的有效凭证仍可读取本人草稿；
- 草稿连续 90 天没有业务修改时自动转为“已归档”，归档不是提交、撤回或删除，不改变金额、附件引用和历史；
- 已归档草稿继续出现在本人提交记录的归档筛选中，员工可恢复为可编辑草稿；恢复追加状态 revision，不重置原创建时间或伪造新草稿；
- 员工只能手动删除从未正式提交且不存在任何付款／结果未知付款的草稿，并必须二次确认；已经提交过的报销不能删除，只能按 BF-222／BF-223 撤回或追加 revision；
- 删除采用追加删除标记并从默认列表隐藏，不抹除审计、幂等记录或已经形成的 Evidence 历史引用；授权人员在审计范围内仍可识别该草稿曾存在；
- 草稿归档／删除不直接物理删除 Evidence；文件后续清理由 BF-231 和独立业务保留策略决定，不能由页面状态级联操作 OSS。

#### 开放 API 标准错误与恢复

- 所有开放 API 错误使用统一版本化结构，至少返回稳定机器码 `code`、可读 `message`、端到端 `request_id`、布尔 `retryable` 和可选 `field_errors`；
- `field_errors` 使用稳定字段路径和错误码定位逐字段问题，不能要求调用方解析自然语言；错误消息可以本地化，但机器码和字段路径在同一主版本内保持兼容；
- HTTP `401` 表示 Key 缺失、无效、过期或撤销，`403` 表示可信身份缺少当前能力／资源授权，`409` 表示 revision、幂等内容或业务状态冲突，`413` 表示上传容量超限，`422` 表示请求字段／业务校验失败，`429` 表示限流，`503` 表示所需服务暂不可用；
- `401`、`403` 和 `422` 默认不可自动重试；`429` 必须携带可重试时间，调用方按契约退避；网络超时和 `503` 仅使用原 `Idempotency-Key` 有界重试；
- 写命令已到达但最终结果无法确定时，以稳定 `UNKNOWN_OUTCOME` 状态／错误暴露，并提供使用原幂等键或稳定业务 ID 的查询恢复方式；调用方不得改用新幂等键重复提交；
- 错误响应、日志和追踪不得包含堆栈、SQL、内部主机／端口、完整 Key、认证 Header、银行账号、发票正文、文件内容或其他员工数据。

### 3.8 已确认：员工发票报销纵向闭环

本轮“走通闭环”不是宣称 OMS1 所有业务都闭环，而是完成并验收以下一条真实纵向链：

`租户管理员建立账号／成员映射并授权 → 员工创建 API Key → 外部 CLI／Skill 上传发票 → 建立并提交本人报销 → 当前无需审批进入待支付 → 财务人员确认实际付款 → Money 保存资金与核销 → 员工通过 API 列表／详情看到已支付`

#### 起点、终点与角色

- 起点：Tenant 已存在，租户管理员为真实员工建立／邀请 IAM 账号，People Person 已存在，并建立唯一可信 Subject↔Person 映射及“发票报销 API 访问”能力；
- 员工：在登录后的开放平台页面创建 Key，由外部 CLI／Skill 通过 `/open-api/v1/` 完成 Evidence 上传、本人报销草稿、明细、附件和正式提交；
- 财务人员：在 Workbench 查看待支付申请，使用独立支付确认能力登记实际付款；员工 Key 不具备审批和付款能力；
- 终点：Money Flow Ledger 已保存稳定实际资金／核销事实，Internal Finance Requests 保存 Money 稳定引用并投影已支付，员工本人列表／详情返回同一报销单的已支付状态。

#### 最小成功证据

- 使用真实 PostgreSQL、正式 IAM／Gateway／Owner 进程和 HTTPS 入口，不用浏览器内 mock、共享表、跨库写入或测试身份绕过；
- 一张允许格式的真实测试发票形成 Evidence File ID／Version，一张报销单形成不可变提交 revision，一次财务确认形成恰好一条 Money 实际付款及对应核销引用；
- 提交响应、本人列表、单笔详情、财务页面和 Money 读取对稳定 ID、精确金额、状态和 revision 的解释一致；
- 备份／恢复后 Tenant、Subject、Person、Key 非秘密元数据、File ID／Version、报销 revision、Money 引用和本人查询结果保持可解释，恢复后可继续完成新请求。

#### 必须验收的异常路径

- 同一写请求以相同 `Idempotency-Key` 重放不重复建立上传、报销或付款事实；同键不同内容返回 `409`；
- 在 Evidence、Internal Finance Requests 或 Money 中途不可用／结果未知时不伪报成功，恢复后使用原幂等键／稳定 ID 收敛为唯一结果；
- 撤销 API Key、撤销员工 API 能力或停用账号后，新的 API 调用立即失败，但已提交报销和资金历史仍可由授权人员读取；
- 跨 Tenant、切换 Person 参数、查看他人报销、由员工 Key 发起审批／付款均被 Owner 最终拒绝且不产生业务写入；
- 强重复发票被阻止，疑似重复进入人工核对；未完成安全扫描、超容量或不允许格式的文件不能提交。

#### 本闭环不代表

- 不代表银行自动代付、自动审批、OCR／AI 识别、Webhook、全部内部管理业务 API、工资、人事、项目／合同或 OMS1 全产品闭环已经完成；
- 不改变 Evidence、Internal Finance Requests、Money、IAM 和 People 各自事实所有权，也不新增通用工作流、通用 API 代理或共享业务数据库。

### 3.9 已确认：Feedback SDK V2 首阶段装配与鉴权

#### 身份、租户与权限

- `customUserId` 由 OMS 可信 IAM 上下文中的 Tenant ID＋Subject ID 派生为稳定、脱敏、不可猜测的标识；不能由页面参数自报，不能直接使用手机号、邮箱、昵称或递增账号编号；
- 同一租户内同一账号应持续得到同一值，以便“我的反馈”看到历史；不同租户即使关联同一自然人也必须得到不同值，避免跨租户反馈串读；
- Workbench 只有在当前账号具备 `feedback.use` 时才展示入口并注入 SDK 配置；隐藏按钮不是授权，OMS 的配置装配端点仍须校验可信会话、租户和能力；
- Feedback 项目 API Key 与 OMS1 员工开放平台 API Key 是完全不同的凭证类型、权限域和生命周期，不得复用、互换或由员工开放平台页面管理。

#### 安全边界

- `apiKey` 直连意味着凭证会在浏览器运行时可被提取，不能把它描述为客户端秘密；当前只能使用项目专用、最小范围、可轮换、可吊销且有网关限流／滥用监控的凭证；
- SDK 必须限制允许的父页面 origin；发布前将 OMS 正式 origin 加入 `VITE_SDK_PARENT_ORIGINS`，宿主对消息同时校验精确 `event.origin`、`event.source === iframe.contentWindow`、消息 `source` 和已知 `type`，发送时使用精确 `targetOrigin`，禁止 `*`；
- Key 不进入查询参数、本地持久化、业务数据库或日志。账号退出、切换或能力撤销时立即卸载／清空 iframe 配置，避免旧身份继续使用；
- 直连模式是首阶段兼容方案。迁移到 Session 时由 OMS 服务端保存长期 Key，基于同一稳定 `customUserId` 换取 15 分钟、单项目／单用户短 Token；迁移不得改变用户可见的反馈历史。

#### 数据所有权与失败边界

- Feedback 平台继续独占反馈、消息、附件、通知、未读和处理状态；OMS 不复制这些事实、不建立反馈业务表，也不把 Feedback 附件写入 OMS Evidence Service；
- OMS 只拥有入口选择、当前账号权限判断、稳定匿名身份派生和 iframe bridge 装配状态；Feedback 不反向成为 OMS 登录、租户、人员或业务事实 Owner；
- SDK 未就绪、凭证无效、项目成员关系失效、跨域白名单错误或 Feedback 服务不可用时，OMS 显示独立错误和重试入口，不得阻塞 OMS 其他业务页面，也不得把空响应解释为“没有反馈”；
- 当前代码的 V2 Session 模式支持 WebSocket 实时消息，`apiKey` 模式在当前 SDK 中退化为轮询；两种传输差异不得改变反馈、消息和已读事实的含义。

#### 已确认：通知与未读角标

- Feedback 项目 115 首阶段启用 V2 通知：服务端将该项目显式加入通知允许范围，Workbench 配置同时显式设置 `feedbackV2NotificationsEnabled: true`，任何一侧未启用都不得伪装成通知可用；
- “产品反馈”侧栏入口展示当前登录账号的未读数量，未读为 0 时不显示红点或空角标；只读查询未读数量不能产生已读副作用；
- 用户打开某条反馈会话后，只标记该 `feedback_id` 对应的通知为已读，不得把其他反馈的通知一并清空；
- 未读范围沿用 Tenant＋Subject 派生的稳定 `customUserId`，退出、账号切换或能力撤销时立即清除宿主内存中的角标状态；不同账号和不同租户不得共享未读缓存；
- `feedback-sdk:unread-changed` 和带 `request_id` 的 `feedback-sdk:unread-count` 响应都必须执行 BF-235 的 origin／source／iframe／type 校验，迟到响应不得覆盖新账号状态；
- 通知 API 返回未开放、超时、轮询失败或实时连接中断时，入口降级为无角标并允许用户继续打开反馈；不得阻塞 OMS 首屏、侧栏、路由切换或任何业务写入。

#### 首阶段验收方向

1. 具备 `feedback.use` 的两个 OMS 测试账号分别提交反馈，只能在各自“我的反馈”中看到自己的记录、消息和附件；
2. 不同 Tenant 下的账号即使名称相同也使用不同 `customUserId`，不能相互枚举或读取；
3. 无能力、账号停用、Key 无效／吊销、错误 Project ID、未允许父 origin 和 Feedback 服务不可用均有明确失败且不影响 OMS 其他页面；
4. “提交反馈”与“我的反馈”共用 iframe 并正确切换，关闭事件只隐藏反馈层，不改变 OMS 当前业务路由；
5. 浏览器请求、页面源码、URL、OMS 日志和错误信息不出现文档／仓库中的明文 Key；部署轮换 Key 后无需修改业务源码；
6. 后续从直连模式迁移 Session 时，同一账号仍能访问原 Feedback 项目 115 下由稳定 `customUserId` 归属的历史。
7. 项目 115 开启通知后，开发者回复能使对应账号角标增加；读取计数不清零，打开一条只清该条，其余反馈未读保持；跨账号／跨租户无法看到该角标或通知。

#### 当前实现审计与拆解依据（2026-10-25）

- 当前 OMS1 主页面由 `oms_phase1.html`／`oms_phase1.js` 装配，其主侧栏尚无产品反馈入口；现有“产品反馈／提交反馈／我的反馈”只存在于已退役的参考 OA 页面，并且点击后只显示“SDK 尚未接入”的提示，不能直接当作 V2 已接入；
- `feedback.use` 当前可在参考 OA 的浏览器权限展示目录中找到，但这只是一项 UI fixture，尚未证明 IAM Capability Manifest、Grant、Gateway 派生凭证和 Workbench 正式门禁已经具备；实施时必须先建立并验证正式 Capability 链，不能复用页面布尔值冒充授权；
- Workbench 已能从可信请求上下文取得 Subject ID，并从 Suite Manifest 取得 Tenant ID，具备生成稳定脱敏 `customUserId` 的输入；具体派生必须使用服务端受控、版本化算法，不能把两个原始 ID 直接拼接后暴露给 Feedback；
- 当前 Workbench 配置只覆盖既有 OMS 运行参数，尚无 Feedback SDK URL、Gateway URL、Project ID、通知开关或 Key 的结构化配置与启动校验；这些配置需要区分非秘密装配值和敏感 Key，测试中使用无效占位值；
- Feedback SDK V2 的父页面默认信任列表不含 `https://oatest.antuinfo.cn`，因此接入不是只改 OMS 仓库：还必须在 Arckit Feedback SDK V2 的独立发布配置中增加该精确 origin，并验证 OSS／API 跨域与 iframe bridge；
- 实施至少拆为：正式 Capability／配置 → 主侧栏入口与可访问反馈层 → iframe bridge／账号生命周期 → 未读角标 → Arckit 父页面与通知项目开关 → 单元／契约／真人浏览器正反例；任一步失败都不能以旧 OA 占位入口或浏览器 mock 代替证据。

#### 已确认：自动诊断上下文

- 提交反馈时自动附带严格 allowlist 内的非敏感诊断字段：OMS release／build、当前模块、无业务标识的路由模板、粗粒度浏览器／系统类型、语言、客户端时间和当前关联 request ID；
- 路由只能使用预定义模板／模块 key，不能发送包含资源 ID、名称或查询参数的实际 URL；浏览器／系统只使用粗粒度类型，不能上传完整 User-Agent 或额外指纹字段；
- 禁止自动附带 Tenant ID、Subject ID、Person ID、账号信息、表单内容、客户／项目／合同／申请标识或名称、金额、文件地址、认证信息、Header、Cookie、错误堆栈和业务正文，也不自动截屏；
- 实现必须从空对象开始逐字段构建并在发送前再次按 allowlist 清洗，禁止展开／序列化页面状态、全局对象、错误对象或任意调用方 metadata；未知字段默认丢弃；
- 用户主动选择的截图或文件仍走 Feedback V2 的附件能力，并由 Feedback 平台拥有；自动诊断上下文不改变附件选择，也不成为身份、授权或业务事实。

## 4. 当前明确不做的推断

- 不把“逻辑隔离”解释为所有租户共享无 Tenant Scope 的业务表；
- 不因为使用同一域名就允许前端自行提交 Tenant ID；
- 不把企业成员名册与 IAM 密码／账号事实合并；
- 不提前建立通用审批、第三方应用市场或通用 AI 数据库；发票报销 API 只实现已确认的窄闭环；
- 不在尚未澄清第 2～5 项时以页面名称代替 Owner、状态机和验收定义。
