原 OA 是围绕项目使用的一套工作界面：**派发待立项项目 → 补资料并完成立项 → 自动进入同一 OA 的项目详情 → 在基本信息、经营、生产之间切换 → 在全站资料和统计入口查结果**。经营与生产是同一项目下的并行工作区，不是让用户依次进入不同小系统。

最先必须纠正的理解：

- 派发时填写项目名称和经营负责人；普通项目正式编号在完成立项前补，不必在派发时先有编号。
- 完成立项不要求生产负责人已经齐备；生产负责人可以后补。经营参与人、生产专业人员也有后续配置入口，不能统统升级为立项必填。
- 立项成功后原界面导航到 `/projects/:id?tab=basic`；仍在同一 OA 项目上下文里，不是跳到另一套独立应用页面。
- 项目类型决定生产工作面与进度线；多类型取工作面的并集，不是一条统一设计流程。
- “资料管理”当前是查询、下载入口，上传发生在对应业务栏目；考勤和薪酬统计当前是占位页，不能将菜单存在记为功能完成。

本文解决“只按小系统 API 验证，遗漏原 OA 的实际操作 → 每个业务动作都有可追溯的前提、输入时机、保存结果、下一步及失败检查”。原 OA 的共享表、浮点金额、读取时写状态和非原子保存不是应当复制的设计；应保留业务体验，使用 BizFoundry 已接受的数据所有权、精确金额、IAM、Evidence 和版本化契约实现。

## 8. 进度与完成：不能从菜单推断

| 结果 | 当前源码计算 | 不应外推 |
| --- | --- | --- |
| 经营进度 | 招投标 → 合同 → 支付，首个未满足项为 current，之后 pending；经营成本还需有记录或不适用 | 栏目都能打开，不代表允许任意状态命令；未审完所有后端写入前不能断言完整锁序 |
| 合同阶段 | 至少一份合同，且计入合同均有合同文件引用 | 并未在此函数逐字段证明“所有必填附件／资料完整” |
| 支付阶段 | 两经营链各自 expected > 0，实付／实收达到其定案金额，缺有效定案时回退合同＋补充金额；旧实现有 0.005 浮点容差 | 不能把两链混算；目标实现不得沿用浮点金额／容差机制 |
| 生产进度 | 所选类型各阶段完成；另需参与人、批复审计、生产成本、外委、生产奖金有相应记录或设不适用 | 当前很多门槛是记录存在／文件存在，不是复杂业务完整性已验收 |
| 项目总体完成 | 经营和全部类型生产条件共同满足；不适用恢复后重新计算 | `GetProgress` 会写 OA2026 ProjectState 的 overall_status／completed_at；不能直接等同主 Project status，也不能复制“GET 写业务状态”到新架构 |

上述计算见 E20 663～928。不适用不是“删资料”：它影响适用性和进度，资料事实、恢复适用后显示、权限与审计都应单独验收。原 OA 不适用选项还存在较新需求与遗留逐文件选项冲突，需要原站确认。

奖金原式为 `基数 × 比例 / 1.065` 并保留两位小数；经营取甲方链定案，生产取公司链实际回款。但分配表独立填写金额基数，固定额在比例池之外；必须确认业务期望，不能因出现同一个“奖金”词就认为两块已闭环。BizFoundry 独立 Bonus、不可变来源快照、整数货币和 Money 建议边界仍有效。

### 9.3 按原 OA 逐步执行和验收

每个操作 ID 建一条验收记录：`原入口 → 使用者有效权限 → 此时必填／可后补 → 命令及所有者 → 保存事实 → 返回／刷新 → 失败后续 → 浏览器证据`。涉及跨应用时再补幂等、撤权、依赖故障、来源版本和恢复；不能用角色名字或页面按钮替代目标授权。

以下是实施／验证顺序，不是要求客户先做完全部经营再开始生产。立项后的经营和生产在同一个项目中并行；每个步骤的实际权限来自有效授权，不按“管理员”或岗位名称笼统推断。

#### 第一步 从派发到同一项目详情

| 步骤 | 按原 OA 点击和填写 | 应看到的结果 | 当前验收状态 |
| --- | --- | --- | --- |
| 1 | 登录 → 项目管理 → 项目立项；查看默认“关于我的”，有额外权限才切“全部” | 待立项列表仅显示可访问任务 | 原源码已确认；克隆全部范围／多角色未验 |
| 2 | “新建待立项项目” → 普通项目；填名称、选经营负责人 → 创建 | 创建一个草稿，自动打开它的完成抽屉；此时不用填正式编号 | C 真实派发自动开抽屉已单列复核；`.3` 修复其刷新误开旧项目，取消和重新打开仍为同一 C |
| 3 | 完成抽屉：名称、正式编号、至少一种项目类型必填；日期、费率、甲方、资质、概况按需填；生产负责人可空 | 当前项目资料保存，仍可识别未完成的内容 | 核心字段新夹具路径曾验；其余可录入字段仍占位，不等效 |
| 4 | 点“完成立项并进入详情” | 关闭抽屉，进入同一 OA 的当前项目基本信息；不跳独立 Project 产品 | .1 新夹具正常路径及 .2 旧状态夹具补齐／更换后完成通过；用户原记录未代提交，完整表单未通过 |
| 5 | 基本信息 → 编辑；补、换或清除两类负责人，按各自权限保存 | 当前项目刷新；负责人不是人员账号或专业参与人 | C 后补、取消、无效类型、no-op、明确清除／恢复和旧历史均复读；`.4` 过期 Cookie 原表单一次保存通过，完整分权／撤权矩阵仍待验 |
| 6 | 返回项目管理，搜索编号，再打开；刷新详情 | 原项目、已保存资料、负责人保持；返回上下文正确 | C 实际编号 Enter 搜索、详情刷新、页面返回及浏览器 Back／Forward 保持同项目／搜索条件；未据此关闭原编号年份排序或项目包矩阵 |

普通项目主链未关闭前不推进新的 B02 功能。必须用隔离副本重现用户这类数据，不能只换一个“干净新项目”绕过去；原记录只读，不擅自补经营负责人。

本步骤必须另测八种情况：新建且生产负责人空；旧草稿缺经营负责人；已有生产负责人原值不变；明确更换生产负责人；保存资料成功而完成失败；保存分工成功而完成失败；结果未知后的刷新／重试；无权、撤权及并发 revision。核对唯一 Project ID、无重复分工、旧历史保留，以及可见缺口能在同一工作面按授权处理。通过后才能将 I01～I04 标为关闭。

#### 第二步 项目管理和项目包

按年份／时间线查项目，Enter 搜索，经营／生产进度筛选；打开详情后返回应保留原筛选和位置。再用独立夹具验证项目包：创建包 → 完成包立项（编号可空）→ 新建子项目（正式编号独立）→ 打开子项 → 返回父包。只有两层，不假设父资料后改自动同步。

归包／外包成新包必须先看预检、确认后核对 ID 和既有业务保持，再验证可安全撤销的条件。删除仅用非真实夹具验证影响，不拿当前用户项目试删。对应 P01～P06；源码流程已拆，完整公网矩阵未通过。

#### 第三步 同一项目经营操作

| 顺序 | 在经营工作区的具体操作 | 必须复读的结果与继续方式 |
| --- | --- | --- |
| 1 | 甲方信息：行内填名称、联系人和电话，保存；名称提示只辅助输入 | 刷新仍是本项目联系资料；不要求用户跳 Party 产品新建，也不自动认定主体身份（B01） |
| 2 | 经营参与人：添加抽屉只选已有人员，保存；确认移出 | 留在本项目名单；移出不删除人员账号；重复及分权受控（B02） |
| 3 | 招投标信息：选承接方式，分别上传所需资料；确实不适用才设置，并测试恢复 | 比选／谈判与招投标的材料要求不同；齐备不表示签约，不适用不删文件（B03） |
| 4 | 合同信息：选“甲方→资质”或“资质→公司”；填号、日期、金额，先保存原始合同 | 获得该链的合同；再补合同文件、协议、定案表。附件失败要续办原合同，不能重复创建（B04） |
| 5 | 在该合同维护补充协议及定案，选择跟随合同金额或手工定案 | 原合同／协议／定案关系能解释；已确认事实用更正保留历史，不直接覆盖（B05～B06） |
| 6 | 支付信息：选正确往来链，填支付时间、费用类型和金额；按需关联发票 | 区分甲方支付与公司收到；保存后金额和列表一致（B07） |
| 7 | 开票信息：选正确链，填开票时间、费用类型和金额，可上传发票、关联支付 | 上传成功而登记失败可恢复；一对一关联必须同项目同链；取消关联不删资金（B08～B09） |
| 8 | 经营成本管理：选类型、填金额，可补日期、说明、票据，提交 | 真记录刷新，不是“校验通过”；删除、更改及票据失败单独验证（B10） |
| 9 | 奖金分配：设置经营奖池，再维护人员分配、日期、比例／固定额 | 当前原奖池与手填分配基数不是自动同一来源；分配不等于实际付款（B11～B12） |

本工作区仅部分甲方输入路径有公网证据；合同、资金、成本等独立系统工程测试不等于这些 OA 按钮已接通。金额修改、记录编辑／删除、取消、不适用恢复、文件替换都要附在对应操作后验，不能只测新增。

#### 第四步 按项目类型进行生产

先在生产工作区配置人员：按专业选择设计／参与／校核／审核等，审定／概算有自己的位置；生产负责人和这些专业成员不是同一个字段。每次保存回读本项目名单，多个请求部分成功时只续办未完成项（D01）。

| 立项选择的类型 | 按原 OA 进入的工作面 | 要执行的操作 |
| --- | --- | --- |
| 设计 | 方案 → 初设 → 施工图 → 施工配合相关资料 | 各面保存主成果、审核资料及评分；变更／竣工另验上传、替换、下载（D02、D05） |
| 咨询 | 方案 → 咨询报告 | 方案保存；报告选一个或多个文件上传、登记、刷新（D02、D04） |
| 勘察 | 方案 → 试验 → 报告 | 试验文件上传后登记阶段引用，报告另存；不得把上传成功当阶段登记成功（D02～D04） |
| 测绘 | 方案 → 报告 | 共用报告展示不表示可以混合各类型事实或权限（D02、D04） |
| 多类型 | 显示所选类型工作面的并集，各有进度线 | 用同一 Project 验咨询＋勘察等组合；不得强行走一条设计流程 |

然后逐项验证批复／审计、生产成本、对外委托、生产奖金（D06～D10）：批复可引用合同金额或手录；审计的“UI 引用批复、后端读合同”冲突必须核实；外委先保存受托方和委托，再维护付款明细，部分失败不重复新建；生产奖金来源为公司实际收款，与经营定案不同。各栏目是否适用、恢复适用、金额与文件权限分别测试。

原源码工作面已拆；完整同 OA 公网生产旅程未通过。任何按类型隐藏、记录存在即完成、读取时改状态的原实现都不能未经确认直接变成目标规则。

#### 第五步 回到资料和统计检查业务结果

项目资料管理 → 展开刚才的项目 → 找到业务栏目产生的文件 → 下载，按需查看下载人员；核对版本、下载权限、过期和实际字节。当前原资料管理只有下载及人员明细，不把业务栏目里的预览功能移到这里，也不新增全站上传按钮（F01～F02）。

项目统计信息 → 台账 → 关键词／费用／日期／状态筛选 → 展开支付／开票 → 分别导出；再看公司两条经营链、人员奖金明细，必须与前述项目事实对得上。原考勤、薪酬是占位，不记为已实现（S01～S04）。本步不能用孤立统计夹具替代同一项目业务来源，当前公网完整证据未齐。

#### 第六步 逐角色检查权限和失败恢复

设置 → 人员管理／权限配置按原可用操作拆解：新增／修改、状态确认、岗位模板保存／重置、项目可见范围。People 人员与 IAM 身份仍分别拥有数据，不照搬旧同表。原临时授权 UI 未开放，单列为未实现（A01～A04）。

对前五步换普通人员、经营责任人员、生产责任人员、金额受限人员和身份管理员等授权组合，验证读、写、金额、文件各自允许或拒绝；撤权／停用后动作和服务端同时收敛。每次只制造一种可恢复故障，用非真实数据验证恢复后不重建项目、合同、资金或文件。当前不能用全权测试管理员的成功代表这些人都能用。

#### 第七步 连续旅程和正式交付

前六步各自关闭后，再让同一个 Tenant／Project 从立项走到经营、各类型生产、资料与台账统计，并在相同发布物的空目标恢复后继续操作。C8、OSS 文件接入、Web OSS 静态分离、正式 clean-HEAD 制品仍是独立门禁，不在本次源码拆解中变成通过。低负载串行执行，不启动本地 Docker，不复活 restore20。

每次只宣布一个操作的已测范围和剩余缺口；按钮能点、真实提交、刷新保持、下一步到达、失败可继续缺一不可。失败立即写回本清单及当前报告，不用“后端已通过”覆盖用户反例。

原站可用地址／授权测试身份尚待取得；若无原站可访问环境，继续做源码比对及非真实夹具验证，但必须标记“原站真人未验”。任何与原站确认需求相冲突的规则先列差异并取得明确选择，不自行以小系统页面顺序替代 OA 使用流程。
