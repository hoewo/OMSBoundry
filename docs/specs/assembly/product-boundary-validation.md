# 小系统群产品边界验证

日期：2026-09-23  
状态：验证方法已接受；首个参考 OA 实际组合变更已通过六层归属验证，跨客户商业适配结论尚未成立

## 1. 要回答的问题

OMSBizFoundry 的目标不是仅让一组服务成功运行，而是面向 OA 所处的现实商业圈子，把反复出现且语义稳定的问题做成可独立交付的小系统，使新客户主要通过选装、配置、策略、类型化扩展和客户装配完成交付。

这个目标同时面对两个相反风险：

- 解耦和复用不足时，每个客户都要求修改或分叉核心系统，最终仍然是重复定制；
- 追求过度 DRY 时，客户差异被压入万能字段、万能流程和复杂条件分支，核心系统变成更难维护的通用平台。

因此，“整套系统已经贯通”只证明工程装配成立，不证明产品边界正确。产品边界必须通过多个真实业务场景反复检验，并允许证据否定当前划分。

## 2. 两条独立验证轴

### 2.1 独立产品轴

每个业务小系统都必须能够作为单独产品交付。这里的“单应用”表示一个被客户选择的主要业务结果及其显式依赖，不表示只运行一个进程。面向公网的标准最小组合是：

```text
Nginx + Gateway + IAM 契约提供者 + 选定结果应用 + 已声明直接依赖
```

应用没有永久的“核心／辅助”商业等级：Party 可以是主体管理场景的选定结果应用，也可以是 Contract、Money 或 Project 的直接依赖；其他应用同样由具体业务结果决定在组合中的角色。只有实际使用文件时才附带 Evidence Service；只有需要统一主体当前档案时才附带 Party Directory。People & Groups、Project Workspace、另一个台账和其他业务扩展都不是隐式启动前提。最小组合必须证明：

- 从空环境安装、迁移、登录并完成自身核心业务闭环；
- 只启用该应用时，菜单、路由、进程和权限目录一致；
- 未安装的应用不会造成隐藏启动依赖、跨库查询或失败级联；所有直接依赖必须显式进入产品清单、版本契约和故障验收；
- 可以独立升级、备份、恢复、导出和停用；
- 使用与完整组合相同的镜像、API、migration 和 IAM 契约，不维护客户专用核心分支。

### 2.2 商业适配轴

每个真实业务案例都按业务事实和生命周期拆解，不从现有页面、表名或岗位反推产品结构。每项差异必须放入以下唯一一层：

| 层次 | 进入条件 | 典型内容 |
| --- | --- | --- |
| 稳定内核 | 至少两个独立真实场景拥有相同业务含义、所有权和纠错生命周期 | 合同 revision、义务、实际资金、核销 |
| 配置 | 只改变术语、字典、显示、编号或简单阈值，不改变事实语义 | 客户称谓、分类显示、编号前缀 |
| 策略 | 同一事实输入在不同客户中采用不同、可版本化的计算或决定 | 合同依据如何形成义务建议 |
| 类型化扩展 | 差异拥有自己的对象、状态、责任人和纠错生命周期 | 报销、奖金、施工计量、付款意图 |
| 客户装配 | 改变选装系统、页面旅程、角色映射和外部接口，不改变核心事实 | 菜单、SSO、审批接入、系统组合 |
| 客户专项 | 只在单个客户成立且尚无稳定复用证据 | 一次性报表、特殊历史数据处理 |

客户专项可以交付，但不得伪装成公共内核；重复出现的专项也不能仅因出现两次就自动上升，仍需确认其业务含义和生命周期相同。

### 2.3 稳定 Base 与 Customer Overlay

上述六层以两个版本化制品边界交付：稳定 Base 保存已经通过独立与组合验收的应用、契约、migration 和装配组件；Customer Overlay 保存当前客户增加的配置、策略、类型化扩展、连接器、只读投影和专项包。Deployment Instance 再注入客户环境的域名、证书、秘密、数据与备份。

“尽量只做加法”表示交付优先增加 Overlay 内容，不表示 Base 永不修改。公共缺陷、重复稳定语义和所有消费者都需要的兼容能力必须回到 Base 演进；Overlay 不得覆盖 Base 镜像、修改其他应用数据库、复制可写事实或维护长期客户核心分支。完整规则和反证门槛见[稳定 Base 与客户覆盖层调研](../../../arckit/tech/assembly/customer-overlay-research.md)。

### 2.4 标准 Web 与定制前端交付轴（远期目标）

商业上优先减少定制：标准 Web 应覆盖已选装应用的主要业务旅程，让低定制客户通过安装、启用和基本配置即可开始使用，而不是每单都先制作客户页面。它是与后端契约分别版本化、可独立发布的 Base 制品；轻定制仅在明确的品牌、术语、导航和声明式扩展点增加 Overlay。确需完全定制的客户可以替换前端制品，但仍使用相同的 Gateway／IAM、应用公开 API、事实所有权和服务端 `allowed_actions`。是否达到“少定制、可升级”必须用真实客户交付耗时、标准前端覆盖率、Overlay／专项数量、兼容升级和回滚证据检验，不能由一套参考 OA 页面或一个 OSS Bucket 推出结论。

目标部署允许标准前端由独立 OSS 网页 Bucket 静态托管，文件 Evidence 使用另一私有 Bucket；受保护业务请求不绕过正式入口链。当前 Go Workbench 依赖服务端按会话和 Suite 渲染，OSS 静态分发、前端独立发布及完全定制前端兼容性均未验收。静态资源迁出可作为较小的部署实验，但不算标准前端产品化通过。

## 3. 可证伪判据

### 3.1 当前边界成立的证据

一个真实场景只有同时满足以下条件，才能支持当前产品方向：

- 所需业务结果可以由现有小系统加明确的配置、策略、类型化扩展或客户装配完成；
- 不需要跨应用读取内部表、共享领域模型或由连接器替目标应用确认事实；
- 不需要复制、修改或长期 fork 稳定内核；
- 未选装系统保持非必需，单个小系统仍能独立完成自身闭环；
- 新增差异有唯一责任层，并能解释失败、纠错、升级和历史数据；
- 场景完成后，已有场景和独立交付验收继续通过。

### 3.2 过度抽象信号

出现下列任一情况，不能继续用“配置更灵活”解释，而要重新检查边界：

- 核心表持续增加客户专用可选列、自由 JSON 或行业枚举；
- 同一状态机包含大量互斥客户分支，且不同分支的事实含义或纠错方式不同；
- 为复用少量代码而增加新的强制服务、共享数据库或同步调用链；
- 客户岗位、菜单、按钮或页面名称进入业务授权和领域判断；
- 一个所谓公共对象同时承载合同、审批、票据、义务和资金等不同生命周期。

### 3.3 解耦不足信号

出现下列任一情况，说明定制仍在侵蚀稳定产品：

- 为单个客户复制仓库、维护长期客户分支或现场修改核心镜像；
- 增加一个客户场景必须同时修改多个无直接责任的业务应用；
- 可选应用停机后，目标小系统无法读取或写入自己的核心事实；
- 相同且语义稳定的变化在多个客户装配中反复手工实现，却没有形成明确配置、策略或类型化扩展；
- 客户升级依赖人工合并核心代码，而不是替换版本化制品并迁移配置或扩展。

## 4. 每个场景保存的验证账目

每个真实场景至少记录以下信息，使方向判断不再依赖感觉：

1. 客户要解决的问题、可观察结果和明确不解决范围；
2. 脱敏的真实输入、参与者、时间点、金额或其他关键事实；
3. 每项需求在六层边界中的归属及理由；
4. 需要启用的小系统和基础设施，未启用系统列表；
5. 核心代码、公开契约、配置、策略、扩展和装配分别发生的变更；
6. 首次交付和下一次升级是否需要客户分支或人工合并；
7. 独立运行、故障隔离、历史纠错、导出及恢复证据；
8. 被当前模型拒绝或无法解释的事实，以及它是否否定既有边界。

持续观察的指标包括核心变更范围、客户分支数量、强制依赖数量、装配变更范围、交付用时和既有场景回归结果。这些指标用于比较场景和发现趋势，不以任意单一数值代替业务判断。

上述账目使用 [Customer Scenario Evidence Contract v1](../../../contracts/scenario-evidence/v1/README.md) 保存和校验。当前参考 OA 的机器可读基准明确标记为 `reference_product`；第二个真实客户从 [`customer-scenario-evidence-v1.json`](../../templates/customer-scenario-evidence-v1.json) 建立 `draft`，在取得客户确认和实际验收证据前不得改为 `passed`。契约门禁只保证证据身份与边界规则没有被绕过，不替代人工业务判断。

第二客户按[采集与就绪判定手册](../../operations/second-customer-scenario-intake.md)和[访谈工作表](../../templates/customer-scenario-intake-v1.md)取得脱敏事实。readiness report 只区分“继续访谈”“可以进入实现评审”“可以形成最终结论”三类操作门槛；它不推断客户需求、不自动选择六层归属，也不把一份场景提升为跨客户结论。

当参考基准和第二客户均形成最终证据后，`make scenario-evidence-compare` 生成固定维度的比较报告。自动部分只负责应用集合、六层／处置数量和七项边界值的无损整理；事实含义、所有权、生命周期、纠错是否等价，核心新增是否真正通用，以及交付时长和改动范围，仍由产品与业务人员逐项判断。比较报告永远不输出跨客户通过结论；真实客户为 `failed` 时，非零信号作为反证保留，而不是阻止生成比较材料。

## 5. 阶段一参考产品

阶段一以现有完成度较高、定制化明显的 OA 作为参考产品，验证当前小系统群能否重组出一套可用、可解释、可独立交付的参考 OA。参考 OA 是第一份系统性业务证据，不是行业标准；阶段一通过也不代表多个客户场景已经验证。

阶段一先盘点参考 OA 的能力与核心旅程，再决定 Project Workspace、连接器、策略、审批适配或其他类型化扩展的实现顺序。不得按旧 OA 页面、数据库表或路线图编号直接复制实现。目标、范围方法和验收门槛见[阶段一参考 OA 小系统重组验证](./oa-reference-stage-1.md)。

## 6. 第一条验证链

第一条业务证据链选择 OA 中已经出现、且最能同时检验系统独立性与组合边界的流程：

```text
合同／结算依据
  → 由明确责任人确认应收或应付
  → 形成 Money Flow 自有义务
  → 独立登记实际收付款
  → 核销并保留后续调整与纠错历史
```

选择该链不是预先决定建设 Contract → Money Flow 连接器。现有 OA 与 OMS 雏形对“合同是否直接形成义务”给出了不同规则，正适合检验稳定内核、客户策略和装配责任是否分得正确。

第一轮只取得一条真实、脱敏的首次形成案例和一条后续变化案例，完成事实映射与纸面走查；在触发事实、责任人、账簿主体、金额、幂等身份和失败处置得到确认前，不实现连接器或审批平台。

## 7. 阶段一验证结果与仍待验证轴

产品边界验证 0.1 包含三个互不替代的结果：

1. **六个独立业务产品**：Contract、Money、People、Evidence、Project、Design 的 Level A 本地独立 Demo 已全部从空状态通过主闭环、重放、失败关闭和清理；这证明业务产品独立性，不冒充完整公网入口；
2. **参考 OA 业务组合**：[OA 全景能力与核心旅程审计](./oa-reference-capability-journey-audit.md)选择的项目立项、经营合同与回款、生产交付、资料追溯四条旅程已经由 Level B 高保真本地组合通过；薄 Project Workspace 和独立 Design Operations 没有吞并相邻应用事实；
3. **完整入口与环境交付**：当前高保真可移植开发包已独立通过；`Nginx + Gateway + IAM + 选定业务应用` 的公司私有 Ubuntu、正式 clean-HEAD 发布和个人试验田公网仍是独立部署轴，不能由前两项结果替代。

阶段一业务架构已经证明 M9 采用薄 Project Workspace，并把设计项目阶段、适用性和成果规则放入类型化扩展是可运行的；没有建立 Contract → Money Flow 自动连接器。下一步不是继续按路线图堆功能，而是保存本次实际变化的六层账目，再用第二个独立真实客户场景反复证伪。

## 8. 阶段一实际组合变更账目（2026-09-25）

本轮把“最小 J1～J4 能跑通”扩展为“高保真 J1～J4 可解释、可纠错、可重放、可局部降级”。变化来自已经运行的参考 OA 证据，不是假设的第二客户需求；它验证定制化开发方法能否承接一次真实组合增量，但不能单独证明跨客户通用性。

### 8.1 可升级与不分叉证据

- 实际变化继续使用同一六个核心应用、公开 API、IAM 契约和各自 migration；高保真增量没有新增客户数据库、客户镜像、客户目录或长期客户分支，当前仓库分支仍为 `main`；
- 组合变化没有新增业务数据库 migration。唯一公共契约调整是 Design reference-read 的加法字段 `id`，旧 `work_item_id` 保留；
- 演示续跑状态采用向后兼容 JSON。`TestReadStateAcceptsPreHighFidelityState` 证明高保真驱动可以读取只有最小 J1～J4 字段的旧状态，并把新增进度视为未执行，而不是伪造完成；
- 所有新增业务动作使用固定幂等命令、公开 API 和来源 revision；完全空库执行后立即重放保持同一批稳定业务 ID。六个 Level A 独立 Demo 的 6/6 结果没有被组合变化替代，Level B 五来源隔离继续通过；
- 上述证据证明本次业务变化不要求合并客户分支或迁移客户专用数据结构。随后生成的 `v0.1.0-demo.11` 已证明六个小系统可分别独立运行，设计交付、商业台账两个子集以及当前高保真全量业务组合也都能从同一无源码归档复现；它仍不证明真实公司 Ubuntu、正式 clean-HEAD 发布、Nginx／Gateway／正式 IAM 或公网入口已经通过，这些属于独立部署轴。

### 8.3 阶段结论

这次实际组合变化支持“稳定内核 + 配置 + 类型化扩展 + 客户装配”的开发方式，并证明连接器和客户专项可以在证据不足时被明确拒绝，而不是被迫进入公共内核。它没有实际实现新的策略，因此只验证了策略的放置门槛和反证规则；下一次出现有输入、输出、版本和纠错样例的真实客户计算规则时，必须单独验证策略运行形态。

阶段一现在可以把首个参考 OA 的本地业务架构与定制化方法视为已通过。仍不能宣称已找到整个商业圈子的最终平衡点；至少还需要第二个独立真实客户场景，比较交付时间、核心变更范围和被拒绝需求，才能判断这些层次是否持续成立。
