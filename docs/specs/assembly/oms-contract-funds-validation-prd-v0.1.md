# OMS 资质单位合同与资金经营验证版 PRD v0.1

日期：2026-10-10  
状态：候选产品方向稿；用于原型评审，不是正式业务规则或生产实施规格

## 1. 文档目的

本文件先用简明方式回答三个问题：OMS 想解决什么、用户通过它完成什么、快速原型应呈现什么。

当前信息主要来自二手转述、原 OMS 文档、旧交互原型和产品推演，尚未经过客户本人、财务、法务及真实单据完整核验。因此本文提出的是一套可以被客户确认、修改或否定的候选产品模型，不把行业推断写成客户事实。

## 2. 产品定义

OMS 暂定为面向资质单位的合同与资金经营验证产品。

它以一份上游合同为经营主线，把合同文件、项目或事项、下游协作对象、开票、应收、回款、结算、应付、付款授权和实际付款组织到同一条可追溯链路中，使管理人员能够快速看清：签了什么、谁在履约、钱回了多少、还差多少、准备付给谁、依据在哪里。

当前版本首先是一套需求验证工具。它通过具体、可操作、允许被推翻的页面和虚构案例，帮助客户把真实业务讲清楚；不表示正式 OMS 产品设计已经完成。

## 3. 想解决的问题

当前优先验证以下四个痛点假设：

1. 合同及其附件分散，查找和确认上下游关系不方便；
2. 一份合同或项目已经开票多少、回款多少、还差多少不够清楚；
3. 参与履约的下游对象、承接内容、合同和人员关系缺少统一视图；
4. 合同、票据、回款、结算和付款依据散落在表格、文件和沟通记录中，难以形成一笔完整经营账。

这些内容目前属于高优先级验证假设，不是已经取得客户一手证据的正式事实。

## 4. 目标用户

- 管理人员：查看整体合同、回款、待收待付和经营异常；
- 合同或运营经办人员：维护合同、下游协作关系和业务附件；
- 财务经办人员：登记开票、应收、回款、应付和实际付款；
- 审核人员：查看业务依据，并处理候选的应收确认、应付确认和付款授权事项。

上述角色名称和权限仅用于原型叙事，正式角色矩阵仍待客户确认。

## 5. 核心业务主线

原型使用以下候选经营循环帮助客户走查业务。当前已经确认的方向事实是资质单位向上游单位开票；循环本身仍是待客户验证的产品模型：

```text
经营事项
  → 查看当前未回、未付和资料缺口
  → 分别推进两条事实链
      上游：资质单位向上游开票 → 应收确认 → 实际回款
      下游：协作与结算 → 应付确认 → 付款授权 → 实际付款
  → 分别核销应收与应付余额
  → 生成下一轮待办
  ↺ 持续推进，直至收付和异常完成处理
```

循环描述经营人员持续查看和推进业务，不表示收到上游款后系统自动向下游付款。项目、合同、开票、应收、回款、应付、授权和付款分别表达不同事实。当前原型可以展示它们之间的显式引用，但不得因为前一项存在就自动生成后一项。

## 6. 核心产品原则

### 6.1 以合同为经营主线

用户从一份上游合同进入后，可以看到其附件、关联事项、下游协作对象、票据、收款、结算和付款情况。项目用于表达履约上下文，不替代合同的法律与金额含义。

### 6.2 金额事实相互分离

- 合同金额不等于已开票金额；
- 开票不自动等于已确认应收；
- 应收确认不等于实际到账；
- 应付确认不等于付款获得授权；
- 付款授权不等于实际付款；
- 回款和付款只有经过明确分配或核销后才减少对应余额。

### 6.3 使用中性下游模型

页面统一使用“下游协作方”作为当前显示术语，并展示企业、组织、班组和个人等候选类型。候选类型用于引导客户指出真实分类，不预设某类对象必然采用对公付款、个人支付或其他固定流程。

### 6.4 不臆造计算与合规规则

管理费、税费、预留和其他调整项在原型中只作人工金额记录或示意，不预设计算公式。原型不执行真实付款、银行代发、税务申报、工资核算或法律关系认定。

### 6.5 所有结论可追溯

页面中的候选字段和状态应明确显示“演示数据”“候选模型”或“待客户确认”。正式规则必须能够追溯到客户确认、真实业务材料、经办人员证据、专业意见或适用的正式制度。

## 7. 原型产品大纲

### 7.1 经营总览

展示合同金额、开票金额、已确认应收、实际回款、未回款、已确认应付、已授权待付和实际付款，并突出逾期、资料缺失和资金条件异常。

### 7.2 合同经营

提供上游合同列表和合同经营全景。详情中集中展示合同原件、关联事项、下游协作关系、开票—应收—回款时间线、结算—应付—授权—付款时间线及附件。

### 7.3 下游协作

展示下游协作方档案、候选类型、联系人或成员、承接事项、关联合同、结算情况和资料完整性。具体类型和付款路径保留待确认标记。

### 7.4 开票与回款

分别展示开票记录、已确认应收、预计到账日期、实际回款、分配核销、未回款和逾期情况，使用户能够快速回答一份合同的钱回到什么进度。

### 7.5 结算与付款

展示结算依据、管理费等人工调整项、已确认应付、付款申请、授权状态、实际付款和未付余额。任何候选审批都不冒充资金已经发生。

### 7.6 资料与待办

汇总合同、票据、结算、确认和付款凭证等资料，并按影响显示待确认角色、缺失附件、逾期收款和待处理付款事项。

### 7.7 产品整体界面形态

原型采用桌面经营工作台形态，打开后先看到当前资质单位的经营总览，而不是数据录入表单。

```text
┌──────────────────────────────────────────────────────────┐
│ OMS｜当前主体：示例资质单位            演示数据／候选模型 │
├──────────────┬───────────────────────────────────────────┤
│ 经营总览     │ 页面标题、当前筛选、主要操作              │
│ 合同经营     ├───────────────────────────────────────────┤
│ 下游协作     │ 合同额｜开票｜应收｜回款｜未回款｜待付款   │
│ 开票与回款   ├───────────────────────────────────────────┤
│ 结算与付款   │ 风险与待办                                │
│ 资料与待办   ├───────────────────────────────────────────┤
│              │ 当前工作区的列表、关系或时间线            │
└──────────────┴───────────────────────────────────────────┘
                                             详情从右侧抽屉展开
```

总览负责发现问题，列表负责定位记录，合同详情负责解释一笔业务的完整关系。用户查看详情后关闭右侧抽屉，应返回原列表和原筛选位置。

### 7.8 关键页面与核心字段

| 页面 | 主要内容 | 原型核心字段 |
| --- | --- | --- |
| 经营总览 | 整体金额、风险和近期事项 | 合同额、开票额、已确认应收、已回款、未回款、已确认应付、已授权待付、已付款、逾期数量 |
| 合同经营列表 | 定位一份上游合同 | 合同编号、名称、上游主体、关联事项、合同金额、开票、回款、未回款、状态、附件完整性 |
| 合同经营全景 | 解释一份合同的完整经营链 | 合同摘要、原件、关联事项、下游协作方、收款时间线、结算付款时间线、待确认项 |
| 下游协作 | 查看谁参与履约及其关系 | 协作方名称、候选类型、联系人或成员、承接内容、关联合同、结算状态、资料状态 |
| 开票与回款 | 追踪上游资金进度 | 发票编号、开票日期、开票金额、应收编号、确认金额、预计到账日、回款金额、核销金额、未收余额、逾期状态 |
| 结算与付款 | 追踪下游资金进度 | 结算批次、结算依据、人工调整项、应付金额、付款申请、授权状态、实付金额、未付余额、付款凭证 |
| 资料与待办 | 补齐证据并处理异常 | 文件名称、文件类型、关联对象、版本、状态、待办类型、影响金额、责任人显示语 |

以上字段是为了让原型具备可讨论的具体形态，不表示字段名称、必填性或业务含义已经获得客户确认。

### 7.9 核心交互

- 点击总览金额或风险项，进入已经带好筛选条件的对应工作区；
- 搜索合同编号、合同名称、上游主体或下游协作方，列表和金额摘要同步更新；
- 点击合同编号，在右侧打开合同经营全景，不离开当前列表；
- 点击时间线节点，查看该节点的金额、日期、依据、关联记录和附件；
- 在开票与回款中切换“开票／应收／回款／逾期”视图，在结算与付款中切换“结算／应付／授权／实付”视图；
- 点击下游协作方，查看其承接事项、关联合同和候选付款路径；
- 所有“待客户确认”标记都能查看其假设来源和需要回答的问题；
- 原型筛选和抽屉可以交互，但不执行真实业务写入。

### 7.10 原型虚构案例

第一版用一份完整虚构案例贯穿所有页面：

```text
上游主体：示例城市维护单位
经营事项：2026 年北区道路维护事项
上游合同：HT-2026-001，合同金额 800 万元
开票记录：累计 320 万元
已确认应收：320 万元
实际回款：两笔，累计 220 万元
应收未收：100 万元，其中一笔已逾期
下游协作：一个候选企业型协作方、一个候选班组型协作方
下游结算：一笔已确认应付、一笔付款授权待处理
管理费等调整项：仅作人工录入示例，不展示自动公式
```

用户应能从总览发现这笔未回款，进入合同全景查看两次回款，再继续追踪对应下游结算和待处理付款。所有名称、金额和关系均显著标注为虚构演示数据。

## 8. 快速原型范围

第一版原型使用一组完整的虚构业务案例，支持：

- 六个工作区切换；
- 合同、状态和关键词筛选；
- 打开合同经营全景和协作方详情；
- 查看开票、应收、回款、结算、应付、授权和付款之间的引用；
- 查看一笔分次回款和一笔待确认付款；
- 查看候选类型、假设来源和待确认提示；
- 桌面浏览器正常使用，并兼顾窄屏查看。

原型只使用演示数据和浏览器内交互，不读取或写入真实 Contract、Money、Party、People、Project、Evidence 或 IAM 事实，不新增业务数据库、Grant 或正式业务契约。

## 9. 明确不做

快速原型阶段不包含：

- 真实客户数据导入；
- 自动管理费、税费或工资计算；
- 银行、开票、财税或工资代发接口；
- 真实审批、真实付款或生产审计；
- 任意配置的通用工作流或通用业务平台；
- 对企业合作、工程分包、劳务班组、个人支付等关系作法律定性；
- 把原 OA 的勘察、设计、测绘等详细生产流程复制到 OMS。

## 10. 原型评审要回答的问题

客户评审时重点确认：

1. 系统当前主体和上游、下游分别是谁；
2. 项目、经营事项和合同之间是什么关系；
3. 实际下游对象有哪些类型，分别使用什么合同和结算方式；
4. 开票、应收确认和项目完成之间是否存在固定关系；
5. 回款如何对应合同、发票或应收；
6. 管理费和其他扣款由谁向谁收取，在什么时点确定；
7. 应付、付款授权和实际付款分别由谁确认；
8. 哪些附件和凭证是完成一笔业务必须保留的；
9. 正常、部分回款、延期调整和付款异常分别如何处理。

## 11. 原型成功标准

- 首次接触的评审者能在十分钟内理解 OMS 主要在管理什么；
- 能从任一合同追溯到下游协作、开票、回款、结算和付款示例；
- 页面不会把候选分类、示例金额或 AI 推断表述为客户事实；
- 客户可以明确指出哪些内容正确、名称不对、关系错误、缺失或不需要；
- 评审结果能够转化为事实—假设—风险—待确认矩阵，作为后续正式 PRD 的输入。

## 12. 与现有架构的关系

本原型继续使用现有 `/oms/` 装配入口和 Unified Workbench，只验证产品信息结构与交互。Workbench 不成为业务事实所有者。

如果后续进入真实产品实施，主体、人员、项目、合同、发票、资金和文件仍分别服从 Party Directory、People & Groups、Project Workspace、Contract Ledger、Billing、Money Flow Ledger 和 Evidence Service 的数据所有权；是否需要新增 OMS 特有窄域应用，必须等真实业务样本验证后另行决策。
