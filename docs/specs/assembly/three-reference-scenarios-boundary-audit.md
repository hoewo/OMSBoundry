# 三类参考装配场景边界审计

里程碑：M6  
功能编号：M6-005  
日期：2026-09-20  
状态：已完成边界审计；不是客户需求验收

## 1. 目标

用设计单位 OA、资质单位与施工综合体、小型咨询或服务公司三个参考场景检查现有 Contract Ledger 和 Money Flow Ledger 是否保持稳定边界，以及客户差异能否留在系统外部。审计只使用当前仓库已经实现并验证的事实和已有讨论材料，不把参考场景补写成客户需求，也不以修改核心表、增加行业枚举或制造跨系统连接器来填补未知内容。

第 4 轮讨论中的三个场景是架构探针，不是三个已经签字确认、完成端到端验收的客户方案。本审计把“设计上可组合”进一步收紧为以下四种证据状态：

| 状态 | 含义 |
| --- | --- |
| 已验证能力 | 已有规格、实现和自动化验证证明的系统能力；只证明能力本身，不证明客户接受 |
| 条件可用 | 可用现有能力人工完成，但依赖尚未由客户确认的使用假设 |
| 明确缺口 | 当前明确未实现或已经审计后延期的能力 |
| 待客户确认 | 连事实含义、责任边界或验收口径都未知，不能进入实现 |

## 2. 两个系统已经证明的共同边界

- Contract Ledger 和 Money Flow Ledger 可以分别安装、迁移、启动、登录、备份和恢复；任一系统不是另一系统的启动前提。
- 两个实际 release 可以在同一主机使用不同端口、数据库和 Contract Evidence 根同时运行；单侧停机和无 bootstrap 重启不影响另一侧。
- 两个系统各自维护本地 Party、身份、会话、审计和业务事实；同名 Party 不自动成为跨系统同一主体。
- Contract Ledger 已拥有合同主体快照、revision、合同关系、结算、终止、操作性关闭、Evidence、导出和恢复能力。
- Money Flow Ledger 已拥有人工应收／应付义务、调整、减免、实际资金、核销与反向、内部转账、受控关闭、账龄、历史余额、当前经营汇总、预计现金排期、导出和恢复能力。
- 当前没有 Contract → Money Flow 业务连接器、共享 IAM、共享 Party 主数据、Project、Approval、客户 OA 装配或通用导入。
- Billing Document、坏账和真实退款已经完成边界审计但明确延期，不能用附件、减免、普通调额、负金额或冲销冒充。

## 3. 场景 A：设计单位 OA

参考设想包含项目／设计生产、合同、收支、文件、可选审批、奖金、外委以及行业分类。当前判断如下：

| 场景需要 | 当前证据状态 | 审计判断 | 正确放置位置 |
| --- | --- | --- | --- |
| 合同建立、变更、结算、终止和证据 | 已验证能力 | Contract Ledger 可独立承担，不需要把项目或 OA 岗位写进合同表 | Contract Ledger |
| 应收／应付、实际收付、核销、账龄和预计日期 | 已验证能力 | Money Flow Ledger 可按明确账簿主体人工建账 | Money Flow Ledger |
| 设计项目与生产过程 | 明确缺口 | 当前两个系统都不拥有该事实，不能用 Contract relation 代替项目生产 | 独立类型化扩展或既有 OA |
| 奖金、外委计算和行业费种 | 待客户确认 | 只有名称，没有稳定公式、生命周期和纠错规则 | 客户策略或独立扩展 |
| 合同／付款审批 | 明确缺口 | 当前没有 Decision Workflow 或审批适配器，且审批通过不等于合同、义务或资金事实 | 可选审批适配器 |
| 设计费、勘察费、咨询费展示 | 条件可用 | 可作为客户术语或分类映射；是否影响规则尚未确认 | 配置或客户装配 |
| OA 用户、岗位和组织权限 | 待客户确认 | Contract 的本地三角色和 Money Flow 的单管理员不能被描述为既有 OA 权限复刻 | SSO／IAM 适配与角色映射 |
| 合同事实自动形成收支义务 | 明确缺口 | 没有真实业务流和连接器契约，只能在两个系统分别人工登记 | 未来 M5 可选连接器 |

结论：两个台账内核可以作为设计单位 OA 的独立业务成品或外接台账使用，但当前不能交付“设计单位 OA 组合产品”。项目生产、奖金、审批、OA 身份和合同—收支流动均不得进入两个稳定内核来换取表面完整。

## 4. 场景 B：资质单位与施工综合体

参考设想包含多层合同关系、上下游收支、施工队／人员、管理费、付款意图与审批、证据和现金排期。当前判断如下：

| 场景需要 | 当前证据状态 | 审计判断 | 正确放置位置 |
| --- | --- | --- | --- |
| 多份合同之间的上游／下游关系 | 已验证能力 | Contract relation 可保存引用两端 revision 的有向关系并防环，不需要固定层级或 chain enum | Contract Ledger |
| 甲方、资质单位、施工方、个人收款对象 | 条件可用 | organization／individual Party 与自由文本合同角色可表达参与方；角色含义仍需具体合同确认 | 各系统本地 Party 与业务快照 |
| 每个明确账簿主体的上下游应收／应付 | 已验证能力 | Money Flow 可相对于单一 owner 建 receivable／payable，并隔离方向与币种 | Money Flow Ledger |
| 多主体之间自动传递金额 | 待客户确认 | 不知道由谁确认、何时形成义务、金额依据和失败后责任，不能从合同链自动推导 | 客户策略与未来连接器 |
| 管理费 | 待客户确认 | 比例基数、确认时点、调差、退回和会计含义均未知 | 独立策略或扩展，不进核心表 |
| 施工队和人员名册 | 明确缺口 | Party 不是人员履历、班组或用工管理系统 | 独立类型化扩展 |
| Payment Intent 与付款审批 | 明确缺口 | 当前只有实际付款事实；申请、意图和审批不能伪装成 Cash Transaction | 可选付款过程／审批扩展 |
| 合同证据与当前预计现金排期 | 已验证能力 | Contract 可保存版本化 Evidence；Money Flow 可保存独立于 due date 的预计日期 | 两个系统各自所有 |

结论：现有核心能够保存合同网络和每个账簿主体自己的收支事实，但不能据此宣称已经实现综合体的自动资金链、管理费、用工或付款审批。新增第三层、第四层关系不需要改 Contract 核心表；行业计算和过程对象也没有理由进入 Money Flow 核心表。

## 5. 场景 C：小型咨询或服务公司

参考设想是不部署 Project 和 Approval，只使用两个台账，主要通过人工或 Excel 建账。当前判断如下：

| 场景需要 | 当前证据状态 | 审计判断 | 正确放置位置 |
| --- | --- | --- | --- |
| 无 Project、无 Approval 运行 | 已验证能力 | 两个 release 的启动和核心业务均不依赖这两类系统 | 当前产品边界 |
| 合同人工登记和完整历史 | 已验证能力 | Contract 可人工完成主体、合同、变更、结算、证据和追溯 | Contract Ledger |
| 义务、资金与核销人工登记 | 已验证能力 | Money Flow 可用人工来源形成独立闭环 | Money Flow Ledger |
| 两系统同机使用 | 已验证能力 | 双登录、四 Cookie、单侧故障隔离和零数据交叉已通过 actual bundle 验收 | 组合部署层 |
| Excel 批量导入 | 明确缺口 | 批次权威、业务键、部分失败、冲突与纠错未定义，不能把简单 CSV 上传称为通用导入 | 待真实样例后设计的系统内适配器 |
| 票据／发票全生命周期 | 明确缺口 | Billing Document／Link 语义不足并已延期 | Money Flow 候选独立子域 |
| 多用户与简单组织权限 | 条件可用 | Contract 已有三种本地角色；Money Flow 当前只有首位管理员，尚未形成对称的多用户权限能力 | 各系统本地身份，必要时再扩展 |
| 合同自动生成义务 | 明确缺口 | 当前只能分别人工录入，不能伪称已经业务联调 | 未来 M5 可选连接器 |

结论：这是与当前实现最接近的参考场景。若客户接受人工分别建账、暂不需要 Excel 导入、完整票据、多用户 Money Flow 和自动跨系统流动，两个系统已经具备试用基础；这些前提尚未由真实客户确认，因此不能把“最接近”写成“客户场景已验收”。

## 6. 核心结构审计结论

三个参考场景都没有提供足以改变 Contract 或 Money Flow 稳定事实语义的新证据，因此本切片：

1. 不新增或修改数据库 migration、核心表、领域状态和公开业务命令；
2. 不增加“设计单位”“资质单位”“施工方”“经营经理”等固定枚举；
3. 不建立万能 Project 外键、行业扩展 JSON 或统一 FinancialRecord；
4. 不创建空的 `connectors/contract-money`、共享 Party 或共享 IAM；
5. 不把两个系统同机运行解释为合同到收支已经发生业务联动；
6. 不为三个场景复制或 fork 两个小系统代码。

现有核心无需为参考场景改表，是“当前没有证据要求改表”的结论，不是“未来任何真实客户都绝不需要扩展”的承诺。

## 7. 进入真实场景验证前必须取得的最小证据

### 设计单位 OA

- 一份实际合同到项目／生产／外委／奖金的责任边界样例；
- 需要进入两个台账的角色、操作和组织范围；
- 合同、结算、应收应付之间由谁在什么时点确认；
- 审批拒绝、撤回和已形成业务事实之间的关系。

### 资质施工综合体

- 一条真实的多方合同链及每份合同的签约主体、角色和 revision；
- 每个账簿所有者、债权人、债务人和实际资金双方；
- 管理费的依据、计算、调整、退回和历史保留规则；
- 付款意图、审批和实际付款的职责分界。

### 小型咨询或服务公司

- 是否接受合同与收支分别人工确认；
- 实际 Excel 样本、业务唯一键、重复行、部分失败和纠错期望；
- 票据是否为首发必需以及真实作废／红冲／更正样例；
- 用户数量、角色、组织范围和数据隔离要求。

## 8. 验收标准与结果

| 验收项 | 结果 |
| --- | --- |
| 每个场景只引用已有实现或明确的参考设想 | 通过 |
| 已验证能力与客户接受、条件假设严格分开 | 通过 |
| 未知内容标为缺口或待确认，不生成代码 | 通过 |
| 三个场景均不要求修改两个系统现有核心表 | 通过 |
| Project、Approval、OA、行业角色和算法未变成启动依赖 | 通过 |
| 没有伪造 Contract → Money Flow 业务流或联调结果 | 通过 |
