# 第 17 轮：稳定 Base、客户覆盖层与 OA 完全体可行性

日期：2026-09-25

## 1. 本轮问题

本轮同时回答两个问题：

1. 小系统边界稳定后，客户定制是否可以像“拿出基础架子继续做加法”一样交付；
2. 当前架构能否承载现有高度定制化 OA 的完整业务，而不仅是已经通过的 J1～J4 Demo。

“能实现”必须区分架构可行性、当前功能覆盖和跨客户产品化证据。只回答一个笼统的“能”会掩盖真正缺口。

## 2. 对参考 OA 的业务理解

参考 OA 不是一组彼此独立的增删改查页面。它以项目为工作上下文，让经营链和生产链并行推进，再由资金、资料和统计形成可追溯结果。

### 2.1 项目与参与者

项目保存编号、类型、负责人和生产组织。人员可以承担经营负责人、生产负责人、设计、参与、校核、审核和审定；部分参与者没有系统账号，因此身份账号、人员名册和项目 Assignment 是三个不同事实。甲方、资质单位、我方、外委个人或公司是业务主体，不能等同于登录用户。

项目包与子项目允许包级共享经营背景，子项目独立推进生产、收付款和发票；转换、回退和合同金额分配仍有规则缺口，不能从已有表结构猜测。

### 2.2 经营链

项目通过比选、竞争性谈判、招投标或明确不适用完成承接。所需材料随方式变化。合同包含设计、勘察、咨询金额、补充和结算，现实中还存在“甲方到资质单位”“资质单位到我方”两段业务关系。

合同与结算是资金义务的依据，但不天然等于已经确认的应收应付。责任人需要确认来源 revision 和金额后，Money Flow 才拥有义务；开票又是独立的票据生命周期，不能塞进现金记录。

### 2.3 生产链

设计、咨询、勘察和测绘拥有不同阶段；同一项目可以选择多个类型并分别推进。阶段留空、明确不适用、恢复适用、替换成果和返工是不同事实。设计还存在方案、初设、施工图、施工配合／验收，成果文件、校审单、评分、批复和审计结果共同影响完成状态。

生产人员和专业分工引用 People，但项目任务不属于 People。成果字节属于 Evidence，成果在某阶段的业务含义属于生产应用。

### 2.4 成本、外委与奖金

交通、住宿等生产成本说明项目为什么发生支出；外委说明委托对象、内容、合同、评分和付款依据。两者可以向 Money Flow 提交义务建议，但不能由 Money Flow 反推来源流程。

经营奖金和生产奖金使用不同来源基数。参考 OA 的比例和除数是客户策略，不是通用金额公式；计算必须保存输入快照、版本、舍入、分配和撤销历史。

### 2.5 资料、统计与待办

项目资料入口聚合合同、票据和生产成果，但不拥有这些事实。公司、项目和人员统计是只读投影，不能通过跨库写入形成第二份真相。立项红点可以从 Assignment 与项目状态派生，回款提醒的触发与关闭规则仍未确认。

## 3. 当前覆盖判断

### 已有稳定基础

- IAM、Gateway、Nginx 和 Workbench 已提供统一入口与授权基础；
- People & Groups 提供人员、组、任职和不可变名册快照；
- Project Workspace 提供单项目身份、Assignment、外部引用和历史；
- Contract Ledger 已覆盖比旧 OA 更完整的合同 revision、终止、结算和纠错；
- Money Flow Ledger 已覆盖义务、实际资金、核销、余额、调整和反向；
- Evidence Service 已覆盖文件版本、摘要、受控访问和 OSS 边界；
- Design Operations 已覆盖 `design-v1` 四阶段、适用性、成果替换和返工。

### 可以沿现有边界增加，但尚未完成

- Party Directory 独立应用及两个台账的迁移；
- 项目包、子项目转换和合同金额分配；
- 双段经营关系与项目级权限策略；
- 咨询、勘察、测绘等生产类型；
- 批复审计结果和完整项目完成投影；
- 项目资料、公司统计、人员统计和个人待办投影。

### 需要新的责任域

- 经营承接／投标；
- Billing／Invoice；
- 生产成本／报销来源；
- 外委／采购来源；
- Bonus／Compensation；
- 跨域只读报表与工作队列。

这些能力不一定都要变成独立服务器，但必须先拥有清晰的事实、状态、纠错和所有权，再决定是独立应用还是某个类型化扩展。

## 4. 可行性结论

### 架构层面：可以实现

没有发现参考 OA 的业务关系要求破坏现有核心边界。项目可以作为组合上下文，合同、资金、人员、主体、文件和生产继续由各自应用拥有；成本、外委和奖金也可以作为来源域向台账提交正式建议。跨应用性能可以用快照、事件和可重建读模型解决，不需要回到共享业务表。

### 当前系统：还不是 OA 完全体

现有代码已经证明最难的结构骨架能够运行，但覆盖的是 J1～J4 和第一生产类型。OA 完全体不是再加几个页面，而是增加多个带生命周期和纠错规则的业务域。它属于显著的产品增量，不能靠配置一次完成。

### 商业产品线：尚未证明

完整复现一个 OA 可以证明当前 Base 对一个复杂客户成立，却仍不能证明第二个、第三个客户主要只做加法。稳定 Base 加 Customer Overlay 是合适的候选模式；它必须通过第二客户、Base 升级和客户专项数量持续验证。

## 5. 稳定 Base 与客户覆盖层

理想交付形态在使用感受上类似 fork：拿到经过验证的基础架子，再增加客户内容。但工程上不维护长期 Git fork，也不允许覆盖公共应用内部代码。

Customer Overlay 可以增加 Suite Manifest、术语与显示、版本化策略、类型化扩展、连接器、只读投影和隔离专项包。它不能覆盖数据所有权、公开契约含义、鉴权、历史规则或直接修改其他应用数据库。

“尽量只做加法”不是 Base 永不变化。两个独立客户反复需要同一语义时，或公共契约本身有缺陷时，应以兼容方式演进 Base；如果覆盖层不断复制事实、堆积分支或无法升级，则说明边界选错了。

## 6. 接受的方向

- OA 完全体成为阶段一后续的业务覆盖目标，J1～J4 保持回归基线；
- 完整复现按业务生命周期推进，不按旧页面、旧表或菜单数量推进；
- 稳定 Base 加 Customer Overlay 作为跨客户产品线候选方向；
- 客户交付优先增加装配、策略、扩展、连接器和投影，不修改公共内核；
- 任何必须共享表、复制可写事实或长期维护客户核心分支的需求都视为边界反证；
- 架构可行、功能完成和跨客户适配是三份独立结论，不互相冒充。

## 7. 开放问题

- 项目包的合同、结算和金额分配规则；
- 发票的红冲、作废、退票和跨期纠错；
- 退款与退回款的真实核销语义；
- 批复审计对合同和义务是否产生正式影响；
- 外委、成本与奖金的实际审批、撤销和重算；
- 考勤与工资属于 OA 自有域还是外部系统投影；
- Customer Overlay 的正式制品格式、兼容范围和升级回退协议；
- 第二个真实客户是否会推翻当前 Base 边界。
