# 第 18 轮：OMS 一期行业调研范围与结构缺口

日期：2026-10-11  
状态：讨论基线；行业资料只提供约束与访谈线索，不自动成为客户业务事实

## 1. 已确认方向

- OMS 一期只处理资质单位的对外经营，不把人员薪酬、耗材、奖金、报销等公司内部成本纳入当前原型；
- 未来目标需要统一财务报告，但统一报告只能组合各来源的版本化财务投影，不能要求 OMS、Workbench 或共享数据库复制所有业务事实；
- 当前确定的产品事实仍很少：主体是 OA 业务链中的资质单位，主体向上游单位开票；现有文档、旧原型、口述和 AI 分析继续作为候选基线；
- 当前进一步确认的经营主线是：工程完成后主体向上游单位开票供其做账，工程款通常按日期不确定的多个批次回收，产品需要持续显示实际到账、核销、剩余未回和下一步跟进，直到结清；
- 一期要先把对外合同、履约依据、开票、应收、回款、下游协作、结算、应付和付款的业务关系讲清，并允许客户用真实案例推翻候选模型。

## 2. 信息等级

| 等级 | 本轮含义 | 示例 |
| --- | --- | --- |
| F1 | 用户直接确认的产品方向 | 一期排除内部成本；未来需要统一财务报告；主体向上游开票 |
| F1 | 用户直接确认的经营主线 | 工程完成后开票；工程款多批、日期不确定地回收直至结清 |

| R | 官方制度或示范合同揭示的行业约束 | 过程结算、质保金、分包资质、工资专户、履约验收 |
| H | 产品候选设计 | 事项工作区、合同节点、风险分类、二级导航 |

R 只能证明系统不能把行业差异压扁，不能证明本客户必然适用某条规则。法律、财税、资质和用工结论仍须核对适用范围并由专业人员确认。

## 3. 第一轮官方资料得到的结构性线索

### 3.1 合同价款不是单一“合同金额”

财政部、住房城乡建设部关于完善建设工程价款结算的通知，以及建设工程施工／工程总承包示范合同，均明确区分预付款、进度款、过程结算、竣工结算、质量保证金与最终结清；变更、签证、索赔和价格调整可能改变可结算金额。产品不能只保存“合同金额、累计开票、累计回款”三个数字。

产品含义：一期至少需要保留付款节点类型、结算批次、价款调整、质保／担保和最终结清的扩展位置；是否启用由真实合同决定。

### 3.2 履约、验收、结算、开票和应收是不同事实

政府采购履约验收指导意见要求合同写明验收要求、与资金支付挂钩的条件和时间，并形成可存档的验收结果。建设工程过程结算又可能按时间或进度节点确认无争议工程量。

产品含义：当前“开票—应收—回款”与“结算—应付—付款”分离是正确的，但还需预留计量／验收／过程结算依据；这些依据不得自动生成发票、应收或付款。

### 3.3 下游协作关系不能只用一个“施工队”字段

住建部违法发包、转包、违法分包及挂靠认定办法，以及建设工程施工合同示范文本，要求系统能够区分主体身份、资质、合同关系、允许分包范围和现场管理责任。自然人班组、企业合作方、专业分包和劳务作业不能由产品擅自归为同一种法律关系。

产品含义：继续使用中性“下游协作方”；保存候选类型、主体引用、合同、工作范围、资质／能力材料和付款路径，但不由系统自动作法律定性。

### 3.4 人员与工资可能形成独立受监管资金链

保障农民工工资支付制度和工资专用账户办法区分人工费用、工资专用账户、总包单位、分包单位、实名制和工资保证金。该链与普通企业对公付款不同。

产品含义：一期不能默认“所有下游付款都直发个人”，也不能把人员支付混入普通应付记录。只有客户真实案例确认后，才启用人员名册、工资专户或代发批次能力。

### 3.5 资质是持续状态，不只是公司名称

公路养护作业单位资质管理办法区分资质序列、等级、有效期、许可范围、变更、延续和监督；2025 年后新竣（交）工养护项目又涉及业绩登记管理。

产品含义：如果客户确为公路养护作业资质单位，主体档案需要能够引用资质类别、范围、有效期、关键人员和业绩材料；但资质管理是否进入一期首页，仍需客户确认其痛点和实际使用频率。

## 4. 当前原型已经成立的部分

- 一级按经营总览、经营事项、收付台账、待办事项分流，避免把所有动作铺成侧栏；
- 单事项与跨事项财务视图并存，同一事实可以从两个入口查看但不复制；
- 开票、应收、回款，以及结算、应付、付款分别表达；
- 合同、资料、协作方、履约结算和收付依据可以回到同一事项；
- 付款条件、付款授权和实际付款分开，不把“有应付”误写成“已经付款”；
- 默认页面通过完成度图、分组台账和渐进披露控制信息量。

## 5. 当前原型的主要结构缺口

| 缺口 | 如果忽略的风险 | 一期候选处理 |
| --- | --- | --- |
| 履约计量／验收依据 | 无法解释为什么可以结算、开票或申请付款 | 在事项内增加独立依据与状态，不自动推动资金事实 |
| 预付、进度、竣工、质保、最终结清 | 所有收款被压成同一种，余额和风险失真 | 为收付节点增加类型和合同条件引用 |
| 变更、签证、索赔与价款调整 | 合同金额与最终可结算金额无法解释 | 以追加 revision／调整记录保留变化历史 |
| 质保金、履约担保和返还 | 未回款可能被误判为普通逾期 | 单独记录担保／留置类型、金额、条件和到期日 |
| 下游合同、资质与付款路径 | 企业对公、劳务班组和人员支付可能混淆 | 中性类型＋明确合同／证据／收款路径，禁止自动定性 |
| 异议、退回、部分确认、冲销 | 顺利路径可演示，异常发生后无法恢复 | 所有确认事实允许追加更正、部分处理和反向记录 |
| 历史导入与来源截止日 | 旧 Excel 导入后无法区分系统事实与历史数据 | 导入批次、截止日、来源文件和确认依据显式留痕 |

## 6. 一期产品主线建议

一期继续围绕一件经营事项组织，但将主线理解为两个循环和一组共同依据：

1. 上游循环：合同条件／履约依据 → 计量或验收 → 开票 → 应收确认 → 回款与核销 → 质保／尾款／最终结清；
2. 下游循环：协作合同／履约依据 → 结算确认 → 应付建议／确认 → 付款条件 → 付款授权 → 实付与核销；
3. 共同依据：主体、资质、合同 revision、变更签证、附件版本、审批记录和历史导入来源。

两个循环之间允许人工引用，但不得把上游回款自动变成下游付款。管理费、税费、人员代发、工资专户等继续作为待验证候选，不写死公式和路径。

### 6.1 Money Flow 兼容支撑原则

这条经营主线不否定现有 Money Flow。已确认应收继续由 Obligation 表达，每次实际到账继续形成独立 Cash Transaction，多笔到账通过多条 Allocation 共同核销同一应收；剩余未回继续从既有事实计算。后续变化只允许兼容演进：

- 旧 `due_on`、Expectation、API、历史行、审计和导出语义保持不变；
- 固定合同到期日、条件触发、客户承诺和无明确期限必须分开，不能都伪装成一个到期日；
- 预计现金日期不重解释为客户承诺，客户承诺和催收跟进如进入正式实现，应使用独立、追加式、可追溯的版本化事实；
- 开票仍不自动生成应收，实际回款仍需显式核销，也不自动形成下游付款或授权；
- 在客户样本没有确认具体期限和承诺规则前，当前工作只调整 OMS 验证原型，不提前修改 Money Flow schema。

## 7. 下一轮原型应优先验证

1. 单事项能否一眼回答确认应收、累计到账、剩余未回、回款批次数、最近回款和下一步跟进；
2. 一条应收能否通过浏览器内模拟动作连续登记多笔回款并逐步减少余额，直至结清，同时保留每批记录；
3. 没有固定期限时能否准确显示“待跟进／承诺待兑现”，有合同到期依据时才显示逾期；
4. 跨事项收付台账能否集中查看未回、待跟进、承诺待兑现和已结清记录，并返回原事项；
5. 合同与资料页能否清楚呈现合同当前金额、价款调整、收付款节点、质保／担保和资料缺口；
6. 经营全貌能否在不增加首屏噪音的情况下，让用户展开查看“为什么能开票／结算／付款”；
7. 协作方页能否区分企业、组织、班组和个人，并显示合同、范围、资质材料及候选付款路径；
8. 收付台账能否按预付／进度／结算／质保／最终结清和普通状态筛选，而不把票、义务和资金混为一条记录；
9. 一笔已结清和一笔多批在途业务能否在同一模型中复述，并在桌面与手机上保持清晰。

第一轮已落入本地原型：经营全貌增加“合同边界 → 履约／计量 → 收付循环”三阶段；经营台账增加履约计量／验收依据；协作关系增加承接范围、合同或依据、资质／名册状态；“预算与结算”更名为“履约与结算”；示例 Excel 同步增加相同业务节点。上述实现仍是验证表达，不代表第 1～9 项已经获得客户确认。

## 9. 明确不在本轮形成的结论

- 不确认客户属于哪一种资质序列、合同模式或政府采购路径；
- 不确认下游是专业分包、劳务分包、企业协作还是自然人班组；
- 不确认开票等于履约完成、验收通过或应收成立；
- 不确认管理费、税费、质保金、工资专户和人员代发的适用规则；
- 不确认任何法律或财税结论；
- 不把行业研究直接变成数据库字段、自动流程或客户必须使用的页面。

## 10. 2026-10-11 一期 MVP 期限、提醒与入口补充

当前产品访谈进一步收口：OMS 一期只登记已经实际发生的开票、收票、回款和支付，显示当前余额以及超额开票、超额收票、超额回款、超额支付等异常。项目不维护工程进度；当前也不要求应收／应付期限，不判断逾期，不生成催收任务或自动提醒。此前原型中的“待跟进／承诺待兑现”和跨事项催收工作面继续作为后续候选，不进入当前第一版交付范围。

对现有小系统的核对结果是：Money Flow 已经实现基于 current Obligation `due_on` 的逾期／账龄只读投影，但人工义务当前要求 `due_on` 必填，账龄规格明确不包含催收流程和自动通知。这意味着现有余额、实际资金、Allocation、冲销与账龄能力可以保留，但不能直接宣称已经支持本次“无固定期限”的 OMS，也不能为了接入而填写虚假到期日。

后续待开发项保留为独立兼容增量：

1. 区分无固定期限、明确合同期限、条件触发和其他期限依据；
2. 使用追加式事实记录客户承诺、跟进结果和下一次跟进，不覆盖义务或实际资金；
3. 在规则得到确认后再增加可选提醒／通知，不从未回余额自动推断逾期；
4. 保持旧 `due_on`、Expectation、API、历史、审计、导出和恢复语义兼容。

第一版确认保留登录，但账号开通和部署形态尚待会议确认。现有可用基础包括 Money Flow 本地单管理员账号／登录，以及完整组合的 Gateway／正式 IAM；会议可在“预置一个本地默认管理员”和“通过后台／既有 IAM 注册账号”之间选择，不采用免登录默认账号。单应用本地验证可以暂不经过 Nginx／Gateway，但仍须使用同形本地 Provider；完整公网组合仍以 Nginx 为唯一公网入口。会议确认前不修改 IAM、Gateway、Nginx、数据库或部署配置。
