# 第 16 轮：Party Directory 与“独立运行”的依赖边界

日期：2026-09-25

## 问题

此前把“小应用能够独立运行”过度解释为业务应用不应依赖任何辅助业务应用，因此 Contract Ledger 与 Money Flow Ledger 分别保留了自己的轻量 Party 目录。随着两个台账实现和参考 OA 装配完成，需要重新验证这种重复是否仍有利于解耦。

## 现有证据

Contract 与 Money Flow 已分别实现独立的 `parties` 表、organization／individual 类型、法定名称、可选登记标识、revision、登记、列表和审计。Money Flow 额外具有 Command ID 幂等保护，但两者表达的当前主体档案语义一致。

两个业务应用都没有把 Party 当前资料当作历史真相。合同激活、结算、义务确认、实际收付款和内部转账会冻结 Party ID、revision、类型、名称与登记标识，因此目录独立后仍须保留业务本地快照。

参考 OA 提供了第三种装配证据：我方、甲方和资质单位是现实主体，但该客户要求隐藏甲方／资质单位独立管理入口，把名称保存到项目并使用历史名称行内自动补全。这个事实证明管理界面是否暴露属于客户装配差异，不证明主体边界不存在。

## 边界判断

应用独立性以可独立交付的产品边界衡量，不以零依赖或单进程衡量。一个 Contract 产品可以由 Nginx、Gateway、IAM、Party、Evidence 和 Contract 共同构成，只要依赖被显式声明、使用版本化契约、具有独立数据所有权并通过组合故障验收。这里的“核心／辅助”只描述本次组合中的角色，不构成应用的永久等级。

Party 已具备两个稳定使用点和清楚的独立 A→B：多个业务应用重复维护同一交易主体 → 在一个可单独管理和复用的目录中获得稳定主体身份与当前资料。Party 因此进入目标应用组合；它可以由需要主体管理的客户直接选择，也可以作为其他领域产品的显式依赖被携带。

消费 Party 的业务应用不把自身角色交给 Party。签约方、债权方、债务方、甲方、资质单位等角色都由发生该事实的业务应用拥有；Party 只拥有跨业务一致的主体身份和当前档案。历史事实继续保存 Party revision 和不可变快照。

## 未采用的候选方案

### 每个业务应用永久内置 Party

该方案保持最少运行服务，但新增业务应用会继续复制主体登记、revision、审计和迁移，并产生多个 Party ID 的长期映射问题。已有两个稳定实现点后，重复开始制造可预见耦合。

### 所有应用共享 Party 表

该方案减少接口调用，但会破坏数据库写入权、独立 migration、备份恢复和故障隔离，不符合已接受的数据边界。

### Party 只作为不可见技术组件

该方案不能覆盖客户直接管理客户、供应商或合作单位的场景。Party 是可独立使用的领域应用，其界面是否显示由客户装配决定。

## 仍需后续设计的问题

- Party v1 当前档案的最小字段、名称历史和停用语义；
- 组织、个人、租户所属主体和外部主体之间的最小关系；
- Contract 与 Money 现有 Party ID 的迁移、合并和冲突处理；
- Party 不可用时，查询历史和创建新业务事实的精确失败行为；
- OA 自由文本与 Party 引用的兼容方式；
- Party 独立管理所需 Capability、备份恢复和交付验收。

这些问题在 Party 实现规格中解决，不通过共享表或临时双写绕过。
