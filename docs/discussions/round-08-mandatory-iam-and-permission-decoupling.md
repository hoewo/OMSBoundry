# 第 8 轮：强制 IAM 契约与业务权限解耦

日期：2026-09-20  
状态：IAM 强制边界已进入讨论基线；权限契约细节仍待设计和验证

## 本轮要解决的问题

每个小应用都需要可信身份和权限，但如果直接把客户岗位、页面和按钮名称写进业务代码，合同或台账应用会被客户组织结构深度绑定。另一方面，如果允许关闭鉴权，小应用的接口、审计和上线形态会出现两套不可等价的安全路径。

本轮需要同时满足：IAM 是正式访问的强制入口；没有外部 IAM 的客户和独立测试仍能使用小应用；客户角色和页面差异不会侵入稳定业务内核。

## 已确认原则

1. 所有受保护访问都必须提供符合版本化契约的 IAM 上下文；缺少上下文的请求不能进入业务用例。
2. 标准生产装配使用正式 IAM 提供者。测试环境可以使用测试提供者；客户明确不接外部 IAM 时可以显式配置本地模板提供者。
3. 测试提供者和本地模板提供者必须产生与正式 IAM 同形、可校验、可审计的身份上下文，不能实现为跳过鉴权。
4. 系统不存在 `auth disabled` 运行模式。公开健康检查等少数端点使用显式允许清单，而不是默认公开。
5. IAM 是可独立建设和管理的平台应用，不归入文件、通知等纯功能“基础能力”杂项。
6. 业务应用只依赖 IAM 契约，不读取 IAM 数据库，也不导入某个 IAM 产品的内部用户或角色模型。

## 最小根因

IAM 契约的 A→B：

> 多个小应用各自解释登录身份会产生不一致和审计缺口 → 每次受保护访问都获得统一、可信且可追溯的访问者上下文。

权限解耦的 A→B：

> 客户岗位、页面和按钮不断变化会迫使业务代码跟着定制 → 小应用只定义稳定业务动作，由 IAM 配置角色与动作的映射，由业务应用结合当前数据作最终授权。

## 角色、能力与业务规则分层

权限采用三层责任，不把三者混成一个“按钮权限表”：

| 层级 | 负责内容 | 示例 |
| --- | --- | --- |
| IAM | 用户、租户、角色、角色到能力的授权关系 | “甲公司的合同经办人拥有 `contract.create`” |
| 业务应用 | 稳定能力目录、资源范围与当前业务状态校验 | “终止合同不能再登记补充协议” |
| 客户装配／前端 | 菜单、页面、按钮的显示与操作入口 | “没有 `contract.revise` 时隐藏修订按钮” |

客户可以定义“经营经理”“法务负责人”“项目管理员”等任意角色名称，但 Contract Ledger 不根据这些名称写条件。它只识别自身发布的稳定能力，例如：

- `contract.read`；
- `contract.create`；
- `contract.revise`；
- `contract.terminate`；
- `contract.settle`；
- `contract.export`。

角色是可配置组合，能力是应用公开契约。客户更改岗位名称或重新组合职责时，只修改 IAM 授权关系，不修改 Contract Ledger 代码。

## 页面按钮如何处理

页面按钮不是安全边界，也不成为权限命名来源。推荐流程是：

1. Contract Ledger 根据 IAM 授权、资源归属和合同当前状态计算 `allowed_actions`；
2. 前端根据 `allowed_actions` 隐藏或禁用相应入口；
3. 用户发出命令时，服务端再次执行同一业务动作授权；
4. 缺少身份返回未认证，身份有效但动作不允许返回拒绝，并记录授权结果与可信 Actor。

因此，`contract.revise` 只是必要条件，不是最终结果。即使用户具有该能力，合同已经终止、资源不属于当前租户、expected revision 失效或需要的业务证明不存在时，Contract Ledger 仍可拒绝修改。

禁止使用 `contract-page.button-7.visible` 一类页面位置作为稳定权限键。相同的合同修订动作无论来自按钮、API、导入还是客户装配页面，都必须经过同一个 `contract.revise` 服务端门禁。

## 候选细化：把外部业务权限收敛为应用可读凭证

用户提出的“层层包装”可以表达为能力凭证：项目成员、组织岗位、数据范围、客户策略和其他前置权限由 IAM 或受信任策略服务组合判断，最终收敛成目标小应用能够理解的授权结果。目标应用不需要知道获准的外部业务理由，只校验这张凭证是否允许当前身份对当前资源执行当前动作。

示例流程：

```text
普通员工请求查看某条台账
  → 上层判断其公司、项目成员关系、岗位与数据范围
  → IAM／策略服务签发“允许读取台账记录 42”的短期凭证
  → Money Flow Ledger 校验签发者、租户、目标应用、动作、资源和有效期
  → Money Flow Ledger 再校验记录 42 的本地归属与业务状态
  → 返回数据或明确拒绝
```

凭证至少需要绑定：

- 可信签发者和决策标识；
- 访问主体与租户；
- 目标应用 audience；
- 应用已发布的稳定 action；
- 明确资源或受限资源范围；
- 签发、过期和必要的撤销信息；
- 高风险写入需要时绑定 Command ID、Expected Revision 或请求摘要，防止凭证被换请求或重复使用。

该模型允许 Money Flow Ledger 不理解“普通员工必须先有项目查看权”这类外部组合规则，但不能让它放弃自身业务判断。外部凭证可以证明 `obligation.adjust` 已获授权，却不能允许应用原地覆盖不可变义务、修改其他租户数据、绕过关闭状态、忽略金额精度或跳过并发版本检查。

应用能力也不宜退化成数据库 CRUD。对于不可变台账，`ledger.row.update` 含义过宽；稳定 action 应使用 `obligation.read`、`obligation.adjust`、`cash.record`、`allocation.apply`、`ledger.export` 等业务动作。这样上层可以自由组合授权原因，小应用仍保持清晰、可审计的领域边界。

能力凭证只能由受信任 IAM／策略服务签发，浏览器和项目页面不能自行组装权限。列表查询还需要明确范围，不能只给一个无边界的 `read`；可以使用限定本方账簿、资源集合或可验证查询范围的凭证。短期离线可验证凭证可以降低每次访问都同步调用 IAM 的运行耦合，但有效期、撤销和 IAM 故障时的行为仍需专门设计。

## IAM 提供者模式

业务应用面对同一个 IAM Port，部署时选择提供者：

| 模式 | 用途 | 边界 |
| --- | --- | --- |
| 正式 IAM 提供者 | 标准生产装配 | 校验正式 IAM 凭据并形成可信上下文 |
| 本地模板提供者 | 客户明确不接外部 IAM | 使用显式配置的模板身份与授权集，仍经过完整鉴权和审计 |
| 测试提供者 | 自动化和独立测试 | 只能在测试边界启用，不能进入正式生产配置 |

本地模板不是万能管理员旁路。它必须明确租户、主体、能力集和审计标识；系统启动时记录当前提供者模式。测试提供者出现在正式环境时必须拒绝启动。

## 网关与 IAM 的关系

网关可以提前校验令牌并把请求路由到业务应用，但网关不拥有合同或台账的业务授权结论。业务应用只能接受可验证的 IAM 令牌或受信任断言，不能相信客户端自行提交的用户、角色和权限 Header。

网关回答“请求来自谁、送到哪里”；IAM 管理“这个身份原则上拥有哪些能力”；业务应用回答“对当前这条业务事实能否执行该动作”。

## 接口强制性

目标接口需要满足以下门禁：

- 受保护命令和查询的应用用例都接收不可为空的访问者上下文；
- 未形成可信上下文时不能构造业务 Actor；
- 每个非公开 HTTP 端点显式声明所需能力或调用统一授权门禁；
- 自动化检查能够发现没有声明授权边界的新端点；
- 前端隐藏按钮不能替代服务端校验；
- IAM 提供者切换不能改变合同 revision、义务、资金、核销或审计语义。

## 当前实现差距

Contract Ledger 和 Money Flow Ledger 当前各自使用本地身份实现；Contract 还使用固定 `administrator`、`editor`、`viewer` 角色。它们已经证明可信 Actor、服务端授权和不可变审计边界，但尚未实现本轮目标 IAM 契约、可版本化能力目录、正式／模板／测试提供者切换和按资源返回 `allowed_actions`。

现有本地身份属于可迁移的运行事实，不自动视为目标 IAM 方案已经完成。

## 尚待确认

- IAM 上下文采用离线可验证令牌、在线校验还是受签名保护的网关断言；
- 身份上下文与能力授权是否分开获取，以及 IAM 不可用时的有效期和降级边界；
- 组织、项目、本人负责和指定资源等授权范围采用什么稳定表达；
- 能力目录如何注册、版本化、弃用和与 IAM 同步；
- `allowed_actions` 放入资源响应还是使用独立查询接口；
- 现有固定本地角色与会话如何迁移且不破坏历史 Actor 和审计。
