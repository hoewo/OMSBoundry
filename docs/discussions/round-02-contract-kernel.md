# 通用商务业务与模块基建讨论：第 2 轮——合同内核

日期：2026-09-19  
状态：候选设计，不是现有项目规格，不包含代码实现

关联文档：[第 1 轮：总体业务与模块拆分](./round-01-contract-income-expense-foundation.md)

## 本轮主要结论

1. 合同系统的通用核心不是“合同表单”，而是**签约主体快照、不可变合同事实、按确定顺序生效的变更、可重放金额演算和合同关系**。
2. 上游合同、资质合作、设计合同、施工合同等都应是独立合同，通过有向关系连接；不能把政府工程的固定角色链写成枚举，也不能把下游合同塞进上游合同聚合。
3. 已签署/生效的合同和变更不能直接编辑或删除。发现错误或再次变化时，应追加更正、替代、终止或结算事实。
4. 合同只提供金额依据，不直接产生应收、应付、发票或现金。是否由合同里程碑生成义务，应由客户装配策略决定。
5. 下游模块引用的不是“合同当前值”，而是 `contract_id + revision + amount_basis`。这样合同后续变化不会静默改写历史应收、审批或统计。
6. 第一阶段仍建议模块化单体，但合同域必须拥有自己的数据、命令、查询和事件契约，其他模块不得跨边界直接改表。

## 一、现实中的候选通用合同流程

### 1. 签约准备

- 建立合同草稿，选择或新建签约主体；
- 记录合同编号、标题、合同类型、币种、金额组成、关键日期和附件；
- 可以关联项目、订单、案件、年度合作等业务上下文，但这些上下文不是合同存在的前提；
- 草稿阶段允许修改或取消，不形成正式合同事实。

招投标、商机、客户跟进和内部报价属于合同前置业务，可以与合同系统组合，但不进入最小合同内核。

### 2. 签署与生效

- 记录实际签署主体、各方在本合同中的角色、签署日期和签署文件；
- 冻结签署时的主体名称、证件/登记标识和代表信息快照，避免主体资料后续修改破坏历史；
- 区分签署日期、生效日期和履约期间；三者不能被一个 `sign_date` 替代；
- 激活后形成合同第一个不可变 revision，并发布可供其他模块引用的合同快照。

是否需要签署审批、用印审批或法务审查由可选决策门禁控制，不写入合同状态机。

### 3. 建立合同关系

现实中同一工程可能同时存在甲方合同、资质合作合同、设计合同、施工合同、劳务合同和采购合同。通用系统不预设固定层级，而是记录合同之间的有向关系，例如：

- 资金来源或上游依据；
- 履约委托或分包；
- 框架合同与具体合同；
- 替代、续签或引用。

每份合同仍独立维护自己的主体、金额、变更和生命周期。上游合同变化不应自动改写下游合同。

### 4. 履约与依据引用

- 里程碑、验收、计量、交付物、批复和审计可以作为履约或结算依据；
- 合同内核只保存稳定的外部引用和必要快照，不承担完整施工、设计或生产过程；
- 外部依据发生变化时，不反向覆盖已经基于旧版本形成的合同或收支事实。

### 5. 合同变更

每个生效变更至少记录：

- 变更编号和法律文件；
- 签署日期、生效日期和明确顺序；
- 变更说明；
- 对金额、日期、主体、范围或其他条款的影响；
- 生效后的合同 revision。

金额变化至少支持三种稳定语义：

- **调整**：在当前有效金额上增加或减少；
- **重述**：用新金额替代此前有效金额；
- **不影响金额**：只改变其他合同条款。

同一天存在多个变更时，不能使用数据库创建时间决定法律顺序，必须有显式生效顺序或能够证明的生效时间；顺序不明时应进入待确认状态。

### 6. 结算

- 当前有效合同金额表示合同条款演算结果；
- 结算金额表示履约后确认的最终计价结果；
- 二者可以相同，也可以不同，必须分别保留；
- 结算应记录依据、日期、版本和确认主体，不能只是合同表上的一个可随意覆盖字段。

结算是否直接生成应收或应付，由合同与收支之间的装配策略决定，不属于合同内核。

### 7. 终止、到期与关闭

- 未激活草稿可以取消；
- 已激活合同的解除、终止、到期和结算是追加事实，不能执行物理删除；
- 合同关闭只表示不再接受普通业务变更，历史查询、纠错和审计仍然存在；
- 已关闭合同如需纠错，使用专门的更正记录，不重新打开后直接改历史。

## 二、最小产品模型

### 1. Contract：合同根对象

只保存稳定身份和生命周期控制：

- 合同 ID；
- 编号命名空间和合同编号；
- 标题与通用分类；
- 当前 revision；
- 最小状态；
- 创建、激活、关闭等审计信息。

合同编号不应全系统全局唯一。更稳妥的唯一范围是“租户/组织 + 编号命名空间 + 合同编号”。

### 2. Contract Party Snapshot：签约主体快照

- 外部主体目录引用；
- 签约时法定名称和登记标识快照；
- 该主体在本合同中的角色；
- 签署代表等必要历史信息。

“甲方、资质单位、设计方、施工方”是某次合同关系中的业务角色，不是系统权限角色，也不是通用表结构中的固定列。

### 3. Contract Instrument：合同法律事实

建议把原合同、补充协议、重述协议、终止协议和结算确认视为同一合同时间线上的不同法律文书/事实，但由类型化行为处理，不做无约束万能记录。

每个生效 Instrument：

- 不可变；
- 有独立 ID、业务编号、签署和生效时点；
- 引用证据文件；
- 指明产生的条款变化；
- 产生新的合同 revision。

草稿 Instrument 可以修改；激活后只能被后续 Instrument 更正或替代。

### 4. Amount Terms：金额条款

通用金额模型只保留：

- 精确十进制金额与币种；
- 总额；
- 可选的分类明细；
- 尚未分类金额；
- 变化语义：调整、重述、不变；
- 当前有效额与最终结算额。

设计费、勘察费、咨询费、管理费等都应是客户可配置或扩展的分类 code，不是合同内核固定字段。

关键规则：

- 金额使用 decimal 或最小货币单位，不能使用二进制浮点数；
- 总额可以先于分类明细确定，差额进入“未分类”，不能丢失历史数据；
- 币种转换、汇率损益、税额和会计处理不属于合同内核；
- 当前有效额由原始条款和全部已生效变更重放得出，衍生汇总不是第二真相源。

### 5. Contract Relation：合同关系

- 来源合同 ID；
- 目标合同 ID；
- 关系类型；
- 生效期间；
- 可选分配或覆盖说明；
- 审计信息。

关系是独立边，不是下游合同的父对象。对“主从”类型关系可限制成无环；引用、续签等其他关系不应被强制套入树结构。

### 6. Context Reference：业务上下文引用

合同可以关联零到多个外部上下文：项目、项目包、订单、客户案件或外部系统对象。引用采用：

```text
context_type + context_id + relation_role
```

合同模块不依赖某个具体 Project 实体，也不通过复制合同事实满足父子项目展示。

### 7. Evidence Reference：证据引用

合同内核只保存证据引用、用途、版本和内容校验信息。文件二进制、预览、病毒扫描和保留策略由文件系统负责。

## 三、最小状态模型

通用状态应保持少而稳定：

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `draft` | 尚未形成正式合同事实 | 修改、取消、提交门禁、激活 |
| `active` | 至少一个正式合同 Instrument 已生效 | 追加变更、结算、终止、关闭 |
| `closed` | 常规履约与变更结束 | 查询、审计、追加受控更正 |
| `cancelled` | 草稿未生效即取消 | 查询审计，不可激活 |

签署、生效、暂停、恢复、到期、解除、终止和结算等法律/业务时点优先保存为时间线事实，不继续膨胀一个状态枚举。合同当前展示状态可由这些事实投影得出。

## 四、合同与其他系统的边界

### 合同系统拥有

- 签约主体历史快照；
- 合同原始事实、revision 和变更时间线；
- 当前有效条款与金额演算；
- 结算事实；
- 合同间关系；
- 业务上下文和证据引用。

### 合同系统不拥有

- 商机、投标和客户跟进全过程；
- 设计、施工、劳务或采购履约明细；
- 应收、应付、发票、收款、付款和核销；
- 会计、税务和银行执行；
- 审批步骤与组织角色；
- 文件二进制；
- 客户页面和行业固定字段。

## 五、代码层最小结构

### 1. 模块分层

```text
contract-domain
  合同聚合、值对象、不变量、金额演算、领域事件

contract-application
  命令用例、幂等、并发版本检查、端口编排

contract-ports
  主体、证据、权限、可选决策门禁、事件发布接口

contract-projection
  当前合同快照、时间线、关系统计等只读模型
```

避免建立包含全部业务对象的巨大 `common-domain`。共享层只保留 ID、精确 Money、时间和幂等等极少数真正稳定的值对象。

### 2. 最小命令契约

| 命令 | 主要结果 |
| --- | --- |
| `CreateContractDraft` | 创建可编辑草稿 |
| `UpdateContractDraft` | 在激活前修改草稿 |
| `ActivateContract` | 冻结主体与原始条款，生成 revision 1 |
| `AppendContractChange` | 追加已生效变更并生成新 revision |
| `RecordContractSettlement` | 记录结算事实与结算依据 |
| `LinkContracts` | 建立有类型的合同关系 |
| `CloseContract` | 结束常规业务变更 |
| `CorrectContractFact` | 用受控更正追加修正，不覆盖历史 |

所有写命令至少携带：

- `command_id` 或幂等键；
- `actor`；
- `expected_contract_revision`；
- 业务发生时间；
- 命令负载；
- 可选的门禁证明。

并发版本不一致时拒绝写入，调用方重新读取后决定，不做最后写入覆盖。

### 3. 最小查询契约

- `GetContractSnapshot(contract_id, as_of?)`
- `GetEffectiveTerms(contract_id, revision|as_of)`
- `ListContractTimeline(contract_id)`
- `ListContractRelations(contract_id)`
- `SearchContracts(filters)`

命令模型与查询模型分开；列表和统计不要求加载完整合同聚合。

### 4. 最小事件契约

- `ContractActivated`
- `ContractChangeActivated`
- `ContractSettlementRecorded`
- `ContractRelationLinked`
- `ContractClosed`
- `ContractFactCorrected`

事件必须包含：合同 ID、产生后的 revision、发生时点、事件 ID 和必要的合同快照引用。事件描述已经发生的事实，不包含“点击保存”“财务经理审批”等界面或客户角色语义。

## 六、可选审批如何接入

审批属于 application orchestration，不属于合同聚合内部状态。

候选流程：

```text
合同命令
  → 形成 ProposedChange（合同版本 + 负载哈希）
  → DecisionGate 判断：无需审批 / 待审批 / 拒绝
  → 无需审批则立即执行
  → 待审批则由审批系统保存申请和快照
  → 审批通过后携带 proof 重新执行原命令
  → 合同版本或负载已变化则 proof 失效
```

这样客户可以完全不部署审批系统，也可以只审批合同激活、重大变更或结算。审批系统发生故障不会污染合同历史，审批通过也不会自行修改合同表。

## 七、与收支系统的关键契约

收支系统生成应收或应付时，应保存不可变来源引用：

```text
ContractSnapshotRef
  contract_id
  contract_revision
  amount_basis       # original / effective / settlement / component
  component_code?    # 可选分类
  effective_at
```

同时复制本次义务实际采用的金额和币种。后续补充协议只会产生新的合同 revision，不会自动修改旧义务。

如果客户希望合同变化自动调整应收，应由装配策略显式生成一笔“义务调整”，保留新旧来源和差额；不能让报表在查询时直接用最新合同额覆盖历史。

## 八、从 OA 提取的经验与反例

| OA 现状 | 通用层判断 |
| --- | --- |
| 原合同、调整、重述、不改金额按顺序演算 | 保留，是稳定内核能力 |
| 当前有效金额与结算金额分离 | 保留，但结算应成为有依据的事实 |
| 同日变更按创建时间和 ID 排序 | 不保留，改为明确业务顺序 |
| 合同强制属于 Project | 不保留，改为可选 Context Reference |
| 固定两段业务链枚举 | 不保留，改为合同关系和合同内 party role |
| 固定设计/勘察/咨询费字段 | 不保留，改为可配置金额分类 |
| 金额使用 `float64` | 不保留，使用 decimal/最小货币单位 |
| 生效补充协议可编辑、删除 | 不保留，生效后只能追加更正或替代 |
| `supplementary_amount` 等衍生总额落库兼容旧页面 | 只可作缓存投影，不能成为真相源 |
| 项目权限与站点权限分离 | 保留原则，但合同内核只调用通用授权端口 |
| 批复记录复制合同金额并保留 source ID | 方向正确；还需补充 source revision 和 amount basis |

## 九、本轮暂定的“最小可复用合同小系统”

第一版只做：

1. 合同草稿与激活；
2. 多签约主体及签署快照；
3. 精确金额、可选分类和币种；
4. 不可变变更时间线与金额重放；
5. 当前有效金额和结算事实；
6. 合同关系与外部上下文引用；
7. 文件证据引用；
8. 权限、审批和事件端口；
9. 当前快照、历史版本和时间线查询。

先不做合同模板编辑器、全文条款解析、电子签章、智能审查、完整履约管理和会计集成。它们都可以通过独立模块接入。

## 下一轮建议

第 3 轮进入经营收支内核，重点确定：

- 应收/应付义务的最小模型；
- 发票与义务、资金之间的关系；
- 多笔对多笔核销；
- 调整、冲销、坏账和关闭；
- 账龄、余额和现金预测如何全部从明细事实投影；
- 如何消费 `ContractSnapshotRef`，又不依赖合同模块才能独立运行。

## 本轮仍然开放的问题

- 第一版是否只允许单合同单币种；
- 合同关系类型采用内置最小集合还是完全由装配层注册；
- 结算是一个合同级最终事实，还是需要支持分阶段结算；
- 哪些主体信息必须在签署时冻结；
- 合同生效和结算的审批证明是否需要进入长期审计包；
- 是否允许对已激活事实做“技术性更正”，以及相应授权等级。
