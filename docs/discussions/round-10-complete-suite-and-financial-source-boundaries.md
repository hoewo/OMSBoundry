# 第 10 轮：完整组合、人员管理与收支来源边界

日期：2026-09-20  
状态：已进入当前讨论基线；除 Contract Ledger 与 Money Flow Ledger 外均为目标设计，尚未实现

## 本轮要解决的问题

在已经确认小应用独立边界之后，第一阶段不能只得到若干互不相连的后台服务，还需要形成一套可以安装、登录、操作和演示的完整系统。同时需要回答：Gateway 是否进入正式组合、登录注册与人员管理分别归谁，以及奖金、报销和合同外收支是否都应该进入 Money Flow Ledger。

## 核心结论

第一目标改为交付一个 **Complete Suite 0.1**：在一台 ECS 上可重复安装，具有统一入口、账号生命周期、人员目录、项目容器、合同、经营收支、文件证据和统一工作台，并能通过部署配置启用或停用可选应用。

“完整”表示从登录到业务操作、数据保存、审计、备份和恢复形成闭环，不表示一次覆盖所有 OA、财务、人事和行业业务。

## 组件清单与最小根因

| 组件 | 类别 | 最小根因 A→B | Complete Suite 0.1 |
| --- | --- | --- | --- |
| Gateway | 边缘装配组件 | 多个应用各自暴露入口和通用访问规则 → 对外形成一个稳定、安全、可观测的入口 | 默认启用；单应用开发和独立交付可绕开特定 Gateway 产品 |
| Identity & Access | 平台应用 | 系统不知道访问者是谁、能做什么 → 每次受保护访问获得可信身份和能力凭证 | 强制，不能关闭 |
| Organization & People | 业务基础应用 | 员工、部门和任职关系散落且无法稳定引用 → 得到一份当前组织人员名册及可追溯身份关联 | 默认启用，可按独立交付组合省略 |
| Project Workspace | 可选业务应用 | 同一项目的合同、收支和资料散落 → 从项目入口组织、查看并操作这些记录 | 演示组合启用，客户组合可关闭 |
| Contract Ledger | 业务应用 | 合同不断补充和修改 → 随时知道当前按哪份约定办事以及为什么 | 可配置启用 |
| Money Flow Ledger | 业务应用 | 应收应付与实际收付款容易混在一起 → 随时知道该收付、已收付和剩余金额 | 可配置启用 |
| Evidence Service | 基础能力应用 | 多个应用分别处理文件会产生重复、安全和追溯差异 → 提供统一、版本化、可校验的文件保存与受控读取 | 完整组合启用；独立应用可使用本地提供者 |
| Unified Workbench | 前端装配组件 | 多应用入口割裂、用户难以连续操作 → 用户从一个界面进入已启用应用并完成跨应用旅程 | 默认启用 |

Gateway 由此成为正式产品组合中的一等装配组件，但不拥有业务事实，也不是所有小应用的代码依赖。第一版可以由 Nginx 或成熟轻量网关实现；只有实际出现统一 API Key、复杂配额、协议转换等需求时，才增加更完整的 API Gateway 能力。

## 登录注册与人员管理必须分开

Identity & Access 拥有：

- 租户和账号；
- 登录、注销、邀请、激活、密码重置和会话；
- 角色到稳定业务能力的授权；
- 短期身份上下文和能力凭证；
- 账号安全与身份审计。

企业系统中的“注册”默认不是匿名用户随意加入公司，而是首个租户管理员建立、管理员邀请、受邀人激活账号的完整账号生命周期。是否开放公共自注册是部署策略，默认关闭。

Organization & People 拥有：

- 员工或成员档案；
- 部门、团队、岗位和任职状态；
- 人员与 IAM Subject 的可选一对一或受控关联；
- 人员和组织关系的历史变化。

它不保存密码、会话或角色授权，也不把“部门经理”等岗位名称直接变成业务权限。一个 IAM 账号可以暂时没有人员档案，人员也可以因为未开通系统账号而没有 IAM Subject。Contract、Money Flow 等业务应用只保存必要的 Person Reference 和当时快照，不直接读取人员数据库。

Organization & People v1 明确不包含工资、奖金计算、考勤、绩效和招聘流程；这些对象各有不同生命周期，不能因为都与“人”有关就塞入人员目录。

## 台账与奖金、报销、合同外收支的关系

Money Flow Ledger 只回答三类问题：

1. 已经确认应该收或付多少钱；
2. 实际已经收或付了多少钱；
3. 哪笔实际资金核销了哪项义务，还剩多少。

它不回答“为什么批准这笔钱”以及“这笔钱应当如何计算”。因此：

| 场景 | 业务事实所有者 | Money Flow 的职责 |
| --- | --- | --- |
| 没有合同的临时应收／应付 | 人工录入或外部来源 | 直接建立带来源快照的义务 |
| 没有先行义务的实际收款／付款 | 银行、人工或外部来源 | 登记资金，保持未分配，之后可以核销 |
| 员工报销 | 可选 Reimbursement 应用拥有申请、明细、票据、审批和退回 | 报销被确认后接收“应付给谁、多少钱”的义务建议或人工确认 |
| 奖金分配 | 可选 Bonus／Compensation 应用拥有方案、计算、分配、确认和撤销 | 方案确认后接收一条或多条应付义务建议 |
| 合同结算 | Contract 拥有合同与结算事实 | 经定向连接器建议建立或调整应收／应付，不直接改台账 |

所以“合同外收支”不需要因为没有合同就新建一套台账。只要需求是记录应收、应付、收款、付款和余额，现有 Money Flow 已能承接；一旦需求包含申请、审批、计算、分摊、票据校验或特定撤销规则，就属于产生资金义务的业务来源，应以独立可选应用或客户装配实现。

报销、奖金等来源应用都只能通过版本化来源快照和义务建议与 Money Flow 交互。Money Flow 自己确认并保存义务；来源应用不能直接写它的数据库。来源应用停机时，已经确认的台账事实继续可查询、核销和纠错。

Money Flow 也不是会计总账：它当前不自动形成收入确认、成本费用、利润、税务分录或法定财务报表。是否增加会计应用，必须取得独立 A→B 和真实会计口径后再决定。

## 应用开关不是运行时删除按钮

Complete Suite 使用一个版本化部署清单声明已安装和启用的应用。第一版不建设独立配置中心。开关产生以下确定结果：

- Gateway 不再暴露该应用的外部路由；
- Workbench 不再显示该应用菜单和跨应用入口；
- 依赖该应用的连接器暂停，不伪造成功；
- 部署工具可以不启动该应用进程；
- 已有数据库和文件保持不变，关闭应用不等于删除数据；
- 重新启用前执行版本、migration、健康检查和权限目录校验。

IAM 是唯一不可关闭的逻辑契约。Complete Suite 安装正式 IAM；单应用测试或客户明确不部署中心 IAM 时，仍必须由同形本地模板提供者满足契约，不允许 `AUTH_DISABLED`。

应用依赖由部署清单校验。例如启用独立 Evidence Service 时必须配置存储和引用契约；关闭 Project 不影响 Contract 与 Money Flow；关闭 Contract 后 Project 不能显示合同操作入口，但已有项目本身仍可工作。

## Complete Suite 0.1 的演示闭环

第一版演示至少证明：

```text
创建首个企业与管理员
  → 邀请并激活一个账号
  → 建立员工档案并关联账号
  → 建立项目
  → 从项目页面创建并查看合同
  → 人工建立一笔合同外应付或应收
  → 登记实际收款或付款并完成核销
  → 上传并读取相关证据文件
  → 按配置关闭 Project 或 Contract 菜单
  → 其余已启用应用继续工作且数据不丢失
  → 完成备份并在空环境恢复
```

这条闭环足以证明系统“全而可用”，但不把报销审批、奖金计算、会计总账、薪资、考勤或行业流程伪装成已经完成。

## 推进顺序

1. 先完成 Suite Manifest、Gateway 最小入口、Workbench 壳和 IAM 账号生命周期，迁移现有应用到统一 IAM 契约；
2. 完成 Organization & People 最小名册及 IAM Subject 关联；
3. 完成 Project Workspace 最小闭环；
4. 完成 Evidence Service 与本地提供者兼容；
5. 以既有 Contract、Money Flow 和新增组件完成一台 ECS 的 Complete Suite 0.1 验收；
6. Reimbursement、Bonus／Compensation 和会计能力等待真实业务案例，按独立 A→B 决定是否进入后续应用组合。

## 仍然开放

- Gateway 第一版采用纯 Nginx、成熟轻量网关还是少量自研控制面的边界；
- 邀请、账号激活、密码重置和租户建立的准确安全契约；
- Organization & People v1 的最小组织层级、任职历史和离职处置；
- Suite Manifest 的格式、依赖校验、配置来源和升级兼容；
- Workbench 使用服务端渲染组合还是独立 SPA；
- IAM 暂时不可用时，既有短期凭证的有效期、撤销和失败策略；
- 是否以及何时用真实报销或奖金案例建立第一个非合同业务来源应用。
