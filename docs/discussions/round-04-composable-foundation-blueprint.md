# 通用商务业务与模块基建讨论：第 4 轮——可组合小系统蓝图

关联文档：

## 本轮主要结论

1. 目标不是一个“人人都能用”的大平台，而是一组**事实边界稳定、可独立运行、可组合部署的小系统**。
2. 第一批真正值得做实的是合同台账和经营收支台账；审批、身份权限、文件证据和客户装配层为可选公共能力。
3. 最大解耦不来自微服务，而来自：数据所有权、稳定命令/查询/事件契约、不可变来源快照、端口适配和禁止跨模块改表。
4. 所谓通用，不是字段无限动态化；稳定事实进入内核，客户差异依次放入配置、策略、类型化扩展和装配层。
5. 技术起点应是模块化单体。模块成熟并出现独立扩缩容、合规或团队边界后，再沿既有契约拆成服务。
6. 用设计单位、资质施工综合体和无项目小型服务公司三种组合验证后，合同与 money-flow 均能独立运行，审批也能完全移除，说明当前边界具备通用候选价值。

## 一、候选产品族

### 1. Contract Ledger：合同台账小系统

负责合同主体快照、合同事实、revision、变更演算、结算、合同关系和证据引用。

可以独立使用，不要求部署 money-flow、审批或 Project 系统。

### 2. Money Flow Ledger：经营收支台账小系统

负责应收/应付义务、票据、实际资金、核销、余额、账龄和现金预测。

可以独立使用，来源可以是合同、订单、外部系统或人工依据。

### 3. Decision Workflow：可选审批小系统

为任意业务命令提供决策门禁和审计。它不拥有合同或资金数据，也不直接修改其他模块的表。

### 4. Party Directory：业务主体目录

维护组织与个人的当前资料，供合同和收支引用。正式业务记录仍保存当时快照，不能只依赖主体目录当前值。

### 5. Identity & Access：身份权限能力

负责登录主体、actor、组织范围和业务授权。它与 Party Directory 分离：业务签约方不一定登录系统，登录用户也不一定是合同主体。

### 6. Evidence Store：文件证据能力

负责文件版本、存储、校验、访问和保留策略。业务模块只持有不可变 Evidence Reference。

### 7. Customer Assembly：客户装配包

负责行业术语、菜单页面、流程编排、角色映射、分类字典、特定计算和外部集成。它是客户差异的主要容器，不是新建一套复制内核。

## 二、依赖方向

```text
客户装配层
  页面 / API / 流程编排 / 行业扩展 / 外部集成
                         │
                         ▼
应用用例与过程管理器
  合同用例 / 收支用例 / 可选审批恢复 / 跨模块编排
             │                    │
             ▼                    ▼
      Contract Ledger       Money Flow Ledger
             │                    │
             └────── 公开事件与快照引用 ──────┘

公共端口：Party / Identity & Access / DecisionGate / Evidence / Event Outbox
基础适配：数据库 / 对象存储 / 消息 / 银行 / 发票 / 外部身份
```

约束：

- 领域模块不依赖客户页面、岗位名称和行业流程；
- Contract 不依赖 Money，Money 不依赖 Contract 的内部模型；
- 二者只通过公开事件、查询和 `SourceSnapshotRef` 组合；
- Approval 依赖业务动作快照，但业务域不依赖某个审批产品；
- Customer Assembly 可以编排模块，但不能跨模块直接改数据库。

## 三、最小共享代码层

共享代码必须比想象中更少，只放跨域语义完全一致的值对象：

- `TenantId` / `OrganizationScope`；
- 类型化 `EntityId`；
- 精确 `Money` 与 `Currency`；
- `LocalDate` / `Instant`；
- `ActorRef`；
- `ExternalRef` / `SourceSnapshotRef`；
- `Revision`；
- `IdempotencyKey`；
- 统一事件 Envelope。

不进入 shared kernel：

- Contract、Project、Client、FinancialRecord；
- 客户岗位和权限角色；
- 审批状态；
- 行业费用类型；
- 管理费、奖金和工资规则；
- ORM BaseModel 或包含业务字段的万能父类。

共享层一旦变成“什么都能放”的目录，模块边界会迅速失效。

## 四、公共端口，而不是公共业务实现

### Authorization Port

```text
authorize(actor, operation, resource, context) -> allow / deny
```

合同模块只知道 `contract.activate` 等操作，不知道“经营经理”或“项目负责人”名称。

### Decision Gate Port

```text
evaluate(proposed_change) -> allowed / pending / denied
verify(proof, payload_hash, aggregate_revision) -> valid / invalid
```

没有审批系统时使用 allow adapter；有审批时接 Decision Workflow。

### Party Port

读取当前主体资料并生成业务快照。合同激活或义务确认后不动态追随主体资料变化。

### Evidence Port

保存和读取版本化证据引用。业务模块不感知本地磁盘、MinIO、S3 或其他实现。

### Event/Outbox Port

领域事件与业务事务一致提交。外部消息发送失败可以重试，但不能重复产生业务事实。

### Clock、ID 与 Idempotency Port

使时间、标识和重复请求行为可测试、可替换，并避免导入或网络重试重复记账。

## 五、模块内部与跨模块数据规则

### 数据所有权

| 数据 | 唯一写入者 |
| --- | --- |
| 合同、revision、Instrument、合同关系 | Contract Ledger |
| 义务、票据、现金、核销 | Money Flow Ledger |
| 审批申请、步骤、意见和 proof | Decision Workflow |
| 主体当前资料 | Party Directory |
| 文件内容与版本 | Evidence Store |
| 登录身份和授权关系 | Identity & Access |
| 统计读模型 | 对应 Projection |

### 数据库原则

- 初期允许一个数据库，但每个模块使用独立 schema 或表前缀；
- 模块内可以使用外键，跨模块使用类型化引用，不建立 ORM 对象导航；
- 禁止其他模块直接读取业务表做正式规则判断；
- 跨模块展示通过公开查询或专用读投影完成；
- 不依赖跨模块大事务，使用 outbox、幂等消费和过程状态恢复。

模块化单体中可以同步调用公开用例以获得即时反馈，但不能依赖“大家在同一个数据库里”绕过契约。

## 六、跨模块主流程

```text
1. ContractActivated / ContractSettlementRecorded
2. 客户装配策略判断是否创建义务草稿
3. ConfirmObligation 经过可选 DecisionGate
4. 形成 open 应收或应付
5. 登记票据，建立 Billing Link
6. 登记实际收付款
7. ApplyAllocation 完成多对多核销
8. Projection 更新余额、账龄和现金预测
```

任何一步都不允许直接改上一步的表：

- 合同变化生成新 revision；
- 已生成义务不自动重写，而是由策略建议调整；
- 审批只发 proof；
- 现金只通过 Allocation 改变义务余额；
- 统计只重建投影。

## 七、客户定制的四层放置规则

| 层级 | 判断标准 | 示例 |
| --- | --- | --- |
| 配置 | 只改变名称、显示或简单阈值 | 分类字典、字段显隐、编号前缀、审批金额门槛 |
| 策略 | 改变可替换计算或决策，但不改变核心事实 | 合同生成义务规则、管理费算法、自动匹配规则 |
| 类型化扩展模块 | 拥有独立对象和生命周期 | 奖金、工资、报销、施工计量、设计生产、项目包 |
| 客户装配层 | 改变页面、旅程、角色映射和系统组合 | 菜单、工作台、流程顺序、外部接口 |

只有跨多个真实场景都稳定、并改变通用事实语义的能力，才考虑进入内核。

“完全动态字段 + 完全动态流程”不是通用化，而是把产品责任转移给客户配置和客服团队。

## 八、三个客户组合验证

### 场景 A：设计单位 OA

组合：

- Party + Identity & Access；
- Project/设计生产扩展；
- Contract Ledger；
- Money Flow Ledger；
- Evidence Store；
- 可选合同/付款审批；
- 奖金和外委扩展；
- 设计费、勘察费、咨询费分类配置。

结果：OA 现有的项目、生产、奖金和角色仍可保留为装配与扩展，但合同金额、收付款和票据不再依赖万能 `FinancialRecord`。

### 场景 B：资质单位 + 施工综合体

组合：

- Contract Ledger 的多层合同关系；
- Money Flow Ledger 的上下游应收/应付；
- 施工队/人员名册扩展；
- 管理费策略；
- Payment Intent + 付款审批；
- Evidence Store 和现金预测。

结果：甲方、资质单位、施工方和个人收款对象通过 party、contract relation 和 obligation 表达，不需要修改合同内核表结构或增加固定 chain enum。

### 场景 C：小型咨询或服务公司

组合：

- 只部署 Contract Ledger + Money Flow Ledger；
- 不建 Project；
- 不部署审批；
- 手工或 Excel 导入合同、义务、票据和收款；
- 使用简单组织权限。

结果：合同和收支仍能完整运行，证明 Project 与 Approval 都不是隐藏的强制依赖。

## 九、解耦验收清单

以下测试同时成立，才可声称“最大程度解耦”：

- 移除审批模块后，合同和收支命令仍可执行；
- 没有 Project 时，合同和 money-flow 仍可独立建账；
- 没有合同系统时，money-flow 可用外部来源或人工依据建义务；
- 文件存储从 MinIO 换成其他实现，不改领域代码；
- 客户把“经营经理”改名或重组岗位，不改合同和收支代码；
- 新增第三层、第四层合同关系，不改合同表结构；
- 合同新 revision 不会静默改写历史义务；
- 一笔回款可分配多个义务，多笔回款可结清一个义务；
- 未分配现金不会因报表计算被丢弃；
- 所有汇总可下钻并从事实重建；
- 一个客户新增管理费或奖金，不向通用内核添加专用字段；
- 同一模块可在单体内调用，也可在未来拆服务后保持公共契约。

## 十、技术演进路线

### 阶段 1：先做边界，不急着做平台

- 定义值对象、命令、事件和来源快照契约；
- 用领域测试固化合同演算和核销不变量；
- 合同与 money-flow 作为模块化单体内两个独立模块；
- 先提供基础 API 与管理界面，不做低代码平台。

### 阶段 2：补公共适配能力

- Party、Identity & Access、Evidence；
- DecisionGate 的 allow adapter 和审批 adapter；
- outbox、导入幂等和审计；
- 客户装配层与行业扩展。

### 阶段 3：基于真实客户抽取稳定扩展

- 管理费、奖金、工资、报销、项目包等独立模块；
- 只有重复出现且语义一致的规则才提升为公共策略；
- 为每个 adapter 建立契约测试，避免客户分支侵入内核。

### 阶段 4：有证据再拆服务

只有出现以下情况才考虑独立服务：

- 独立扩缩容需求；
- 数据隔离或合规要求；
- 明确团队所有权；
- 独立发布节奏；
- 外部客户需要单独购买和部署。

拆分时沿既有命令、事件和数据所有权边界移动，不重新发明业务模型。

## 十一、质量基线

### 领域测试

- 合同变更顺序、重述、调整和结算；
- 金额精度与币种约束；
- 义务调整、部分核销、多对多核销；
- 退款、冲销和未分配资金；
- revision、幂等和并发冲突。

### 模块契约测试

- 命令输入输出；
- 事件 schema 与兼容性；
- Source Snapshot Reference；
- DecisionGate、Evidence、Party 和 Authorization adapter。

### 装配场景测试

- 设计单位；
- 资质施工综合体；
- 无项目、无审批的小型服务公司。

测试目标不是覆盖某个页面，而是证明每个小系统独立成立、组合后不产生双重真相。

## 十二、阶段性产品判断

当前最合理的产品方向不是先卖“通用工程管理平台”，而是先把以下两个小系统做实：

1. **合同台账**：稳定处理主体、版本、变更、金额、结算、关系和证据；
2. **经营收支台账**：稳定处理义务、票据、资金、核销、余额和预测。

审批、权限、文件、奖金、人员和项目管理围绕它们按需组合。这样商务可以针对客户搭建不同产品外观和流程，而研发只维护少量稳定事实内核与扩展契约。

## 后续讨论入口

阶段性总体设计已经形成。继续讨论时，优先从以下三个方向中选择一个：

1. 用一组真实合同、回款和付款样例走完整模型，验证遗漏；
2. 深入 Party + Identity & Access，区分业务参与方、登录用户和授权范围；
3. 把当前候选蓝图转成新项目的正式产品规格与技术方案。

在没有真实样例或正式立项之前，不建议继续增加内核对象或代码框架。
