# ADR-0001：初始技术栈

日期：2026-09-19  
状态：接受，用于 M0-M2；出现明确反证时重新评审

## 背景

首要目标是快速交付稳定、独立、范围窄的小系统，而不是建设前后端基础平台。既有 OA 项目证明团队环境能够支持 Go 和 React，但 BizFoundry 不复制其业务架构。

## 决策

初始采用：

- Go 1.25+ 兼容模块，使用当前 Go 1.26 补丁工具链开发；
- Go 标准库 `net/http`、`html/template`、`log/slog`；
- PostgreSQL 18；
- `pgx/v5` 作为唯一初始运行时第三方依赖；
- 内嵌 SQL migration；
- 服务端渲染基础页面，不在 M0 引入 React 构建链。

## 原因

- 单一二进制、依赖少、启动和部署边界清晰；
- Go 的兼容承诺和标准库适合长期维护；
- PostgreSQL 提供事务、精确数值、约束、并发和可靠备份能力；
- `pgx` 是稳定的 PostgreSQL Go 驱动，避免 ORM 模型泄漏到系统边界；
- 服务端渲染能够更快完成第一批后台业务闭环；
- 未来如出现复杂交互证据，可以在公开 HTTP 契约之上增加独立前端，不影响领域和数据边界。

## 未选择

- 未采用 OMS 原型中的 beta 前端运行时；
- 未直接复制 OA 的 Gin、GORM 和 React 组合；
- 未采用微服务基础设施、消息队列或统一网关；
- 未在业务需求明确前引入 ORM、流程引擎和动态表单引擎。

## 后果

- 初期允许两个应用存在少量启动和数据库代码重复；
- 页面以稳定可用为先，不追求首版复杂前端体验；
- SQL 和领域映射需要显式维护；
- 如未来选择独立前端，需要新增 API 契约测试。

## 重新评审触发条件

- 服务端渲染无法满足已经确认的关键交互；
- 团队无法稳定维护 Go；
- 目标部署环境不能运行 Go 或 PostgreSQL；
- 实测交付效率低于替代方案且问题不能通过局部调整解决。
