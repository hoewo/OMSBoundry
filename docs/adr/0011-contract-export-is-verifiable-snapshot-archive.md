# ADR-0011：合同导出采用可验证的单合同快照归档

日期：2026-09-19  
状态：Accepted；恢复部分由 ADR-0012 扩展

## 背景

Contract Ledger 已经形成草稿、不可变 Revision、Instrument、关系、结算、关闭、Evidence 和受控更正。M2 要求数据可导出并为后续恢复建立入口，但简单的合同列表 CSV 不能保留历史语义；直接把 PostgreSQL 备份当作产品导出又会暴露内部结构、凭证和存储位置，并把恢复、版本兼容和运维环境耦合在同一步里。

更正能力尤其要求导出同时保存旧 Revision、新 Revision 和仍然引用旧 Revision 的既有事实。导出还需要能够在不运行本系统的环境中验证内容是否发生非预期改变。

## 决策

1. 第一版导出单元是一份 Contract ID 的完整业务账簿，不是列表行、页面投影或全库备份。
2. 使用版本化 ZIP，固定包含 `manifest.json` 与 `ledger.json`；manifest 保存 ledger 原始字节的 SHA-256 和长度。
3. SHA-256 直接覆盖归档中的 `ledger.json` 字节，不引入第一版尚不需要的 JSON 规范化、数字签名或自引用 ZIP 摘要。
4. 全部数据在一个 PostgreSQL `REPEATABLE READ, READ ONLY` 事务中读取，保证跨表导出来自同一数据库快照。
5. 正式历史、当前投影、双向关系、Settlement、Closure、Evidence 元数据和通用审计进入 ledger；身份凭证、Evidence 二进制、`storage_key` 和内部幂等 payload hash 不进入。
6. Evidence 二进制继续由独立文件存储和下载能力负责；导出保留其 SHA-256 与大小，使后续取得文件内容时可以核验。
7. 完整归档只允许 administrator 使用新增的 `business.export` 权限下载。
8. 服务先构造归档，再记录 `contract_ledger_exported` 审计，审计成功后才发送字节。该审计不放入它自身记录的快照。
9. 本次只实现导出。该历史决策随后由 ADR-0012 增加严格的空业务库单合同恢复；全库备份和格式迁移仍分别设计。

## 原因

- 每合同归档符合当前小系统的真实使用和交接边界，又不会提前建设批处理平台。
- JSON 能明确表达嵌套 Revision、Party Snapshot 和引用关系；ZIP 提供稳定容器，并允许以后在新格式版本中有控制地增加文件。
- 对精确 ledger 字节求摘要，使任何标准 SHA-256 工具都能验证，避免不同 JSON 实现的序列化差异。
- 一致性只由 Contract Ledger 自己的 PostgreSQL 事务保证，不引入跨系统分布式快照。
- 先稳定可验证的业务归档，再讨论恢复，能够让恢复规则依据真实格式版本而不是猜测内部表结构。

## 后果

- 导出不是可直接 `pg_restore` 的数据库备份，也不能单独恢复 Evidence 文件内容；用户界面和文档必须明确这一点。
- 导出需要一次性在内存中构造归档，适合第一版单合同范围；大合同上限、流式生成或后台任务需要有实际规模证据后再设计。
- 每次成功导出都会新增访问审计，因此后续归档即使业务事实未变也可能有不同的 ledger 摘要和生成时间。
- 格式一旦交付就需要版本兼容。字段的破坏性改变必须使用新的格式标识／版本，不能静默改变 v1 语义。
- 恢复能力已经由 ADR-0012 在“空业务库、无 Relation、Evidence 字节缺失”的窄边界内完成；其他导入、合并、全库备份和 Evidence 内容恢复仍不是本 ADR 的能力。

## 被否决方案

### 只导出当前合同列表或 CSV

不能表达多个 Revision、嵌套主体快照、双向关系和旧 Revision 引用，也无法证明当前投影来自哪条历史。

### 直接向客户提供 PostgreSQL dump

会把内部表、身份与存储实现暴露为产品契约，也无法安全地区分业务归档和环境级灾难恢复。

### 把 Evidence 二进制全部打进 ZIP

会使一次同步 HTTP 下载的体积和失败模式由文件存储决定，并可能暴露内部路径。第一版通过版本校验元数据保持可验证引用，完整文件备份另行设计。

### 在同一功能中同时实现导入和恢复

在导出格式和真实样例尚未验证前实现反向写入，会过早决定冲突、幂等、版本迁移和部分失败语义，风险远高于单向导出。
