# ADR-0015：Money Flow 在财务事实前建立独立身份边界

日期：2026-09-19  
状态：Accepted

## 背景

Money Flow Ledger 当前只有数据库 migration、健康检查和公开首页。M3 计划随后登记主体、应收应付义务、实际资金和核销；这些事实一旦写入，就必须能够证明是谁执行了动作，并由服务端权限边界而不是请求字段决定 Actor。

直接先做匿名义务写入，或临时接受 `actor_id` 表单字段，会在不可变财务事实中留下无法可信修复的历史。要求先部署 Contract Ledger 身份、客户 OA 或共享 IAM，又会破坏 Money Flow 独立交付边界。

## 决策

1. `MF-M3-001` 先实现 Money Flow 自己拥有的首位管理员、登录会话、CSRF 和不可变身份审计，再开始 Party 与 Obligation 写入。
2. 空用户库通过显式 bootstrap 配置原子建立一名 active administrator；任意用户已存在时不覆盖。
3. 密码只保存 BCrypt 摘要；会话令牌只在客户端出现，数据库保存 SHA-256。
4. 受保护请求从服务端会话解析 Principal；未来业务 Actor 只能由 Principal 构造。
5. 会话代次、状态和过期时间均参与解析，为后续密码变更和停用提供统一失效点。
6. 第一功能只交付首位管理员的登录／注销，不顺带实现完整用户后台、外部身份或组织模型。
7. Money Flow 与 Contract Ledger 即使采用相似本地身份语义，也各自保存用户、会话、Cookie 和审计，不抽取共享运行时包。

## 原因

- 先建立可信 Actor，后续不可变义务、资金与核销从第一条记录起就不需要身份回填。
- bootstrap 使空环境可以独立进入可用状态，同时避免把测试用固定 Actor 带进产品。
- 原始 session token 不落库，数据库泄露不会直接得到可复用 Cookie。
- 本地身份是默认适配器，不妨碍未来用外部 SSO 替换认证入口，但外部适配器仍须产生同一 Principal 边界。
- 先只做首位管理员，使本轮保持一个可独立验收的功能；多用户生命周期在真实需要出现时单独闭环。

## 后果

- 第一笔 Money Flow 业务事实会比原计划晚一个功能，但不会产生匿名或可伪造的历史。
- 初期只有首位管理员可使用系统；添加第二名用户前必须另立用户管理功能，不能直接手改生产数据库。
- 两个应用暂时存在少量相似身份代码，这是维护独立部署与数据所有权的有意重复；只有两个实现都稳定后才评估共享技术原语。
- bootstrap 密码必须由部署环境安全注入，首次成功后从运行配置移除。

## 被否决方案

### 先允许匿名或固定 Actor 写义务

无法证明真实操作者，后续回填会伪造历史，不符合不可变财务事实要求。

### 让请求提交 actor_id

客户端可以冒充其他用户；审计只能证明请求内容，不能证明执行身份。

### 复用 Contract Ledger Cookie 或用户表

会形成运行和数据耦合，Contract 停止、未安装或升级时 Money Flow 不能独立工作。

### 立即建设共享 IAM 或完整组织权限平台

当前没有跨客户稳定证据，范围远超 M3 最小纵向闭环。

### 复制 Contract Ledger 的全部用户管理功能

角色变更、停用、重置和自助改密都值得独立验收；本轮只实现形成后续可信 Actor 所需的最小入口。
