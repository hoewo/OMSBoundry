# ADR-0009：合同证据使用版本化引用与内置文件适配器

日期：2026-09-19  
状态：Accepted

## 背景

Contract Ledger v1 需要保存合同文件与 Evidence Reference，同时必须保持独立安装：客户不能为了上传一份合同先部署统一文件中心、对象存储或文档平台。现有讨论又明确区分结构化合同事实和文件二进制，要求业务内核只依赖稳定引用，并保留以后替换存储实现的能力。

文件具有覆盖、路径穿越、内容伪装、未授权下载、数据库与文件不一致等额外风险。只在 Contract 表增加一个文件名或磁盘路径既不能表达版本，也不能证明内容是否变化，更无法安全替换存储。

## 决策

1. 在 Contract Ledger 应用内实现 Evidence 用例与端口，不建设共享 Evidence 服务。
2. Evidence Document 表示稳定逻辑文件，Evidence Version 表示不可变字节版本；修改内容只能追加连续版本。
3. Contract Evidence 只引用 Contract、Instrument、Settlement 或 Closure 四种本地不可变／稳定目标，目标所属关系由 repository 与数据库触发器双重验证。
4. Version 保存服务端生成的 storage key、实际大小、服务端探测媒体类型和完整 SHA-256；用户文件名只作为受限显示元数据。
5. 默认 Blob Store 使用配置目录下的本地文件系统。业务与 HTTP 层不感知实际路径，未来对象存储实现必须保持同一 Put/Open/Delete 契约与完整性校验语义。
6. 文件先以限制权限写入并原子落盘，再在 PostgreSQL 事务中提交 Document、Version、command 和上传审计。数据库失败或幂等重放时清理本次候选对象。
7. 下载前使用同一文件描述符验证大小和 SHA-256；下载只采用 attachment，不提供内联预览。
8. 每次授权下载写入不可变审计，审计失败时不交付文件。
9. cancelled 和 closed 合同仍可追加 Evidence，因为该动作只补充佐证，不改变核心业务事实。

## 原因

- Document/Version 分离可以表达“同一逻辑文件的新扫描件或更正版”，而不会覆盖历史内容。
- 内容哈希把 Reference 与实际字节绑定，能够检测意外损坏或存储替换。
- 本地适配器让单机安装默认可用，也保留替换 MinIO、S3 或客户文档系统的端口。
- 固定本地目标类型比万能字符串引用更容易执行授权、所属校验和历史展示。
- 强制下载审计使文件访问与已有可信 Actor 模型一致。

## 后果

- 部署必须为 Evidence 目录提供持久存储、限制操作系统权限，并把该目录与 PostgreSQL 纳入一致备份。
- PostgreSQL 与本地文件系统没有分布式事务。当前顺序保证不会正常提交一个尚未成功落盘的 Reference，并对可观察失败做补偿删除；极窄的进程崩溃窗口可能留下未引用孤儿对象。M6 需要实现并演练只清理超过安全年龄且数据库未引用对象的巡检。
- 第一版不能在线预览、扫描恶意内容或验证电子签章。下载强制为 attachment，部署方仍应在需要时于存储适配器前后接入安全扫描。
- Evidence 追加不推进 Contract revision；如果文件揭示结构化事实错误，必须走后续受控纠错能力，而不是把上传视为事实更正。

## 被否决方案

### 直接把文件路径写进 Contract 或 Instrument

路径会泄漏存储实现，缺少版本、哈希、幂等与访问审计，也无法安全迁移到其他存储。

### 把二进制保存在 Contract 业务表

虽然容易获得单事务，但会把大对象、业务事实和存储生命周期耦合在一起，不符合可替换 Evidence Port，并增加常规查询和备份压力。

### 第一版强制部署对象存储

会破坏 Contract Ledger 的默认独立可用性；当前规模与客户证据不足以证明该运行依赖合理。

### 只保存外部 URL

URL 不能证明内容未变化，容易绕过访问控制并引入失效、SSRF 或公开泄漏问题。外部证据需要未来独立契约。
