# ADR-0013：全量备份是同一快照下的数据库与 Evidence 集合

日期：2026-09-19  
状态：Accepted

## 背景

单合同账簿导出和恢复解决的是可移植业务归档，不包含 Evidence 字节、本地身份或完整数据库，因此不能承担灾难恢复。Contract Ledger 当前把事实保存在 PostgreSQL，把文件字节保存在应用独占的本地目录；只备份其中一侧会产生不可下载的引用或失去业务元数据。

简单地先执行 `pg_dump`、再复制整个 Evidence 目录也没有明确一致性时点，并且会把失败上传临时文件、未引用候选文件和未来实现细节带入备份。

## 决策

1. 全量备份采用版本化单 ZIP，由 custom-format PostgreSQL dump、严格 manifest 和该数据库 snapshot 实际引用的 available Evidence 文件组成。
2. 工具用 PostgreSQL 导出 snapshot 同时约束 `pg_dump`、schema／计数和 Evidence 引用查询；文件按数据库记录的大小与 SHA-256 收集。
3. 不复制 Evidence 根目录中的 `.tmp`、孤立文件或其他未引用内容；`missing` Version 只随数据库恢复。
4. dump 排除 `local_sessions` 数据，保留用户、密码摘要、权限、审计及所有业务事实。
5. 恢复只面向真正空的数据库和不存在的 Evidence 根目录，拒绝覆盖、清空和合并。
6. Evidence 先校验并原子发布，数据库再通过 `pg_restore --single-transaction` 恢复；数据库失败时只回收带本次标记的已发布目录。
7. 恢复后强制核对 migration、计数、空会话和 Evidence 引用。跨资源最终核验失败时隔离目标，不执行未经授权的数据库清空。
8. PostgreSQL 客户端是显式依赖，并允许应用连接与客户端连接使用不同网络地址访问同一数据库集群。

## 原因

- 导出 snapshot 给数据库 dump 与文件引用集合一个可解释、可测试的时点。
- 复用 Evidence 已有的“先原子落盘、后提交引用”和不可变 Version 约束，不需要停服或建设分布式锁。
- 按引用收集比复制整个目录更小，也不会把上传临时状态当成正式事实。
- custom dump 保留数据库约束、触发器和完整身份／业务事实；排除会话能避免恢复旧 Cookie。
- 空目标和单事务恢复把失败边界保持在可重试范围内，避免定义未经验证的合并语义。

## 后果

- 备份文件本身含敏感身份摘要和业务附件，必须使用受控存储；v1 不内置加密。
- PostgreSQL custom dump 仍受客户端／服务器版本兼容规则约束；跨 major 升级必须走独立升级演练。
- PostgreSQL 与文件系统没有共同事务。工具可以安全处理 restore 失败，但 restore 已提交后的核验异常需要隔离并重建目标，不能伪称原子成功。
- 数据库中存在 `missing` Evidence 时，全量恢复后仍然是 `missing`；本功能不会伪造原始字节。
- 在线备份会持有一个只读 snapshot，超大数据库需要在部署层设置容量、超时、调度和监控。

## 被否决方案

### 只写一份运行手册，分别执行 dump 和目录复制

两步没有共享一致性时点，也没有逐文件摘要闭环，无法自动判断得到的集合是否可恢复。

### 停服后复制 PostgreSQL 数据目录

这与数据库部署和存储实现强耦合，不适合作为应用级最小交付入口，也不能用于托管 PostgreSQL。

### 把 Evidence 字节塞进数据库

会改变已经验证的 Evidence 存储边界，只为备份方便付出运行时存储和迁移成本。

### 直接复制整个 Evidence 根目录

会包含临时文件、失败候选和未引用对象，且不能证明每个对象对应哪个数据库 snapshot。

### 自动清空非空目标后恢复

这是破坏性覆盖能力，超出灾难恢复的最小安全边界；v1 要求运维人员显式提供全新空目标。
