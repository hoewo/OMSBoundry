# 稳定 Base 与客户覆盖层调研

## 状态

本调研给出跨客户产品线的候选技术方向。首个参考 OA 已证明稳定应用、类型化扩展和客户装配可以共同工作，但尚未证明多个真实客户能够长期共享同一 Base。本方向处于调研中，不构成跨客户适配已经成立的声明。

## 要解决的问题

每个客户直接复制一套代码能够快速满足首次差异，但会形成长期分支、重复修复和无法统一升级。把所有差异提前抽成通用平台又会把未知业务压成万能字段、万能流程和不可靠抽象。

候选方向需要同时满足：

- 已验证的小应用内核持续共享和升级；
- 客户差异具有明确归属、独立生命周期和可移除性；
- 新客户优先增加内容，不重写既有业务事实；
- 真实差异能够反向修正 Base，而不是被覆盖层永久掩盖；
- 任意客户部署仍保持应用数据所有权、鉴权和恢复边界。

## 术语

### Base

Base 是经过独立产品和组合验收的版本化发布集合，包括业务应用镜像、公开契约、migration、IAM 契约、Evidence 契约、装配组件和兼容规则。Base 不等于所有客户必须安装的完整套件；Suite Manifest 从 Base 中选择当前组合。

### Customer Overlay

Customer Overlay 是面向一个客户或一类已确认场景的版本化增量包。它声明组合、显示、策略、扩展、连接器、投影和专项内容，但不替换 Base 的可写业务事实、公开契约含义或安全边界。

### Deployment Instance

Deployment Instance 是 Base、Customer Overlay、Suite Manifest、Deployment Profile 和环境秘密在一个客户环境中的实际装配。实例数据、秘密和备份属于该环境，不回流为 Base 或 Overlay 内容。

## 候选模型

目标形态在交付感受上类似“从稳定架子开始增加客户内容”，但不是长期 Git fork：

| 层次 | 可以承载 | 不得承载 |
| --- | --- | --- |
| Base 应用 | 稳定事实、状态机、历史、不变量、公开契约 | 客户名称、客户岗位、客户专用条件分支 |
| 配置 | 术语、显示、启用能力、枚举定义 | 不同事实含义或不同纠错生命周期 |
| 版本化策略 | 明确输入、输出、版本和追溯的计算／决定 | 隐藏 SQL、页面公式或不可重放脚本 |
| 类型化扩展 | 有独立状态机和验收的行业业务类型 | 向通用 Project 填入所有行业字段 |
| 连接器 | 公开契约之间的幂等建议、命令或事件 | 写目标数据库或替目标应用确认事实 |
| 客户装配 | Suite Manifest、旅程、菜单、角色映射、外部接口 | 修改公共镜像、共享业务表 |
| 客户专项 | 报表、导入、迁移和一次性适配 | 阻止 Base 升级或成为第二套公共内核 |

## “尽量只做加法”的准确含义

加法表示客户交付优先增加新装配声明、新策略版本、新类型化扩展、新连接器、新只读投影或隔离专项包。它不表示 Base 永不修改，也不表示所有变化都可以堆在覆盖层。

以下变化必须回到 Base：

- 已有业务事实或不变量本身错误；
- 两个以上独立场景证明同一语义稳定复用；
- 公共契约缺少所有消费者都需要的兼容能力；
- 安全、数据完整性、性能或恢复缺陷影响所有部署；
- 覆盖层为绕过错误边界而复制可写事实或长期分叉。

Base 的修改继续采用向后兼容契约、显式 migration 和完整回归。客户覆盖层不能覆盖 Base 文件来伪造“只做加法”。

## 选择规则

每个客户差异依次回答：

1. 它是否只是术语、显示或启用选择；若是，进入配置或 Suite Manifest。
2. 它是否在相同事实输入上采用不同计算；若是，进入版本化策略。
3. 它是否拥有独立状态、纠错和历史；若是，进入类型化扩展或新业务应用。
4. 它是否只负责在两个公开契约间搬运并确认动作；若是，进入连接器。
5. 它是否只在一个客户成立且没有复用证据；若是，进入可删除的客户专项。
6. 它是否改变现有事实所有权、历史或安全边界；若是，覆盖层拒绝承载，重新审查 Base 边界。

## 装入与升级边界

- Overlay 声明唯一标识、版本、兼容的 Base 版本范围和所需 Capability；
- Overlay 只迁移自己拥有的状态，不执行其他应用数据库 migration；
- Suite Manifest 校验应用、扩展、策略和连接器依赖，不靠隐藏进程补齐；
- Workbench 根据已验证清单装入页面与旅程，不以菜单隐藏代替服务端权限；
- Base 升级前验证 Overlay 兼容范围、公开契约、数据迁移、回滚和备份恢复；
- 同一 Overlay 可以装入不同 Deployment Profile，节点放置不改变业务语义；
- 客户秘密、证书、域名、OSS、数据库数据和备份不进入 Overlay 制品。

## 可证伪门槛

该方向只有在多个真实场景中持续满足以下结果才可以升级为已采用产品线方案：

- 同一 Base 版本支持不同 Suite Manifest 和 Overlay；
- 客户交付没有长期核心分支、共享业务表或现场核心补丁；
- 新客户变化主要落入已有层次，且每项只有一个责任位置；
- Base 升级不丢失客户数据、ID、revision、历史和业务引用；
- 移除某个 Overlay 后，Base 应用仍能完成自己的主要闭环；
- 客户专项数量和复杂度不持续增长为隐藏第二套系统；
- 交付时间、变更范围和回归成本相对从头定制出现可测量下降。

以下任一现象构成反证：

- 每个客户都需要修改同一核心状态机；
- Overlay 必须读取或写入应用内部表；
- 一个客户升级需要合并长期 Git 分支；
- 同名策略在客户间具有不同事实含义或纠错规则；
- 为页面连贯而复制其他应用当前状态；
- 大量客户专项无法删除、迁移或独立验收。

## 首轮 OA 完整体验证结构

首轮以参考 OA 完整业务范围检验该方向，不以继续增加页面数量作为证据。每个业务增量同时记录：

- Base 的兼容修改及其公共理由；
- Overlay 新增的配置、策略、类型化扩展、连接器、只读投影或专项；
- 应用、公开契约、migration 和 Suite Manifest 版本；
- 最小组合中实际选择与未选择的应用；
- 独立启动、故障隔离、升级、回退和恢复结果；
- 客户核心分支、共享业务表、现场核心补丁和无法升级 Overlay 的数量。

同一增量先在本地完成业务与边界证据，再把相同镜像摘要、migration、Suite Manifest 和 Overlay 提升到真实 Ubuntu 环境。目标环境可以是获授权的公司私服，也可以是 ICP 生效后的个人阿里云试验田；两者的秘密、数据、备份和环境证据分别拥有，不从一个环境隐式继承到另一个环境。

缺少真实环境不否定本地业务证据，但不能证明完整交付路径。最终验证报告因此把业务可行性、边界可行性、定制化可行性和环境可交付性分栏判断，并在任一核心证据缺失时给出 `insufficient-evidence`，而不是把局部通过外推为整体成功。

下一轮参考应用保持待选。其选择要求具有不同的业务结构或纠错方式、可合法取得的脱敏证据，以及至少一个能够挑战当前 Base／Overlay 边界的真实差异。

## 当前结论

稳定 Base 加客户覆盖层是目前最符合“小系统可复用、客户差异可控、尽量只做加法”目标的候选方向。首个参考 OA 的高保真组合证明了配置、`design-v1` 类型化扩展、客户装配和加法契约修正可以成立，也证明无证据能力可以被拒绝而不污染内核。

现有证据只有一个参考产品和合成子组合，不能证明跨客户长期升级。第二个独立真实客户、OA 完全体增量和真实策略样例是继续验证该方向的必要证据。

## 未决技术问题

- Overlay manifest 的正式 Schema、签名、依赖解析和兼容失败格式；
- 类型化扩展是独立进程、应用内插件还是二者并存的选择准则；
- 客户页面覆盖与公共前端组件之间的版本隔离；
- 客户只读投影的重建、延迟、权限和故障降级；
- Overlay 升级和回退的原子性，以及跨多个应用契约版本的兼容矩阵；
- 客户专项达到何种重复证据时提升为 Base 能力。
