# 独立 Demo 体验基线

## 元信息

- 状态：🟢 已接受
- 适用范围：Contract Ledger、Money Flow Ledger、People & Groups、Evidence Service、Project Workspace、Design Operations 的独立 Demo
- 不适用范围：统一 Workbench、客户品牌主题、生产身份管理、完整公网入口

## 问题与可验证结果

六个小系统已经能够用自动化脚本证明业务闭环，但页面缺少用途说明、任务路径和一致反馈，非开发者进入后无法判断“这是做什么的、现在有什么数据、下一步点哪里”。每个独立 Demo 提供自解释的入口、任务导航、业务页面和恢复说明后，用户无需阅读源码或拼接 API 就能完成一条代表性路径并核对结果。

“简单”表示少层级、少装饰、少分支，不表示裸 JSON、空白页面或只提供接口文档。统一视觉品牌可以延期，但页面框架、业务术语、操作顺序、结果反馈、历史和错误恢复不能延期。

## 目标用户与使用边界

### Demo 操作者

Demo 操作者启动本地环境、进入一个小系统、按推荐路径操作合成数据并核对结果。操作者可以不是开发者，不需要理解 HTTP 方法、数据库表或容器名称。

### 方案评估者

方案评估者比较小系统的职责、能力和状态历史，判断系统是否可独立使用、是否保留数据所有权以及组合时哪些事实通过公开契约流动。

### 工程诊断者

工程诊断者可以从帮助区进入 API、健康检查、演示脚本和日志说明。工程入口属于次级信息，不占据业务页面主路径。

独立 Demo 使用合成数据和模板 IAM。页面必须明确显示“演示环境”，不得让操作者误以为它连接真实客户数据或生产身份系统。

## 页面框架

每个小系统至少提供以下三类页面角色；规模较小的应用允许把列表与工作区合并，但不能删除对应信息和操作语义。

### Demo Overview

根路径 `/` 是人类可读的系统首页，不以 JSON、404 或 API 清单作为主要内容。首页固定回答：

1. 这个系统拥有哪类业务事实；
2. 当前运行的是独立 Demo 还是组合模式；
3. 当前使用什么数据与身份；
4. 推荐从哪一步开始，完整路径有几步；
5. 已有多少关键记录、最近发生了什么；
6. 如何重跑、重置、排错和查看 API。

首页的主操作进入推荐业务路径，次级操作进入记录列表。健康检查、API 与脚本说明放在帮助区，不与业务主操作竞争。

### Records List

列表页面以领域语言展示记录，不显示内部结构体或未经解释的 JSON。页面提供：

- 当前记录类型和它解决的问题；
- 搜索或最小必要筛选；
- 关键状态、业务金额或责任人、更新时间；
- 明确的主操作；
- 加载、内容、空和错误状态；
- 空状态中的创建或生成演示数据入口。

列表行点击进入记录工作区。状态颜色只作辅助，文本标签始终存在。

### Record Workspace

记录工作区同时显示业务摘要、当前状态、可执行动作、关联事实和修订历史。主操作来自服务端 `allowed_actions` 或同等授权结果；隐藏按钮不能代替服务端授权。

改变事实的操作先显示影响范围和必要输入，提交后在原位显示结果、稳定 ID、revision 和下一可执行动作。发生并发冲突、非法状态或外部引用不可用时，页面保留用户输入并给出可恢复路径。

## 通用信息架构

桌面端使用稳定的三层结构：

1. 顶部产品栏：产品名称、演示标识、运行模式、身份与帮助；
2. 左侧或横向局部导航：首页、当前领域记录、历史／审计；
3. 主工作区：页面标题、上下文说明、主操作、业务内容和原位反馈。

独立 Demo 不展示未启动的小系统入口，也不通过前端隐藏制造“可选应用”假象。完整组合可以由 Workbench 提供跨应用导航，但各应用自身页面仍保持可直接进入和独立理解。

## 六个系统的首页任务路径

| 小系统 | 首页必须解释的事实所有权 | 推荐路径 | 首个业务页面 |
| --- | --- | --- | --- |
| Contract Ledger | 主体、合同、合同修订、结算与合同审计 | 建立主体 → 起草合同 → 激活 → 查看变更与结算 | 合同列表 |
| Money Flow Ledger | 正式义务、资金、核销、余额和经营投影 | 确认义务 → 登记收付款 → 核销 → 查看余额与纠错 | 经营概览或义务列表 |
| People & Groups | Person、Group、Membership、能力画像和名册快照 | 建立人员 → 建组 → 加入成员 → 生成名册快照 | 人员与组概览 |
| Evidence Service | File、Version、上传会话、校验与短期访问 | 建立上传 → 传输文件 → 完成校验 → 下载／预览 | 文件列表 |
| Project Workspace | Project、Assignment、Resource Link 与项目历史 | 建立草稿 → 分配责任 → 关联资源 → 立项 | 项目列表 |
| Design Operations | Design Work Item、阶段、负责人和成果引用 | 建立工作项 → 指定负责人 → 登记成果 → 推进阶段 | 设计工作项列表 |

## 状态与反馈

- 首次加载只骨架化数据区域，产品身份和页面用途保持可见。
- 空状态解释为什么为空，并只提供一个推荐下一步。
- 成功反馈紧邻触发区域，显示结果名称、稳定 ID、revision 与下一步。
- 字段错误就地显示；页面级失败显示原因、影响范围和重试入口。
- 并发冲突明确区分“重新加载最新状态”和“放弃当前编辑”。
- 外部引用不可用时标明不可用来源，不把当前应用自身记录伪装成失败或成功。
- 终态或无权限动作可见但不可用时，页面说明原因；安全要求禁止暴露的动作可以隐藏。
- 长任务显示进行状态并阻止重复提交；幂等重放说明复用已有结果而非再次创建。

## 视觉表现基线

页面采用克制的业务工具风格：浅色中性背景、深色正文、单一冷色交互强调、低圆角、细边框和紧凑但不拥挤的间距。视觉层级依赖排版、留白和位置，卡片只用于确有边界的摘要、帮助或状态块，不把每段内容都包装成卡片。

状态不能只依赖颜色。危险操作使用暖色语义和二次确认；成功、警告与错误反馈均包含图标或文字标签。正文在桌面端保持可读行宽，表格在窄窗口优先保留关键列并允许横向滚动。

此基线是演示产品的可用性约束，不是最终客户品牌方案。客户 Logo、品牌色、营销插画和暗色主题在有明确依据后单独确认。

## 验收条件

### 单应用入口

- 六个应用的根路径都返回人类可读页面，并明确产品用途、演示模式和推荐路径；
- 根路径不再以裸 JSON 或 404 作为操作者入口；
- 页面提供业务主操作、记录入口、历史／审计入口和帮助入口；
- 页面可以在未启动其他业务应用时完成自身解释和主闭环导航。

### 业务操作

- 每个应用至少有一条代表性路径可以从首页开始、完成操作并核对稳定 ID／revision；
- Project 与 Design 不再要求操作者手写 HTTP 请求完成代表性路径；
- Evidence 提供文件入口、上传状态、校验结果和访问入口，不把对象存储细节暴露为主要交互；
- 原有鉴权、幂等、并发、历史和失败关闭语义保持不变。

### 状态与恢复

- Overview、Records List 和 Record Workspace 均覆盖加载、内容、空和错误状态；
- 高风险操作覆盖确认、进行、成功和失败恢复；
- 外部依赖不可用、无权限、非法状态和并发冲突至少各有一个与应用边界相称的可见反馈；
- 自动化业务验收与浏览器关键路径验证同时通过，二者互不替代。

## 不负责的相邻问题

- 本基线不改变 Nginx、Gateway、IAM、Workbench 或数据所有权；
- 本基线不把独立 Demo 变成生产系统，也不使用真实客户数据；
- 本基线不承诺最终品牌、营销页面、移动端原生应用或通用低代码界面；
- OMS 作为第二个参考产品的业务边界比较属于独立证据工作，不由界面基线自动完成；
- 第二个真实客户场景仍需经过客户确认、匿名化和 Customer Scenario Evidence 门槛。
